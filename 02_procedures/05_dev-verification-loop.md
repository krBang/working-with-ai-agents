# 개발 환경 검증 루프

「반영됐다」는 말을 들었을 때, 또는 기능을 검증하라는 요청을 받았을 때의 절차. 스킬로 만든 것은 [`dev-verify`](../04_skills/dev-verify/SKILL.md).

## 왜 절차가 필요했나

- 이미 처리된 데이터 하나로 확인하고 끝냈다. 「검체가 없으면 만들어야 할 것 아닌가」.
- 테스트 케이스 표 없이 시작했다. 「왜 이런 건 케이스를 안 만들어서 하나」.
- 특정 채널은 사용자가 시켜서야 테스트했고 거기서 오류가 나왔다. 「안 시켰으면 몇 개나 놓쳤나」.

공통 원인은 **만든 쪽이 자기 케이스를 통과시키는 구조**였다. 그래서 생성과 검증을 분리한다.

## 1. 테스트 케이스 표부터(실행 전)

- 주제 폴더에 TC 문서를 만든다. 열: `TC | 케이스 | 입력 | 기대 | 결과 | 검체`.
- **기대**에는 응답값뿐 아니라 **DB 상태 변화**(어느 테이블·컬럼이 무엇으로)까지 적는다.
- 아래 축을 하나씩 대 본다. 해당 없으면 「해당 없음 — 이유」를 적는다. 빈칸으로 넘기지 않는다.

| 축 | 넣을 것 |
|---|---|
| 정상 | 대표 정상 1회 이상, 상태가 실제로 바뀌는 경로 |
| 오류 | 없는 키, 업무 불일치, 필수값 누락, 중복·재처리 |
| 채널·유형 | 데이터가 다른 테이블에 저장되는 채널, 다른 거래 유형, 외부 연동 채널 등 — **프로젝트의 채널 목록을 표로 고정해 둔다** |
| 취소 | 부분 취소 후 · 전체 취소 후 |
| 후속 | 이벤트 발행·수신, 다음 단계(정산·집계 등)로 넘어가는지 |

채널 축이 특히 중요하다. 어떤 채널의 데이터는 주 테이블에 행이 없어서, 주 테이블을 내부 조인하는 새 API는 그 채널에서만 「없음」을 돌려준다.

템플릿: [`templates/tc-document.md`](../templates/tc-document.md)

## 2. 독립 검토(실행 전)

- 검증 역할 에이전트에 **TC 표와 변경 diff 경로만** 주고 「빠진 채널·경로·DB 판정 기준」을 찾게 한다. 내 결론(「충분하다」)은 넘기지 않는다.
- 검토 지적은 코드로 재확인하고 ✅반영 / ⚠오탐을 표에 남긴다. 반영한 뒤 실행한다.

## 3. 검체는 직접 만든다

- 맞는 검체가 없으면 묻지 않고 만든다. 「검체를 아껴서 생략」하지 않는다.
- 화면을 거쳐야 하는 준비(테스트 데이터 생성 등)는 브라우저 자동화가 연결된 세션에 시킨다. 테스트 실행의 승인 기준은 [승인 경계 8](../01_principles/02_approval-boundary.md).
- API·DB·프로시저·배치는 개발 환경 E2E 도구로 한다. → [E2E 자동화 도구](../06_tools-catalog/01_dev-e2e-automation.md)
- 개발 환경에서 만들 수 없는 유형은 「미확인 — 검체 없음」으로 표에 남기고 보고에 적는다. ✅로 덮지 않는다.
- 접수류 테스트의 입력값(주소 등)은 **원본 데이터와 똑같이** 넣는다. 모르면 추정 값이나 다른 건의 값을 재사용하지 말고 조회해서 채운다.

**Why** 다른 건의 테스트 입력을 재사용했더니 필수 필드가 빠져 후속 컨슈머가 거절했고, 오류가 연달아 났다.

## 4. 실행·판정

- 각 TC 전후로 상태 스냅샷(또는 조회)을 떠서 기대한 컬럼 변화를 확인한다. **응답 코드만으로 ✅하지 않는다.**
- 결과 칸에 무엇을 기준으로 확인했는지 적는다 — `✅(배포본)` / `✅(로컬 수정본)`. 수정이 생기면 배포 후 배포본으로 다시 확인한다.
- 실패하면 **재시도 전에 상태부터** 본다. 반쯤 처리된 상태에서 재시도하면 상황이 더 꼬인다.
- 접수 뒤 승인·송신처럼 이어지는 단계가 있으면 끝 단계의 결과까지 확인한 뒤 보고한다.

### 「통과」라고 말하기 전에

| 확인 | 이유(Why) |
|---|---|
| 테스트가 **수정한 분기를 실제로 탔는가** — 분기 진입 조건(입력 값)을 코드에서 먼저 도출해 검체를 설계한다 | 「실증 통과」를 선언했는데 검체가 다른 분기를 타고 있었다. 세 번 |
| 판정에 **반사실 증거**를 적는다 — 「수정이 없었다면 깨졌을 구성」 | 수정 전에도 통과했을 테스트는 아무것도 증명하지 않는다 |
| 회귀 입력이 문제의 분기에 닿지 못했으면 「통과」가 아니라 **「미검증」 + 한계** | 도달할 수 없는 분기를 전제로 한 결정을 뒤늦게 정정했다 |
| 조작한 검체·더미 값에서 나온 현상은 결함으로 단정하지 않는다. 실제 값·정상 경로로 다시 본다 | 억지로 만든 데이터 탓인 현상을 테스트 케이스로 올렸다 |
| 원인을 판정하기 전에 **내 입력·내 확인 쿼리**부터 의심한다 | 에이전트 자신의 입력 누락·조인 팬아웃이 소스 결함처럼 보인 일이 다섯 번 |
| 상대에게 확인을 요청하기 전에 **내 쪽이 끝까지 흘렀는지** 본다 | 중간 단계에서 멈춘 검체로 확인을 요청할 뻔했다 |
| 루틴을 직접 호출하는 테스트는 **호출부가 하던 선행·후속 작업**을 대신해야 한다 | 직접 호출하면서 뒤이어 불러야 할 정리 루틴을 빼먹어 상태가 꼬였다 |
| 판정 전에 배치의 가동 여부와 처리 시간 창을 확인한다 | 개발 환경의 배치가 꺼져 있거나 창이 달라 결과가 달라진 일이 네 번 |

## 5. 기록·보고

- TC 문서의 결과 칸을 갱신하고 메모(의도된 동작·공통 관행·미확인 사유)를 단다.
- 보고 = 통과/실패/미확인 개수 + 실패·미확인 항목만.
- 일일노트 「실행·실측」에 한 줄.
- 「없다·안 된다」를 보고할 때는 읽은 위치(file:line·쿼리)를 같이 적는다. 확인하지 않았으면 「미확인」.

## 6. 변경 종류별 최소 검증

| 바꾼 것 | 최소 검증 |
|---|---|
| 애플리케이션 코드 | 컴파일 + 관련 단위 테스트 |
| 매퍼·설정 파일 | **로컬 서버 기동 + 해당 API 호출** — 컴파일러는 이 파일을 파싱하지 않는다 |
| DB 프로시저 | 반영 전 점검(파일 ↔ 환경 정의, 시그니처, 참조 객체 권한) + 사본으로 실행해 결과 비교(항상 롤백) |
| 조회 쿼리 | 운영에 넘기기 전 실행계획 점검 → [운영 조회 루프](06_prod-query-loop.md) |
| 배치 | 로컬 실행(개발 환경 DB) + 대상 건 전후 스냅샷 |

**Why** 매퍼 파일에 파싱 오류가 있는 상태로 PR을 올렸다. 컴파일과 단독 SQL 실행은 모두 통과했고, 사용자의 「서버 띄워서 호출해 봤나」로 발견됐다.

## 7. 개발 환경에서 지킬 것

- 개발 DB 쓰기 실험은 **트랜잭션 + 롤백**이 기본이다. 커밋이 필요한 실험은 실행 전에 알린다.
- 로컬 전용 테스트 API·설정은 커밋 대상이 아니다. 저장소의 로컬 제외 목록(`.git/info/exclude`)에 넣어 숨긴다.
- 로컬 서버를 끌 때는 포트를 잡고 있는 프로세스까지 종료한다.
- 개발 환경 결과로 운영 실측을 대신하지 않는다. 개발 환경은 행 수가 작아 실행계획도 운영과 다르다.
- 환경이 초기화(데이터 현행화)되면 검체와 반영해 둔 프로시저가 사라질 수 있다. 검증 전에 반영 상태부터 점검한다.
