# 위임 루프

서브에이전트에 일을 넘기고, 결과를 검증하고, 정리하기까지.

## 1. 언제 위임하는가

| 상황 | 처리 | 이유(Why) |
|---|---|---|
| 1~2파일 소규모 수정 | 메인이 직접 고치고 검증 명령 1회(`git diff --stat` + 컴파일) | 열 줄 변경에 위임 왕복이 수 분 걸렸다 |
| 다중 파일·대형 구현 | 구현 담당 에이전트에 위임 | 메인 컨텍스트를 보호하고 구현과 검증을 분리한다 |
| 영향도 분석·설계 판단·원인 추적·레거시 흐름 분석 | 설계 검토 역할 에이전트에 위임(추론 강도 높게) 또는 단계적 검토 | 메인의 즉답은 깊이가 부족했다 |
| 큰 출력이 나오는 조사·여러 파일 읽기 | 위임하고 결론만 받는다 | 파일 덤프가 메인 컨텍스트를 채운다 |
| 독립 검토(만든 것을 다른 눈으로) | 검증 역할 에이전트에 **자료만** 주고 결론은 주지 않는다 | 가설을 넘겨받은 에이전트는 그 가설을 확인해 돌려준다 |

모델 배분
- 조회는 가벼운 모델, 표준 작업은 중간 모델, 복잡한 설계·레거시 분석은 상위 모델에 맡긴다.
- 설계·판단 위임에는 에이전트 종류와 무관하게 추론 강도를 높게 지정한다.
- 가장 비싼 모델은 사용자가 명시할 때만 쓴다. 제안할 때는 예상 토큰을 함께 적고, 다른 모델의 결과를 그 모델로 자동 재평가하지 않는다.
- 평가·재평가가 필요해 보이면 먼저 메인이 정답 사례·재현율로 검증한다. 구현자의 자체 검증과 메인의 독립 검증으로 충분하면 재평가를 덧붙이지 않는다.

**Why** 하루에 최상위 모델 위임을 세 건 띄우고 재평가까지 그 모델로 걸었다가 사용자가 중단시켰다.

## 2. 위임 프롬프트에 반드시 넣는 것

위임받은 에이전트는 메인의 대화도 메모리도 보지 못한다. 프롬프트가 유일한 맥락이다.

- 목표와 이미 배제한 것
- 대상 파일 경로, 정확한 변경 내용(「무엇을 어느 파일 어디에 어떻게」)
- 금지: 파일 헤더 이력 추가, git 커밋·푸시, 범위 밖 파일 수정
- 검증 명령과 통과 기준(컴파일 종료 코드 0. 설정·매퍼 파일을 바꿨으면 서버 기동 + 해당 API 호출까지)
- 필요한 도메인 함정(직접 적거나 rules 파일을 읽게 한다)
- 코드 스타일 조건(프로젝트 관례, 식별자 약어 기준 등)과 「완료 보고에 사용한 약어 목록」 같은 확인용 산출
- 산출물 경로와 완료 보고 형식
- 다른 에이전트가 쓰고 있는 작업 폴더 목록(동시 수정 금지)

템플릿: [`templates/delegation-prompt.md`](../templates/delegation-prompt.md)

## 3. 위임 시점에 기록한다

위임하는 그 시점에 일일노트 「실행·실측」에 한 줄 남긴다 — 과제, 작업 폴더(worktree), 담당, 산출물 경로.

**Why** 프롬프트에만 두면 다음 세션이 그 작업을 찾지 못한다.

## 4. 완료 보고를 받으면

1. **메인이 독립 검증한다.** `git diff --stat` + 검색 + 컴파일을 명령 한 번으로 돌린다. 에이전트의 「통과했다」는 보고를 그대로 옮기지 않는다.
2. **지적·결론을 재검증한다.** 리뷰 지적, 「영향 없음」, 「수단 없음」 같은 결론은 해당 위치를 열어 확인하고 ✅확인 / ⚠오탐 / 미검증을 붙인다.
3. **사용자에게 보고한다.** 한 일, 검증 결과, 미확인으로 남은 것.
4. **에이전트를 정리한다.** 검증이 끝난 에이전트는 바로 종료 요청으로 정리한다.

**Why**
- 리뷰 에이전트의 지적 절반이 재검증에서 오탐이었다. 재검증 없이 전달했으면 불필요한 수정이 나갔을 것이다.
- 위임 결과의 「그 상태로 만들 수단이 없다」를 그대로 전달했는데 실제로는 가능했다.
- 유휴 에이전트를 여럿 방치해 사용자가 직접 정리하라고 지시했다.

## 5. 위임하지 말아야 하는 형태

| 형태 | 대신 |
|---|---|
| 「주석을 자연스럽게 다듬어 줘」 같은 자유 재작성 | 치환 문구를 메인이 확정해 넘기고, 로직·필드 무변경을 검증 항목(diff에 코드 줄 0)으로 못 박는다 |
| 내 결론을 붙인 검토 요청(「충분해 보이는데 확인해 줘」) | 자료와 질문만 준다 |
| 사용자에게 받을 값이 빠진 구현 위임 | 값을 먼저 받는다(한 번에 묶어 묻기) |
| 실행 중인 위임을 묻지 않고 중단·재시작 | 그대로 두는 선택지를 포함해 먼저 묻는다 |

## 6. 작업 방식의 변천

| 단계 | 규칙 | 결과 |
|---|---|---|
| 1 | 코드 수정은 한 줄이라도 위임 | 구현·검증 분리는 됐지만 작은 변경도 왕복이 길었다. 에이전트 호출이 사용자 메시지 100개당 약 12회까지 올랐다 |
| 2 | 크기별 차등(소규모는 메인 직접) | 에이전트 호출이 약 4회로 줄었다. 측정에서 확인된 유일한 개편 효과였다 |
| 3 | 로컬 수정은 승인 없이, 검증은 사후 | 사용자 부재 중에도 작업이 이어진다 |

## 7. 다른 종류의 에이전트에 위임할 때

두 번째 에이전트(예: 다른 회사의 코딩 에이전트)에 넘길 때는 [협업 규칙](../07_multi-agent/01_collaboration-rules.md)을 따른다. 핵심만 적으면:

- 독립적으로 답할 수 있는 질문·산출물 단위로 나눈다.
- 요청에 과제 ID·대상 자료·산출물·완료 기준·통합 담당을 적는다. 코드 작업이면 작업 폴더·브랜치·기준 커밋도 적는다.
- 같은 파일·같은 작업 폴더를 동시에 고치지 않는다.
- 사용자가 묻기 전에, 작업 묶음을 시작할 때 「병렬로 넘길 독립 작업이 있는가」를 먼저 본다. 사용자의 요청이 겹칠 때도 같다. → [겹치는 요청 나누기](11_approval-batching-and-request-triage.md)
