# 주간 개선 루프

작업 방식과 자작 도구를 한 번 만들고 끝내지 않는다. **신호 수집 → 우리 작업에 맞는 것만 고르기 → 적용 → 효과 추적**을 주기적으로 돌린다.

## 흐름

```
금요일 오후(자동)            월요일 오전(자동)           그 주 첫 근무일(사람과 함께)
┌──────────────────┐     ┌──────────────────┐     ┌────────────────────────────┐
│ 주간 세션 회고      │     │ 주간 트렌드 조사     │     │ 주간 개선 점검               │
│ 주간 팀 문서 후보   │ ──▶ │ (격주) 실패 사례 수집 │ ──▶ │ ① 외부 ② 내 방식 ③ 후보 1~3건 │
└──────────────────┘     └──────────────────┘     │ ④ 팀 문서 ⑤ 도구 주간 패치    │
   로컬 예약 작업              클라우드 루틴            └────────────────────────────┘
```

자동 부분은 [예약 루틴](10_scheduled-routines.md)에, 사람과 함께 하는 부분은 [`daily-standup`](../04_skills/daily-standup/SKILL.md) 스킬의 「주간 개선 점검」 절에 들어 있다.

## 입력 신호

| 신호 | 어디서 | 무엇을 본다 |
|---|---|---|
| 사용자 정정 | 정정 로그(`corrections.jsonl`, 입력 훅이 기록) + 세션 기록 | 직전 행동을 뒤집는 지적이 같은 유형으로 반복되는가 |
| 가드·권한 차단 | 세션 기록의 훅 거부·권한 거절 | 같은 명령을 재시도하는가, 차단이 과한가 |
| 되돌림 | 직후 원복한 편집, 철회한 결론 | 확대 해석·성급한 결론 |
| 비효율 | 같은 파일 반복 읽기, 실패 후 같은 호출 재실행, 쓸모없는 위임 | 도구·스크립트로 줄일 수 있는가 |
| 외부 변화 | 에이전트 도구의 릴리스 노트, 설치한 플러그인의 새 버전, 트렌드 조사 | 우리 훅·권한·스킬이 영향받는가, 새 기능이 지금의 불편을 덜어 주는가 |
| 도구 보정 후보 | 도구 사용 중 적어 둔 「과하게 막힌 사례」 | 가드를 어디까지 풀어도 안전한가 |
| 규칙의 사용 흔적 | 지난 4주의 세션 기록·정정 로그·일일노트 | 4주 넘게 쓰이지 않은 규칙, 서로 겹치는 규칙 → **지울 후보** |

## 판정 기준

1. **같은 유형이 2회 이상**(세션이 달라도) 나온 것만 후보다. 1회성은 버린다.
2. 이미 규칙이 있는데 또 어긴 것은 **「규칙은 있는데 안 지켜짐」**으로 따로 표시한다. 문구를 더하지 않고 강제 수단을 검토한다 — 훅·스크립트 차단 > 스킬 절차 단계 > 규칙 문구.
3. 외부 트렌드는 **그대로 옮기지 않는다.** 반복 실수나 실제 병목에 닿는 것만 고른다.
4. 새 기능은 「영향 있음」(우리 설정의 동작이 바뀜)과 「써 볼 만함」(지금 불편을 덜어 줌) 둘로만 분류하고 나머지는 버린다. 날짜가 확인된 항목만 쓴다.

**Why** 사용자가 먼저 요청해야 했던 새 기능이 있었다. 에이전트가 릴리스 노트를 우리 설정과 대조하고 있었다면 먼저 제안할 수 있었다.

## 그 주 첫 근무일의 점검

업무 보고 목록을 낸 뒤 이어서 한다.

| 단계 | 내용 |
|---|---|
| ① 외부 | 트렌드 루틴의 그 주 결과 + 설치 플러그인 버전 대조 + 에이전트 도구 신기능 대조 |
| ② 내 방식 | 가장 최근 주간 회고 파일 + 지난주 일일노트·피드백 메모리 변경·같은 지적의 반복 |
| ③ 출력 | 「이번 주 적용 후보」 1~3건 — 각각 무엇 / 왜(①·② 근거) / **바꿀 곳(설정·훅·스킬·규칙 파일 경로)** / 첫 손 / 규모 |
| ④ 팀 문서 | 가장 최근 팀 문서 후보 표를 보여 주고 반영할 것을 묻는다. 고른 것만 초안을 다듬어 브랜치·1커밋·PR |
| ⑤ 도구 주간 패치 | 도구 메모리의 보정 후보를 모아 보여 주고 한 주 치를 한 번에 패치할지 묻는다 |

승인된 후보는 그 자리에서 진행한다. 채택·기각 결과는 그날 일일노트에 한 줄 남긴다.

### 규칙 감량 후보도 같이 올린다

주간 회고가 「4주 넘게 쓰이지 않은 규칙」과 「서로 겹치는 규칙」을 지울 후보로 올리면, 점검 자리에서 보여 주고 고른 것만 합치거나 지운다. 규칙이 늘어나는 비용의 관리는 에이전트의 책임이다. → [메모리 정리 루틴 8](../03_memory-system/02_maintenance.md)

(위 ①~⑤는 실제로 돌려 온 절차이고, 이 항목은 플레이북을 정리하던 날 정했다. 아직 한 주도 돌려 보지 않았다.)

## 도입한 것은 지표와 판정일을 같이 정한다

| 도입한 것 | 지표 | 판정 |
|---|---|---|
| 정적 참조 조회 도구 | 주간 사용 횟수(사용 로그) | 주 N회 미만이면 다음 단계(확장)로 가지 않는다 |
| 입력 훅(모드) | 붙은 날 대비 지켜진 날, 주입 횟수, 정정 감소 | 2주 뒤 유지·조정·제거 |
| 규칙 개편 | 사용자 메시지 100개당 질문·에이전트 호출·정정 | 표본이 충분히 쌓인 뒤 같은 모델·같은 진입점으로 재측정 |

**규칙** 효과가 없으면 줄이거나 뺀다. 늘리기만 하지 않는다.

**Why** 도구에 쓰는 시간이 업무를 앞지르는 시점이 왔다. 한 도구는 감사 로그의 대부분이 도구 자체의 개발·시험 호출이었다. 그 뒤 「새로 만들기보다 쓰고·측정하고·줄이는」 기간을 따로 두었고, 이어서 방침을 확정했다 — **도구는 더 만들지 않는다. 있는 것을 보고 고치기만 한다.**

## 도구 보정은 주 1회 묶음으로

- 사용 중 「과하게 막혔다」 싶은 사례는 그때그때 메모리에 「보정 후보」로 적는다(막힌 호출 형태, 근거, 바꿀 곳).
- 로컬에서 바로 고칠 수는 있지만(원본 작업 폴더 + 테스트), 설치본 반영과 PR은 주 1회 묶어서 한다.
- 패치 뒤에는 **실사용 재생 회귀**(감사 로그에 남은 과거 성공 호출을 다시 판정)를 먼저 돌린다.
- **실행 중인 폴더를 직접 고치지 않는다.** 원본 작업 폴더에서 고치고 검토 뒤 동기화한다.

**Why** 도구가 실행되는 폴더를 한 에이전트가 직접 고치는 동안 다른 에이전트도 같은 폴더를 고쳐 충돌했다.

## 한 달에 한 번 — 효과 측정

`session_metrics.py`로 개편 전후를 비교한다. 읽는 법은 [규칙에 대한 규칙 9](../01_principles/05_rules-about-rules.md).

실제 측정에서 배운 것
- 「질문이 절반으로 줄었다」는 2주 창의 착시였다. 전체 기간으로는 줄지 않았다.
- 모든 고정 조건에서 줄어든 것은 에이전트 호출뿐이었다(「한 줄이라도 위임」 규칙을 되돌린 효과).
- 정정 발화 감소는 개편 전부터 이어진 추세·모델 교체와 분리되지 않았다.
- 과제당 세션·메시지 수는 개선 근거가 없었다. 과제의 성격이 달라졌기 때문이다.

정직한 결론을 남기는 것 자체가 다음 개편의 기준선이 된다.
