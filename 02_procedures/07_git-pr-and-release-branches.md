# Git·PR·배포 브랜치 운영

## 1. 커밋·푸시

| 규칙 | 이유(Why) |
|---|---|
| 커밋·푸시는 사용자가 명시적으로 요청할 때만. 커밋 전 diff 요약을 보여 주고 승인받는다 | 밖으로 나가는 상태 변경이다 |
| 전체 스테이징(`git add .`·`-A`·`-u`·`commit -a`) 금지. 파일을 명시한다 | 한 클론에 여러 과제의 미커밋 변경이 겹쳐 있을 때 한 번의 실수로 무관한 과제가 한 커밋에 섞인다 |
| 커밋·PR에 생성 도구 서명·공동 작성자 줄을 붙이지 않는다 | 사용자의 명시적 거부. 하네스 기본 지시보다 우선하고, 설정으로도 끈다 |
| 브랜치명·커밋 메시지·PR 형식은 팀 규칙 파일 하나를 정본으로 둔다 | 형식 규칙이 여러 곳에 있으면 서로 어긋난다 |
| 브랜치 번호는 사용자가 알려 주지 않으면 임의로 만들지 않는다 | 번호는 외부 대장에서 채번한다 |

이 규칙들은 권한 설정과 실행 전 훅으로도 강제한다. → `guard.mjs`

## 2. 브랜치 기준과 PR 타깃

**규칙** 작업 브랜치는 **통합 브랜치에서 따고 통합 브랜치로** PR한다. 운영 브랜치는 통합 브랜치가 올라가는 상위 단계다. 저장소의 기본 HEAD가 어디를 가리키는지는 팀의 브랜치 전략과 무관하다.

**Why** 저장소 기본 HEAD가 운영 브랜치를 가리킨다는 이유로 운영 브랜치를 base로 잡아 PR을 올렸다. 실제로 통합 브랜치는 운영 브랜치보다 수십 커밋 앞서 있었다. PR 타깃은 나중에 도구로 못 바꾸는 경우가 있으니 **만들기 전에** 확인한다.

### 레포별 운영 배포 브랜치 표

**규칙** 운영용 PR의 타깃은 레포별 표로 정한다. 표에 없는 레포는 PR을 만들기 전에 사용자에게 확인한다.

| 레포 | 운영 배포 브랜치 | 비고 |
|---|---|---|
| `<repo-a>`·`<repo-b>` | `release` | 배포 파이프라인이 이 브랜치를 본다 |
| `<repo-c>`·`<repo-d>` | `main` | release 브랜치가 있어도 쓰지 않는다(최근 머지 날짜로 확인) |
| 그 밖 | **PR 전 확인** | |

**Why** 「운영용은 main으로」라는 규칙대로 올려 머지했는데 그 레포의 배포 브랜치는 release였다. 머지는 됐지만 운영에는 반영되지 않았고, 올바른 브랜치로 다시 올려야 했다.

### 통합 브랜치에 아직 나가면 안 되는 변경이 섞여 있을 때

**규칙** 수정할 파일이 통합 브랜치에서 「운영 반영 불가」 변경과 섞여 있으면, 브랜치를 **운영 브랜치에서 따고 운영 브랜치로** 따로 올린다. 통합 브랜치 반영은 별도로 한다. 브랜치를 따기 전에 「그 파일이 통합 브랜치에서 섞였는지」부터 확인한다.

**Why** 문제는 머지 충돌이 아니라 반영 범위다. 통합 브랜치를 경유하면 승격 때 미공개 기능이 함께 나간다.

## 3. 배포 직전 운영 정의 재비교

**규칙** 배포가 git과 분리된 대상(예: 담당자가 수동으로 반영하는 DB 프로시저)을 고칠 때는, 반영 전에 **운영의 실제 정의와 레포 파일을 대조**한다. 어긋나면 운영 본문으로 레포의 운영 브랜치부터 맞춘 뒤 그 위에서 수정한다. 반영 후에도 다시 대조해 같은지 확인한다.

**Why** 같은 유형이 두 번 있었다.
- 레포의 운영 브랜치가 운영 DB보다 뒤처져 있었다. 운영에만 있던 핫픽스가 레포에 없어서, 레포 기준으로 고친 본문을 그대로 반영했으면 핫픽스를 덮어쓸 뻔했다.
- 운영에는 이미 반영됐지만 공유 브랜치에는 없고 다른 사람의 feature 브랜치에만 있던 변경이, 이번 배포로 덮여 되돌아갈 뻔했다. 두 번째 에이전트의 독립 검토가 찾아냈다.

그래서 **배포 직전에 최종본을 운영 정의와 한 번 더 대조하는 단계**를 넣었다. 운영에 먼저 반영한 변경은 머지까지 마무리하도록 작성자에게 요청한다. 장기 feature 브랜치를 반영할 때는 대상 파일을 기준 브랜치와 비교해, 그사이 다른 과제가 같은 파일을 고치지 않았는지 본다.

### 형상관리에 없는 객체를 고칠 때

**규칙** 레포에 없는 운영 객체를 수정할 때는 ① 운영 정의 그대로 「초기 등록」 커밋을 통합 브랜치에 먼저 올리고 ② 수정은 그 위에 feature 브랜치로 커밋해 PR에는 수정 커밋만 들어가게 한다.

**Why** 원본 등록과 수정을 한 PR에 담았더니 리뷰어가 원본 수백 줄을 리뷰 대상으로 보게 됐다.

## 4. 새 과제를 시작할 때 — 브랜치 전환이 기본, worktree는 예외

**규칙** 수정 전에 메인 워킹트리의 `git status --short`를 본다.
- 깨끗하면 → 메인에서 브랜치를 만들어 전환한다.
- 다른 과제의 미커밋 변경이 있으면 → 그때만 통합 브랜치 기준 worktree를 만든다.

메인 워킹트리의 unstaged 변경은 「지금 개발 중이며 다음에 커밋할 대상」만 남긴다. 작업 끝에 unstaged 0을 확인하고 보고한다.

**Why 두 방향 모두**
- 진행 중인 다른 과제의 워킹트리에 새 과제 수정을 섞으면, 반영 일정이 달라 커밋을 미루는 사이 여러 과제 변경이 한 클론(심지어 같은 파일)에 겹친다.
- 반대로 메인이 깨끗한데도 기계적으로 worktree를 만들면, 사용자가 쓰는 Git 클라이언트의 기존 탭에서 변경이 보이지 않는다.

훅이 `git worktree add`를 감지해 메인이 깨끗하면 확인 창을 띄운다.

## 5. PR 만들기

| 규칙 | 이유(Why) |
|---|---|
| 리뷰어는 생성할 때 함께 넣는다. **레포마다 기본 리뷰어를 조회**하고(페이지네이션 끝까지), 본인만 뺀다 | 다른 레포의 명단을 복사했다가 리뷰어를 빠뜨렸고, 첫 페이지만 보고 마지막 한 명을 놓쳤다 |
| 빠뜨렸으면 REST 호출로 추가한다. PR을 닫고 다시 만들지 않는다 | PR 상태·커밋·설명이 그대로 유지된다 |
| PR 작업은 MCP 대신 REST 스크립트로(응답 한 줄) | PR 조회 MCP 응답이 호출당 수만 자였고, 한 달 도구 출력의 최대 원천이었다 |
| 제목·설명에는 내 작업만 담백하게. 체리픽·타인 작업 제외 같은 브랜치 운영 사정은 넣지 않는다 | 리뷰어에게 필요한 것은 이 변경이 무엇인지다 |
| 목록 앞에 빈 줄, 중첩 불릿 금지, 절 구분은 제목 문법으로. **올린 뒤 렌더링을 확인**한다 | 호스팅 서비스의 마크다운 렌더러가 목록을 한 문단으로 뭉갰다 |
| 제목의 특수문자를 HTML 이스케이프하지 않는다 | 이스케이프 문자열이 화면에 그대로 보였다 |
| 올라간 PR의 제목·설명 수정은 before/after를 보여 주고 승인받는다. 정정은 모아서 한 번 | 고칠 때마다 리뷰어에게 알림이 간다 |
| PR을 올린 뒤의 후속 수정은 작업 트리에 모았다가 **마지막에 커밋 1개**로 푸시한다 | 수정·재평가 회차마다 커밋해 알림과 커밋 노이즈를 만들었다 |
| 문서 PR은 업무 단위 1커밋 | 머지 커밋 방식이면 이력에 그대로 남는다 |
| 병합은 매번 사용자 승인 | 되돌리기 어렵다. 훅이 확인 창을 띄운다 |
| 같은 변경을 두 브랜치용 PR로 올렸으면 머지 때 **소스 브랜치를 지우지 않는다** | 한쪽을 머지하며 소스 브랜치를 지워 형제 PR이 깨졌다 |
| 푸시하기 전에 **PR이 아직 열려 있는지** 확인한다 | 이미 머지된 PR의 브랜치에 강제 푸시해 옛 브랜치가 되살아났다. 보완분은 새 브랜치·새 PR로 |
| 브랜치 간 「있다/없다」는 커밋 해시가 아니라 **파일 내용**으로 대조한다 | 같은 변경이 다른 해시로 이미 있었는데 「누락」이라고 설명했다 |

스크립트: `pr_cli.py`

## 6. 티켓 상태의 기준은 사용자가 정한다

**규칙** 티켓 대장의 「완료」가 무엇을 뜻하는지(PR 완료인지 운영 반영인지)는 사용자가 정한 기준을 따른다. 도구의 안내문이 다른 기준을 말해도 사용자 기준이 우선이다. PR 보고 끝에 완료 전환을 묻지 않는다.

**Why** 도구 안내문대로 「PR을 만들었으니 완료로 바꿀까요」를 반복해 물었는데, 사용자의 기준은 「운영에 나가면 완료」였다.

- 티켓 제목·설명은 각각 한 줄로 짧게 먼저 제시한다(제목은 일반화된 한 구절, 설명은 구체 대상 한 줄). 원인·수치·파일명은 PR과 문서의 몫이다.
- 대장의 비고가 변경 이력으로 길어지지 않게, 바꿀 값은 한 번의 호출로 묶는다.

## 7. 문서 레포도 브랜치 + PR

팀 공유 문서 레포도 기본 브랜치 직접 커밋 금지다. 실수로 기본 브랜치에 커밋했으면 새 브랜치로 옮기고 기본 브랜치를 원격 상태로 되돌린다. 노트 앱이 프론트매터를 정규화해 diff에 잡음이 섞이니 커밋 전 diff를 눈으로 본다.

## 8. 워킹트리가 「변경 100여 개」로 보일 때

판정: `git diff --name-only | wc -l`이 status 건수와 크게 다르면 가짜다. 파일의 HEAD 해시·인덱스 해시·워킹 파일 해시가 같으면 확정.

원인: 인덱스의 stat 캐시가 줄 끝 문자 변환 전 크기를 갖고 있는데 워킹 파일은 다른 줄 끝으로 다시 쓰였다(다른 도구가 파일을 저장하면서).

처치: 스테이징이 0건인지 확인한 뒤 인덱스를 HEAD 기준으로 다시 세운다(`rm .git/index && git reset`). 줄 끝 변환 설정 자체는 바꾸지 않는다 — 반대 방향으로 전부 변경으로 뜬다.

## 9. 월초 브랜치 정리

그달 첫 근무일에 읽기 전용 스크립트로 정리 후보(내 작업이면서 운영 브랜치에 머지됐거나, 원격이 삭제되고 고유 커밋이 없는 브랜치·worktree)만 뽑아 보여 주고 지울 것을 묻는다. 활성 과제의 티켓·미커밋 worktree·커밋 0개 브랜치는 제외한다. 강제 삭제·원격 삭제는 하지 않는다.

스크립트: `branch_tidy.py`
