# 분석·영향도 절차

「없다」「영향 없다」「이게 원인이다」를 말하기 전에 거치는 절차.

## 1. 이슈로 올리기 전 — 이미 결정된 것인지 찾는다

1. 과제 메모리 최상단 **「확정 정책·결정 표」**를 본다.
2. 핵심어 2~3개(동의어·코드값 포함)로 메모리와 일일노트를 검색한다. **건수를 먼저 보고**, 출력을 앞부분만 자르지 않는다.
3. 주제 폴더의 목차 문서를 본다.
4. 그래도 없으면 미결로 올린다. 사용자가 정책을 말해 주면 그 자리에서 결정 표에 올린다.

**Why** 이미 확정된 정책이 과제 메모리 세 군데에 적혀 있었는데, 대안어 열네 개로 검색한 결과를 앞 60줄만 봐서 놓쳤다.

## 2. 「누가 만들고 누가 읽는가」

| 질문 | 볼 경로 |
|---|---|
| 이 테이블에 행을 누가 만드나 | ① SQL `INSERT`(프로시저·매퍼) ② 엔티티 클래스명 + `save`/`saveAll`/`persist`(ORM) ③ 메시지 컨슈머·배치 서비스 |
| 이 루틴을 누가 부르나 | ① 다른 루틴의 호출문 ② 매퍼의 호출 문장 ③ 애플리케이션의 프로시저 호출 API ④ 배치 스케줄(레포 밖일 수 있다) |
| 이 테이블을 누가 읽나 | ① SQL `FROM`/`JOIN` ② 엔티티를 쓰는 조회 메서드(ORM 쿼리 언어는 테이블명이 아니라 엔티티명으로 적힌다) |

- 정적 참조 조회 도구가 있으면 먼저 돌린다. 결과는 출발 목록일 뿐이고, 판단은 위치를 열어 읽은 뒤에 한다. → [레포 횡단 참조 도구](../06_tools-catalog/02_repo-xref.md)
- 프로시저를 정본으로 지목하기 전에 호출부가 실재하는지 확인한다. 이관 중인 시스템에는 안 쓰이는 레거시가 파일로 남아 있다.
- 통합 브랜치와 운영 브랜치를 **둘 다** 본다. 통합 브랜치에서 바뀐 호출부가 운영에는 살아 있을 수 있다.
- 컬럼이 실제로 있는지는 엔티티 클래스나 DB 카탈로그로 확인한다. 「사용처 0건」을 「컬럼 없음」으로 읽지 않는다.

## 3. 영향도 분석 — 전수로

데이터 형태를 바꾸는 설계(새 형태의 행을 남긴다, 코드값을 추가한다, 컬럼 의미를 바꾼다)는 다음 순서로 한다.

1. **검색 키를 정한다.** 테이블명, 구분 조건, 코드 enum, 사유 코드.
2. **레포별 전수 목록을 만든다.** 프로시저·배치·컨슈머·API·화면.
3. **영역별로 나눠 열어 읽는다.** 필요하면 영역별로 상위 모델 에이전트에 병렬 위임한다(추론 강도 높게).
4. **「나중에 그 데이터를 다시 읽는」 경로를 따로 본다.** 취소·되돌리기·정산·집계·증빙·감시처럼 뒤 단계에서 그 데이터를 다시 읽는 곳.
5. **판정마다 근거를 단다.** 「영향 없음」도 file:line. 못 읽은 것은 「미확인」.
6. **사용자의 기존 PR·보류 브랜치와 대조한다.**

**Why** 전제 두 개에서 연역해 영향 범위를 보고했다가, 전체 취소 경로의 이중 처리를 빠뜨렸다. 사용자가 관련 PR을 짚어 준 뒤에야 알았다.

## 4. 원인 추적

- 가설을 세우면 반증을 같이 찾는다. 가설 하나에 맞는 증거만 모으지 않는다.
- 무거운 집계로 답을 찾기 전에 **단건 조회로 끝나는 문제인지** 먼저 본다. 판정은 대개 대표 건 한 행이면 결론이 난다.
- 사용자가 데이터로 확인해 가는 중이면 데이터에 찍힌 사실만 말한다. 원인 추정을 결론처럼 섞지 않는다.
- 전환 시점 같은 문제는 넓은 기간 집계 대신 좁은 날짜 창 몇 개를 표본으로 비교한다.

### 집계 결과를 읽을 때의 함정

| 함정 | 대응 |
|---|---|
| 상위 단위 조건으로 하위 단위를 센다 | 판정 단위로 다시 센다. 다대다 조인으로 건수가 부풀지 않았는지 본다 |
| 자동 재처리·시스템 계정의 행위가 섞인다 | 행위자 축(사람/시스템)을 건다 |
| 완료되지 않은 건이 모집단에 섞여 비율이 부푼다 | 완료 상태 축을 건다. 결과를 「정상 제외분 → 이탈분 → 진짜 구멍」으로 분해해 보고한다 |
| 여러 주체가 같이 쓰는 테이블에서 「우리 것만 고르는 조건」을 빠뜨린다 | 식별 조건을 쿼리 전에 적는다 |
| else 버킷이 공란 값 집단을 다른 범주에 섞는다 | 명시적으로 분류한다 |
| 좁은 창만 보고 「그날만」이라고 쓴다 | 지속/일시는 첫 기록부터 본다. 좁은 창의 결론은 「창 한정」으로 표기한다 |
| 0행 | 모수 설계부터 의심한다(운영에 실재하는 집단인가) |
| 데이터에 찍힌 값을 액면 그대로 믿는다 | 분포가 이상하게 평평하거나 꺾이면 현장 사정을 먼저 묻는다 |
| 시간적 일치를 인과로 읽는다 | 「인과 미확인」으로 적는다 |

### 근거 줄에 붙이는 것

- **등급** — 열어 읽음 / 검색만 / 미열람 / 위임 판정·미재검 / 추정
- **기준** — 어느 브랜치(원격 최신 기준으로 읽는다), 어느 환경, 어느 창(기간)
- **범위** — 검색한 레포 목록. 그 밖은 「미확인」

**Why** 로컬 브랜치가 원격보다 뒤처진 상태로 읽어 낡은 코드를 근거로 댔다. 검색이 닿지 않는 외부 호출처를 「없음」으로 적을 뻔했다.

## 5. 명세·문서 파일을 읽을 때

- 스프레드시트를 내부 XML로 덤프해 읽으면 병합 셀이 아래 행에서 사라진다. 병합 범위를 먼저 파싱해 앵커 값을 채우고, 셀 주소 기준으로 열을 맞춘다.
- 그래도 이상해 보이면 **결함으로 보고하기 전에 사용자에게 먼저 묻는다.** 원본을 볼 수 있는 것은 사용자다.

**Why** 병합 셀을 놓쳐 「필드 이름 누락」을 두 번 이상 결함으로 보고했다. 사용자가 이미 설명한 사안이었다.

- 디자인 도구에서 내보낸 PDF는 글꼴 형식 때문에 텍스트가 깨져 보일 수 있다. 추출 라이브러리를 바꿔 한 번만 텍스트로 뽑아 저장해 두고, 배치·연결선은 이미지 렌더링으로 따로 본다. 가능하면 원본 열람 권한이나 텍스트가 보존되는 형식을 요청한다.

## 6. 무거운 추론의 깊이

착수 전에 「이 일은 추론이 무거운가」를 먼저 판정한다. 영향도·설계·디버깅·레거시 분석이면 무겁다.

| 선택 | 방법 |
|---|---|
| 위임 | 설계 검토 역할 에이전트(읽기 전용)에 맡긴다. 판단이 갈리는 사안은 두 관점을 교차시켜 종합한다 |
| 메인 직접 | 가설 ↔ 반증의 단계적 검토를 거친 뒤 결론을 낸다 |
| 다른 종류의 모델 | 같은 질문과 원문을 주고 독립 검토를 받는다. 지적마다 메인이 원문·코드 분기를 다시 읽어 확인·오탐·미검증으로 보고한다 |
