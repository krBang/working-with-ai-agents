# 승인 호출 묶기와 겹치는 요청 나누기

사용자의 주의를 아끼는 두 가지 절차다. 승인 창을 없애는 것이 아니라 **에이전트가 부르는 횟수를 줄이고**, 요청이 겹칠 때 **사용자가 세션을 나누지 않게** 한다.

> 이 문서의 두 절차는 플레이북을 정리하던 날 사용자와 「아쉬운 점 → 개선」으로 정한 것이다. 규칙으로 굳힌 지 얼마 안 돼 운영 실적이 없다. 돌려 본 뒤 고칠 것을 전제로 읽는다.

## 1. 의도한 승인은 줄이지 않는다 — 호출 횟수를 줄인다

**전제** 사용자는 기본적으로 자동 승인 모드로 일한다. 그런데도 뜨는 승인 창은 전부 가드가 **의도적으로** 남긴 것이다 — 커밋·푸시·PR·병합. 이 창을 없애거나 「다시 묻지 않기」로 바꾸는 것은 답이 아니다(→ [승인 경계 6](../01_principles/02_approval-boundary.md)).

**규칙** 승인 창이 많다고 느껴지면 가드를 풀지 않고 에이전트가 호출을 줄인다.

| 방법 | 예 | 이유(Why) |
|---|---|---|
| **여러 단계로 이어지는 외부 행위는 처음에 전체 단계를 보여 주고 한 번에 결정받는다** | (예) 「① 푸시 → ② PR 생성 → ③ 대장 갱신」을 먼저 보여 주고 어디까지 할지 한 번에 묻는다 | 단계마다 따로 물으면 사용자는 전체 그림 없이 조각을 승인하게 된다 |
| **같은 대상의 수정은 한 호출로 모은다** | 대장의 상태·기한·비고를 따로따로 고치지 않는다 | 수정할 때마다 승인이 따로 뜨고 변경 이력도 따로 붙었다(→ [티켓 도구](../06_tools-catalog/03_ticket-automation.md)) |

묶을 때 지킬 것
- 한 번에 결정받은 단계 중 하나가 실패하면 멈추고 보고한다. 나머지를 계속 밀지 않는다.
- 승인의 범위는 보여 준 단계까지다. 보여 주지 않은 단계를 덧붙이지 않는다(→ [승인 경계 4](../01_principles/02_approval-boundary.md)).

## 2. 겹치는 요청은 한 세션에서 세 갈래로 나눈다

**규칙** 사용자가 일을 시켜 둔 도중에 다른 요청을 던져도 세션을 따로 띄우게 하지 않는다. 한 세션에 계속 던지게 하고, 에이전트가 요청을 나눈다.

| 갈래 | 어떤 요청 | 처리 |
|---|---|---|
| ① 위임 | 하던 일과 **독립적인** 작업(조사·문서 등) | 백그라운드 에이전트나 [보조 에이전트](../07_multi-agent/01_collaboration-rules.md)에 넘기고 하던 일을 계속한다 |
| ② 끼워 넣기 | **승인이나 판단이 필요한 짧은 일** | 하던 작업의 현재 단계만 끝내고 바로 처리한다 |
| ③ 대기 | 하던 일과 **얽힌** 일 | 대기 목록에 올린다 |

**대기가 2건 이상이면** 답변 맨 위에 한 줄을 둔다.

```
대기: ① <요청 A> ② <요청 B>
```

- 대기가 1건 이하로 줄면 줄을 없앤다.
- 「사용자 할 일」 블록도 답변 맨 위에 온다([보고 형식 1](../08_communication/01_reporting-format.md)). 둘이 겹칠 때의 순서는 따로 정하지 않았다.
- 위임한 것은 위임 시점에 일일노트에 한 줄 남긴다(과제·작업 폴더·산출물 경로).

**Why** 사용자가 물었다 — 「요청이 여러 개면 어떻게 해결하나, 내가 그냥 세션을 여러 개 띄우나」.

### 왜 세션을 나누지 않나

| 이유 | 설명 |
|---|---|
| 세션마다 맥락이 따로다 | 새 세션에는 방금 한 논의를 다시 설명해야 한다 |
| 메모리를 동시에 쓰면 꼬인다 | 두 세션이 같은 메모리 파일을 각자 고친다 |
| 같은 작업 폴더를 동시에 고치면 충돌한다 | 두 에이전트 사이에서는 실제로 겪었다(→ [실패 사례 1](../07_multi-agent/04_failure-cases.md)) |

### 세션을 나눠도 되는 경우

**계정이나 환경이 다를 때뿐이다.**

- 다른 계정에 묶인 작업(개인 저장소 등)
- 브라우저 자동화가 연결된 세션에서만 할 수 있는 화면 E2E
