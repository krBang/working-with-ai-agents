# 운영 조회 루프

운영 DB에서 사실을 확인해야 할 때의 절차. 여기서의 실수는 「느려진다」가 아니라 **세션이 잡혀 취소가 안 먹는다**로 끝난다.

## 왜 이렇게까지 하나

에이전트가 무거운 쿼리를 넘기는 실수가 세 번 반복됐다.

1. 인덱스 없는 컬럼으로 대형 테이블에 진입하는 쿼리를 넘겼다. 같은 문서 아래쪽에 「이 컬럼으로 진입하면 풀스캔」이라고 직접 써 놓고도.
2. 「비용이 기준을 넘으면 실행 금지」라는 중단 기준을 직접 써 놓고, 그 열 배가 넘는 쿼리를 넘겼다. 인덱스는 정상이었고 원인은 드라이빙 집합에서 필터를 뺀 것이었다.
3. 대형 테이블 둘을 헐거운 조건끼리 조인하는 쿼리를 실행계획 확인도 타임아웃도 없이 넘겼다. 사용자가 취소했으나 먹지 않아 수동 종료가 필요했다.

세 번 모두 **규칙은 이미 적혀 있었다.** 그래서 문구가 아니라 형식 고정 → 점검 스크립트 → 훅 순으로 강제 수준을 올렸다.

## 1. 운영 쿼리의 고정 형식

| 규칙 | 이유(Why) |
|---|---|
| **`EXPLAIN`을 붙인 한 벌만** 준다(ANALYZE 없이). 기대 계획과 중단 기준을 한 줄 덧붙인다 | 사용자가 계획이 괜찮으면 `EXPLAIN`만 떼고 돌린다. 실행용을 따로 한 벌 더 주면 둘 중 무엇을 돌릴지 헷갈린다 |
| `EXPLAIN`은 에이전트가 붙인다. 「느리면 먼저 보세요」라고 사용자에게 시키지 않는다 | 「느리면 바꾸세요」는 실행 뒤에 대응할 수 있다는 전제인데, 그 전제가 틀렸다 |
| 드라이빙 테이블의 **인덱스 선두 컬럼**으로 진입한다. 진입 컬럼과 필터 컬럼을 구분해 주석으로 표시한다 | 인덱스에 없는 컬럼은 힙 필터일 뿐 범위를 좁히지 못한다 |
| 대형 테이블 둘을 조인할 때는 **한쪽을 MATERIALIZED 소집합**(수백~수천 행)으로 먼저 좁힌다 | 헐거운 조건끼리 조인하면 양쪽 전량 정렬·병합 계획이 나온다 |
| `IN` 목록과 날짜 경계는 **리터럴**로 박는다 | 런타임 값이 되면 플래너가 범위를 인덱스 조건으로 쓰지 못한다 |
| MATERIALIZED CTE와 `EXISTS`/`NOT EXISTS`를 같이 쓰지 않는다(창 함수로 치환) | semi/anti join으로 평탄화되면서 MATERIALIZED가 무력화된다 |
| 탐색용 조회에 `LIMIT 1`을 붙이지 않는다 | 인덱스로 진입하지 않는 조회에서는 row-goal 계획 때문에 오히려 느려진다 |
| 집계 대상을 좁히는 필터는 **CTE 안**에 둔다 | SELECT의 CASE에만 두면 드라이빙 집합이 통째로 들어온다 |
| 무거울 여지가 있으면 `SET LOCAL statement_timeout`을 한 줄로 권고한다 | 추정이 틀려도 정해진 시간에 끊긴다. 세션에 남지 않는다 |

### `EXPLAIN`을 생략해도 되는 경우

- 기본 키·확인된 인덱스로 소수 리터럴을 조회하는 쿼리
- 이미 문제없이 돌린 적 있는 쿼리와 같은 테이블·같은 키 형태

**Why** 확인 쿼리마다 습관적으로 `EXPLAIN`을 붙여 사용자가 매번 떼야 했다.

## 2. 넘기기 전 자기 검산

- 내가 문서에 적은 주의 사항·중단 기준을 **쿼리마다 대조**한다.
- 드라이빙 집합의 행 수를 실제로 어림한다. 인덱스가 있어도 진입 조건이 헐거우면 끝이다.
- 보조·대조 쿼리는 본 쿼리와 모집단(필터)을 맞춘다. 한쪽에만 조건이 있으면 두 결과를 대조할 수 없다.
- 잔존·방치·미처리를 세는 쿼리에는 **상한**을 건다(예: 현재 시각 10분 전까지). 하한만 걸면 그 숫자는 적체가 아니라 유입량이다.
- 보정·원복·상태 조회 쿼리는 「사용자가 말한 상태 이름 ↔ 쿼리의 코드값 ↔ 코드표 조회 결과」 3열 표를 직접 적어 대조한다.

## 3. 비용 추정이 믿기지 않을 때

통계가 낡은 테이블은 추정이 통째로 깨진다(수만 배 과대 추정 사례). 비용만 보고 반려하면 멀쩡한 쿼리를 계속 못 돌린다. 순서대로 따진다.

1. 이미 성공한 쿼리의 진부분집합인가 → 그렇다면 안전하다.
2. 실제 카디널리티를 아는 값이 있는가 → 앞선 실행 결과와 추정치를 대조한다.
3. 둘 다 애매하면 비용으로 막지 말고 타임아웃으로 막는다.

단, 인덱스 자체가 없어 풀스캔이 걸리는 경우는 여전히 실행 금지다. 타임아웃 우회는 「인덱스는 정상인데 추정만 이상한」 경우에 한한다.

덧붙임
- 창을 넓힐지 판단은 추정 행 수가 아니라 리터럴 범위로 `EXPLAIN`을 한 번 돌려 보고 한다. 플래너가 인덱스 둘을 비트맵으로 교차하면 실제 작업량은 교집합 뒤에 있다.
- 인덱스에 없는 컬럼을 집계 축에 넣으면 커버링 인덱스를 버린다. 넓은 집계는 커버 컬럼만으로 뽑고 부가 축은 범위를 좁힌 뒤 별도 쿼리로 본다.
- 창을 쪼개려고 생성 함수 + LATERAL 조인을 쓰면 날짜 경계가 런타임 값이 되어 인덱스 축 자체가 바뀐다.

## 4. 점검을 기계에 맡긴다

| 수단 | 하는 일 |
|---|---|
| 스킬 [`query-plan-check`](../04_skills/query-plan-check/SKILL.md) | 쿼리를 넘기기 직전 정적 점검 + 인덱스 정의 대조. 실행계획 텍스트도 점검 |
| 훅 `sql_check.py` | 분석 문서에 SQL 블록을 쓰면 자동 점검. 금지 판정이면 막고 알린다 |

## 5. 운영 데이터에서 하지 않는 것

- 실고객 데이터를 화면에서 열어 대조하자고 제안하지 않는다. 쿼리로 화면 로직을 재현한 결과까지로 판정한다. 화면 확인은 개발 환경 검체로만.
- 검증 쿼리에 개인정보 컬럼을 넣지 않는다. 식별은 키로 충분하다. 개인정보 축이 판정 대상이면 값이 아니라 길이·NULL 여부·앞 글자 마스킹 형태로 뽑는다.
- 개발 환경 결과로 운영 실측을 대신하지 않는다.

쿼리를 사용자에게 건네는 형식은 [쿼리 전달 형식](../08_communication/05_query-handoff-format.md).
