# 피드백 메모리 카탈로그

그동안 쌓인 피드백·사용자 메모리(묶음 7개 + 단건 약 25개 + 사용자 3개)를 **규칙 · Why · How to apply**로 일반화한 목록이다.
원문의 사례는 업무 내용을 걷어 낸 짧은 예로 바꿨다. 새 환경에서는 이 표를 출발점으로 삼되, **자기 환경에서 실제로 실패가 난 뒤에** 해당 줄을 메모리로 옮기는 것을 권한다.

읽는 법: 「상세」 열은 이 플레이북에서 그 규칙을 풀어 쓴 문서다.

## A. 분석·위임 묶음

| 규칙 | Why | How to apply | 상세 |
|---|---|---|---|
| 검색 0건을 「없다」의 근거로 삼지 않는다 | 0건을 근거로 「그 경로는 없다」고 판정했는데 다른 코드값의 조건부 허용으로 존재했다 | 분기를 열어 읽고 위치를 근거로 적는다. 못 읽었으면 「미확인」 | [증거 우선 1](../01_principles/01_evidence-first.md) |
| 생성 주체를 INSERT 문자열 검색으로 판정하지 않는다 | 검색이 레거시 루틴만 잡았고 실제 정본은 ORM `save()`였다 | SQL 리터럴 + 엔티티·save + 컨슈머 세 경로를 병렬로. 호출부 실재 확인 | [증거 우선 3](../01_principles/01_evidence-first.md) |
| 영향도는 그 흔적을 읽는 모든 코드를 열어 판정한다 | 전제에서 연역한 영향 목록이 전체 취소 경로를 빠뜨렸다 | 검색 키 → 레포별 전수 목록 → 영역별 병렬 위임 → file:line | [분석 절차 3](../02_procedures/04_analysis-and-impact.md) |
| 무거운 추론은 깊이를 강제하고, 리뷰 지적은 전달 전에 재검증한다 | 리뷰 지적의 절반이 오탐이었다 | 설계·영향도·디버깅은 위임 또는 단계적 검토. 지적마다 ✅/⚠/미검증 | [위임 루프 4](../02_procedures/02_delegation-loop.md) |
| 코드 수정은 크기별로 — 소규모는 메인, 대형은 위임 | 열 줄 변경에 위임 왕복이 수 분 걸렸다 | 1~2파일은 직접 + 검증 명령 1회. 안(案)은 이름만 붙이지 말고 「어느 파일 어디를 어떻게」로 제시 | [위임 루프 1](../02_procedures/02_delegation-loop.md) |
| 설정·매퍼 파일을 바꾼 변경은 서버 기동과 실제 호출까지 한다 | 컴파일은 통과했는데 서버가 뜨지 않는 상태로 PR을 올렸다 | 위임 프롬프트의 검증 항목에 기동 + 호출을 넣는다 | [검증 루프 6](../02_procedures/05_dev-verification-loop.md) |
| 사용자가 데이터로 확인해 가는 중엔 추정으로 빈칸을 채우지 않는다 | 근거 없는 원인 추정을 연달아 내놓았다 | 답은 데이터에 찍힌 사실만. 모르면 「모름」 + 확인 쿼리 | [증거 우선 7](../01_principles/01_evidence-first.md) |
| 설계·분석 위임에는 추론 강도를 처음부터 높게 | 강도를 빠뜨려 결과를 버리고 다시 돌렸다 | 에이전트 종류와 무관하게 적용. 중단·재시작 전엔 먼저 묻는다 | [실행 규율 6](../01_principles/04_execution-discipline.md) |

## B. 질문·결정 묶음

| 규칙 | Why | How to apply | 상세 |
|---|---|---|---|
| 묻는 것은 안전장치 승인·사용자만 아는 값·결과가 갈리는 업무 판단뿐 | 하루 질문 열 번 중 필요한 것은 두 번이었다 | 구현 선택은 권고 1안으로, 내부 관리는 하고 1줄 보고 | [질문 매트릭스 1](../01_principles/03_question-matrix.md) |
| 명시 동사 없는 발언은 미결로 올리지 않는다 | 흘린 말을 세 곳에 기록했다가 철회했다 | 사실로만 반영. 애매하면 한 문장으로 묻는다 | [질문 매트릭스 2](../01_principles/03_question-matrix.md) |
| 질문에는 답만 한다 | 질문에 답하면서 조치까지 실행해 지적받았다 | 동사가 없으면 바꾸는 일(편집·기록·전송·위임)을 하지 않는다. 필요해 보이면 한 줄로 제안하고 멈춘다 | [질문 매트릭스 2-1](../01_principles/03_question-matrix.md) |
| 보류로 마킹하기 전에 사용자에게 먼저 묻는다 | 「확인 필요」로 미룬 네 건 중 두 건은 사용자가 즉답했다 | 사용자가 모른다고 한 것만 확인 필요로 남긴다 | [질문 매트릭스 4](../01_principles/03_question-matrix.md) |
| 질문 도구 인자에 한글을 이스케이프로 쓰지 않는다 | 깨진 글자가 사용자 화면에 그대로 나갔다 | 평문으로 입력. 사용자에게 노출되는 모든 인자에 적용 | [질문 매트릭스 3](../01_principles/03_question-matrix.md) |
| 물을 때는 질문 도구로, 권고안을 첫 선택지에 | 설명에 섞인 질문은 사용자가 찾아내야 한다 | 배경은 산문, 결정 지점은 도구. 한 턴 질문은 한 번에 | [질문 매트릭스 3](../01_principles/03_question-matrix.md) |
| 사용자가 보류한 결정을 매 턴 다시 묻지 않는다 | 같은 보류 해제 여부를 세 턴 연속 물었다 | 「사용자 지시 대기」로만 적는다. 전제가 바뀌었을 때만 재질문 | [질문 매트릭스 5](../01_principles/03_question-matrix.md) |
| 업무 우선순위·다음 할 일을 먼저 제안하지 않는다 | 매 턴 「본업으로 돌아가라」를 붙여 주제넘다는 지적을 받았다 | 완료 보고에서 멈춘다. 다음 할 일은 물었을 때만 | [질문 매트릭스 9](../01_principles/03_question-matrix.md) |
| 진행 중인 작업에는 다음 한 걸음만 준다 | 검증 중에 「나중에 판단용」 쿼리를 덧붙여 환경까지 헷갈리게 했다 | 곁가지는 끝난 뒤, 물었을 때만. 쿼리는 실행 환경을 한 줄로 못 박는다 | [질문 매트릭스 9](../01_principles/03_question-matrix.md) |
| 본 과제가 안 끝났는데 감시·모니터링부터 꺼내지 않는다 | 부수 과제가 앞머리에 오면 지금 손댈 것이 흐려진다 | 부수 과제는 미결 목록 아래쪽에 둔다 | [질문 매트릭스 9](../01_principles/03_question-matrix.md) |
| 전해 받은 담당자 회신은 전제로 받는다 | 전언을 「실측 확인 필요」로 세 턴 연속 되돌렸다 | 실측 제안 전에 실행할 데이터가 있는지 판단. 코드로 확인 가능한 것은 계속 직접 검증 | [질문 매트릭스 6](../01_principles/03_question-matrix.md) |
| 지적받으면 지적된 범위만 고친다 | 유효한 질문까지 접고 사용자가 하지 않은 결론을 지어냈다 | 틀린 것 / 열려 있는 것 / 검증한 것으로 가른다 | [질문 매트릭스 7](../01_principles/03_question-matrix.md) |
| 명확한 개발 환경 테스트 요청은 바로 시도한다 | 정보 확인을 이유로 멈춰 하루가 밀렸다 | 가장 단순한 가정으로 호출하고 오류를 보고 조정. 업무 용어를 코드값으로 단정하지 않는다 | [질문 매트릭스 10](../01_principles/03_question-matrix.md) |
| 비용을 이유로 검증 범위를 줄이자고 하지 않는다 | 사용자가 비용은 감당한다고 명시했다(환경에 따라 다름) | 판단 기준은 품질·정확도·사용자 시간 | [원칙 요약](../01_principles/00_overview.md) |
| 정책 여부는 정책 문서 → 화면 → 코드 → 실측 순으로 근거를 댄다 | 실측만으로는 「없었다」만 말할 수 있다 | 사용자가 말한 정책은 그 자리에서 결정 표에 올린다 | [증거 우선 8](../01_principles/01_evidence-first.md) |
| 다른 팀 PR의 댓글은 올리기 전에 초안을 보여 준다 | 일괄 허락을 새 건에 넓혀 댓글을 여러 번 고쳤다 | 허락은 그 묶음에만 유효 | [승인 경계 4·5](../01_principles/02_approval-boundary.md) |
| 승인 대기 건은 한 번 물었으면 다시 꺼내지 않는다 | 같은 승인 대기를 다섯 번 반복했다 | 상태 줄에만 둔다 | [승인 경계 7](../01_principles/02_approval-boundary.md) |

## C. 산출물·기록 묶음

| 규칙 | Why | How to apply | 상세 |
|---|---|---|---|
| 모든 산출물은 한 볼트 안에, 워크스페이스 루트에는 만들지 않는다 | 흩어진 파일을 한 구조로 정리한 직후 다시 루트에 파일을 만들었다 | 만들기 전에 경로부터 정한다 → 프론트매터 → 목차 등재 | [문서와 채번 1](../02_procedures/09_documents-and-numbering.md) |

| 작업 문서 갱신은 요청할 때만 | 실측마다 문서를 고쳐 흐름이 끊겼다 | 메모리에만 반영하고 「반영할 항목 N건」만 알린다 | [실행 규율 5](../01_principles/04_execution-discipline.md) |
| 일일노트는 작업 묶음 끝에 한 번, 짧게 | 발언마다 고쳐 편집 diff가 화면을 채웠다 | 셸 append 1회, 줄당 160자 안팎 | [일일노트](../02_procedures/03_daily-note-3-layer.md) |
| 요일은 추정하지 말고 계산한다 | 이틀 치 요일을 틀리게 적었다 | 날짜 명령으로 확인 | [일일노트](../02_procedures/03_daily-note-3-layer.md) |

## D. Git·PR 묶음

| 규칙 | Why | How to apply | 상세 |
|---|---|---|---|
| 커밋·PR에 생성 도구 서명을 붙이지 않는다 | 사용자의 명시적 거부. 하네스 안내를 따라 PR 여러 건에 붙였다가 지웠다 | 설정으로 끄고, 커밋뿐 아니라 PR 본문도 확인 | [Git 1](../02_procedures/07_git-pr-and-release-branches.md) |
| PR 설명에는 내 작업만, 목록 서식 주의 | 설명이 한 문단으로 뭉개져 렌더링됐다 | 목록 앞 빈 줄, 중첩 금지, 올린 뒤 렌더링 확인 | [Git 5](../02_procedures/07_git-pr-and-release-branches.md) |
| 브랜치는 통합 브랜치에서 따고 통합 브랜치로 | 저장소 기본 HEAD를 base로 잡아 잘못 올렸다 | 만들기 전에 타깃 확인 | [Git 2](../02_procedures/07_git-pr-and-release-branches.md) |
| 운영용 PR 타깃은 레포별 배포 브랜치 표로 | 배포 브랜치가 아닌 곳에 머지해 운영 미반영 | 표에 없는 레포는 PR 전에 묻는다 | [Git 2](../02_procedures/07_git-pr-and-release-branches.md) |
| 수동 반영 대상은 반영 전 운영 정의와 레포를 대조한다 | 레포가 운영보다 뒤처져 핫픽스를 덮어쓸 뻔했다 | 어긋나면 운영 본문으로 레포부터 맞춘다 | [Git 3](../02_procedures/07_git-pr-and-release-branches.md) |
| PR 작업은 REST 스크립트로 | MCP 응답 전문이 도구 출력의 최대 원천이었다 | 응답 한 줄. MCP는 조회만 | [스크립트](../05_hooks-and-scripts/README.md) |
| 리뷰어는 생성 시 함께, 레포마다 조회 | 다른 레포 명단을 복사해 빠뜨렸다 | 페이지네이션 끝까지. 빠뜨리면 REST로 추가 | [Git 5](../02_procedures/07_git-pr-and-release-branches.md) |
| 올라간 PR의 수정은 승인받고, 후속 수정은 마지막 1커밋 | 짧은 시간에 세 번 고쳐 알림을 반복 보냈다 | before/after 제시, 모아서 한 번 | [Git 5](../02_procedures/07_git-pr-and-release-branches.md) |
| 형상관리에 없는 객체는 원본 등록 커밋을 따로 | 리뷰어가 원본 수백 줄을 리뷰 대상으로 봤다 | 원본은 통합 브랜치에 먼저, PR엔 수정만 | [Git 3](../02_procedures/07_git-pr-and-release-branches.md) |
| 새 과제는 메인이 깨끗하면 브랜치 전환, 아닐 때만 worktree | 양쪽 실패가 모두 있었다(과제 섞임 / 기계적 worktree) | 수정 전에 메인 상태부터 본다. 훅이 확인 | [Git 4](../02_procedures/07_git-pr-and-release-branches.md) |
| 티켓 「완료」의 기준은 사용자 정의를 따른다 | 도구 안내문대로 완료 전환을 반복해 물었다 | PR 보고 끝에 완료 전환을 묻지 않는다 | [Git 6](../02_procedures/07_git-pr-and-release-branches.md) |
| 「변경 100여 개」는 가짜일 수 있다 | 줄 끝 문자 stat 캐시 문제였다 | 해시 셋을 비교하고 인덱스만 다시 세운다 | [Git 8](../02_procedures/07_git-pr-and-release-branches.md) |

## E. 코드 스타일 묶음(프로젝트마다 다르다 — 형식만 참고)

| 규칙 | Why | How to apply |
|---|---|---|
| 프로젝트의 코드 관례를 위임 프롬프트의 명시 조건으로 넣는다 | 리팩터링 지적 세 건(상태 변경 방식·불필요한 변환 계층·표기 관례)을 한 번에 받았다 | 관례 목록을 메모리에 두고 위임 때 그대로 붙인다 |
| 새 식별자의 약어는 조직의 표준 사전으로 확인한다 | 기존 이름을 보고 조합해 비표준 약어가 여럿 섞였다 | 완료 보고에 사용 약어 목록을 받게 하고 독립 검증에서 점검한다 |
| 주석에 AI가 쓴 티를 남기지 않는다 | 「커밋된 주석이 전부 AI가 쓴 티가 난다」 | 강조 기호, 실측 수치·조사 날짜, 자기 정당화, 타 파일 줄 번호 인용, 장식선을 뺀다. 남기는 것은 코드만 봐서는 모르는 함정뿐 |
| API 문서 주석에 내부 스키마를 노출하지 않는다 | 응답 문서에 테이블·컬럼 이름이 그대로 나갔다 | 사용자 언어의 필드 이름만. 소비자가 알아야 하는 코드 그룹 번호는 유지 |
| 파일 헤더의 변경 이력은 파일당 한 줄 | 미배포 상태의 중간 이력은 노이즈다 | 세션·날짜별 줄을 쌓지 않는다. 설명은 커밋·PR로 |
| SQL은 팀 표준 서식으로, 요청자가 준 모양을 그대로 옮기지 않는다 | 이웃 쿼리의 서식을 따라 팀 표준과 다르게 썼다 | 표본 파일 하나를 정해 두고 따른다. 테이블 별칭은 의미 있게 |
| 주석만 바꾸는 작업은 별도 패스로 | 로직이 섞이면 검증할 수 없다 | 치환 문구를 메인이 확정해 넘기고 「diff에 코드 줄 0」으로 검증 |

## F. 쿼리 전달 묶음

상세는 [쿼리 전달 형식](../08_communication/05_query-handoff-format.md).

| 규칙 | Why |
|---|---|
| 쿼리는 항상 그대로 실행 가능한 전체로 준다 | 조각을 이어 붙이다 누락·오타가 생기면 결과가 틀리는데 추적이 어렵다 |
| 대상 범위는 파생 데이터의 존재가 아니라 업무 조건으로 정의한다 | 조인으로 건수를 맞췄더니 「그건 뒤 단계까지 간 건만 고른 것」이었다 |
| 확인 단계는 작게, 최종 전달은 전체로 | 큰 쿼리 뭉치를 세 번 연속 다시 던져 혼란을 줬다 |
| 설명과 코드블록 사이에 빈 줄 | 드래그 복사할 때 설명 줄이 딸려 온다 |
| 검증 쿼리에 개인정보 컬럼을 넣지 않는다 | 사용자가 직접 지워야 했다 |
| 실고객 데이터를 화면에서 열어 보자고 하지 않는다 | 열람 수단도 필요도 없다 |
| 실행을 부탁하는 쿼리는 대화 본문에 전부 보여 준다 | 문서에만 넣었더니 보이는 한 줄만 실행됐다 |
| 여러 단계 보정은 트랜잭션 시작과 커밋·롤백을 모두 적는다 | 「자동 커밋을 끄고」라는 안내는 빠뜨리기 쉽다 |

## G. 상황별 형식·용어 묶음

| 규칙 | Why |
|---|---|
| 캔버스 노드 높이는 스크립트로 계산한다 | 눈대중으로 넣어 텍스트가 잘렸다 |
| 스프레드시트 덤프에서 병합 셀을 놓치지 않는다 | 「필드 누락」으로 두 번 이상 오진했다 |
| 메일 초안은 처음부터 HTML 파일로 띄운다 | 붙여넣었을 때 서식이 유지돼야 한다. 소속 표기는 내부용/외부용을 구분 |
| 발번용 제목·설명은 각각 한 줄 | 문단을 써 줬더니 대장에는 설명급이었다 |
| 팀 공유 문서는 팀의 기존 문체와 「현황 → 내용」 구조로, 내가 헤맨 흔적은 뺀다 | 건조한 변경 목록도 서사형 성과 문서도 반려됐다 |
| 우리 몫이 아닌 후속 조치를 회신에 약속하지 않는다 | 다른 조직이 진행하는 일을 「요청하겠다」고 적었다 |
| 다른 팀에 줄 가이드에는 요청받은 사용법만 | 확인하지 않은 인과를 덧붙였는데 사실과 달랐다 |
| 용어는 사용자가 정한 이름으로 통일한다 | 혼용되는 이름이 새 기능처럼 읽혔다 |
| 「하나씩 설명해」는 한 답변에 한 항목 | 한 번에 풀어 놓으면 읽을 수 없다 |
| 메신저에 붙일 API 안내는 기본 주소와 경로를 나눠 적는다 | 긴 주소가 자동 링크로 바뀌며 뒤가 잘렸다 |

상세는 [대신 쓰는 글](../08_communication/03_ghostwriting-tone.md).

## I. 사용자 메모리
