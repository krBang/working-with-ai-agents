# 메모리 설계

에이전트의 자동 메모리(세션마다 자동으로 로드되는 인덱스 + 필요할 때 읽는 토픽 파일)를 어떻게 구성하고 무엇을 넣는가.

## 1. 구조

```
<memory-dir>/
  MEMORY.md                      ← 인덱스. 세션 시작 때 자동 로드(앞 200줄 또는 25KB까지만)
  <과제>.md                       ← project: 과제별 현재 상태·결정·함정
  <주제>-rules.md                 ← feedback 묶음: 일하는 방식
  <개별 피드백>.md                ← feedback: 묶음에 안 들어간 단건
  user-*.md                      ← user: 사용자에 대한 사실
  <기술 주제>.md                  ← reference: 기술 지식·함정·접속 방법
  closed-tasks.md                ← reference: 종결 과제 목록
```

토픽 파일은 인덱스의 링크를 따라 **필요할 때만** 읽힌다. 그래서 인덱스 줄의 한 줄 설명이 「언제 이 파일을 열어야 하는지」를 말해 줘야 한다.

## 2. 유형 네 가지

| 유형 | 담는 것 | 예 | 자동 정리 대상 |
|---|---|---|---|
| `user` | 사용자에 대한 사실 — 소속, 표기, 계정 구분 | 「소속 팀 이름은 이것이다. 추측하지 말 것」 | 아니다(코어) |
| `feedback` | 일하는 방식에 대한 교정 — 규칙 + Why + How to apply | 「질문·결정 매트릭스」「Git·PR 규칙」 | 아니다(코어) |
| `project` | 진행 중 과제의 현재 상태·결정·대기 | 과제 파일, 도구 상태 파일 | **그렇다** — 상태 줄만 |
| `reference` | 다시 쓸 기술 지식·함정·절차 | 「이 테이블의 조인 키」「개발 DB 접속 방법」 | 아니다 |

**Why 구분하나** 정리 루틴이 과제 상태만 줄이고 일하는 방식은 건드리지 않게 하려면 유형이 파일에 적혀 있어야 한다.

## 3. 파일 형식

```markdown
---
name: <파일명과 같은 이름>
description: <한 줄 — 이 파일을 언제 열어야 하는지가 드러나게>
metadata:
  type: feedback        # user | feedback | project | reference
---

<규칙을 한두 문장으로>

**Why:** <언제 어떤 일이 있었고 무엇이 문제였는지. 날짜 포함>

**How to apply:** <구체적으로 언제 무엇을 하는지. 예외와 경계>

관련: [[다른-메모리-이름]]
```

- **Why를 반드시 적는다.** 규칙만 있으면 새 상황에서 적용 범위를 판단할 수 없다. 사용자의 실제 말을 짧게 인용해 두면 강도가 전달된다.
- 파일끼리는 `[[이름]]`으로 잇는다. 정리 루틴이 끊긴 링크와 고아 파일을 찾는다.
- 템플릿: [`templates/memory-feedback.md`](../templates/memory-feedback.md) · [`memory-project.md`](../templates/memory-project.md) · [`memory-user.md`](../templates/memory-user.md) · [`memory-reference.md`](../templates/memory-reference.md)

## 4. 인덱스(MEMORY.md)의 절

| 절 | 내용 |
|---|---|
| 즉시 참조 함정 | 포인터 한 줄 — 함정 본문은 프로젝트 rules 파일에 있다 |
| 활성 작업 | **과제당 한 줄** |
| 종결 | 종결 목록 파일 링크 한 줄 |
| 보존 가드 | 지우거나 다시 제안하지 말 것 — 「먼저 언급 금지」「재제안 금지」 표시가 붙은 항목 |
| 사용자 | user 메모리 링크 |
| 작업 방식(피드백) | feedback 메모리 링크 + 한 줄 요약 |
| 참조 · 기술 지식 | reference 메모리 링크 + 한 줄 요약 |

템플릿: [`templates/MEMORY.md`](../templates/MEMORY.md)

## 5. 인덱스 한 줄 원칙

**규칙** 활성 작업은 과제당 한 줄만 둔다 — 「지금 상태 · 다음 · ⏳대기 · `작업물:`」. 목표 300자 이내. 고칠 때는 **덧붙이지 말고 그 줄을 다시 쓴다.** 끝난 단계(✅)는 지운다. 진행 경위·커밋 해시·검체·테스트 결과는 과제 파일 스냅샷이나 일일노트에 둔다.

**Why** 인덱스가 로드 한도 직전까지 불어났고, 한 과제의 줄이 수천 자였다. 한도를 넘으면 뒤쪽 줄은 아예 로드되지 않는다.

### 활성 작업 줄의 필수 필드

```
- [과제 이름](과제-파일.md) — 지금 상태 · ⬜다음 할 일 · ⏳타팀(담당·~예상일) · 작업물: <작업 폴더>@<브랜치> 미커밋N / 대기: <무엇을 기다리나>
```

**Why** 메모리 파일이 없는 작은 과제는 이 줄이 유일한 저장소다. 작업물 위치가 없으면 다음 세션이 어느 폴더·브랜치에서 이어 갈지 알 수 없다.

## 6. 크기 한도는 바이트로 센다

| 기준 | 값 |
|---|---|
| 로드 한도(도구 제약) | 앞 200줄 또는 25KB |
| 운영 상한 | 22KB 미만 |
| 목표 | 18KB 안팎 |

**Why** 처음에는 글자 수로 상한을 정했다. 한글은 글자당 3바이트라 글자 수로는 한도를 거를 수 없었다 — 글자 수 기준으로는 여유가 있었는데 바이트로는 한도 직전이었다.

한도 근처가 되면 보고만 하지 말고 구조 개선(절 분리·과제 파일로 이동)을 먼저 제안한다.

## 7. 과제 메모리 파일의 최상단

```markdown
## 현재 상태 스냅샷 (YYYY-MM-DD)
- 지금 상태 / 다음 첫 손 / 대기 / 작업물

## 확정 정책·결정 표
| 결정 | 내용 | 근거(누가·언제·문서) |

## 함정
- ⛔ … (file:line)
```

**규칙**
- 세션은 이 위쪽만 읽고도 이어 갈 수 있어야 한다.
- 사용자가 정책을 말하면 그 자리에서 결정 표에 올린다.
- 날짜 이력을 쌓지 않는다. 경위는 일일노트로.
- 결정이 뒤집히면 **옛 줄을 지운다.** 「(이전)」으로 남기지 않는다.

**Why** 스냅샷이 몇 주 전 날짜에 멈춰 있었고, 파일 하나에 스냅샷 절이 네 개였다. 무엇이 최신인지 알 수 없었다. 옛 결정이 남아 있으면 다음 세션이 그것을 현행으로 읽는다.

## 8. 상태를 담는 곳은 둘뿐

1. 메모리 인덱스의 활성 작업 한 줄
2. 과제 메모리 파일 최상단 스냅샷

문서 목차·최상위 인덱스·팀 문서에는 상태어를 쓰지 않는다. 일일노트의 「지금 상황」 블록은 메모리에서 하루 한 번 렌더링한 스냅샷일 뿐 저장소가 아니다.

## 9. 메모리에 넣지 않는 것

| 넣지 않는 것 | 대신 |
|---|---|
| 날짜별 경위·이력 | 일일노트 |
| 커밋 해시·검체 목록·테스트 결과 전문 | 과제 파일 스냅샷(최신만) 또는 주제 문서 |
| 비밀값·토큰 | OS 자격 증명 저장소. 메모리에는 「어디에 있고 열지 말 것」만 |
| 고정 테스트 값(테스트 수신자 정보 등) | 로컬 프로필 파일. 메모리·문서·대화에 값을 다시 쓰지 않는다 |
| 개인정보·실제 식별값 | 넣지 않는다 |
| 사용자가 망설이며 흘린 관행 | 규칙으로 굳히지 않는다 |

## 10. 메모리는 그 시점의 관찰이다

메모리의 컬럼·코드값·file:line은 적은 시점의 사실이다. 쿼리나 설계에 쓰기 전에 현재 코드·DB로 다시 확인한다. 오래된 메모리일수록 그렇다.

## 11. 에이전트가 둘 이상일 때

메모리는 **한 에이전트만 쓴다.** 다른 에이전트는 읽기만 하고, 갱신이 필요하면 쓰는 쪽에 메시지로 요청한다.

**Why** 쓰는 쪽이 하나여야 같은 줄을 동시에 고쳐 상태가 꼬이지 않는다.
