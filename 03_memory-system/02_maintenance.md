# 메모리 정리 루틴

메모리는 쓰기만 하면 불어난다. 정리를 사람의 기억에 맡기지 않고 루틴으로 돌린다. 스킬: [`memory-tidy`](../04_skills/memory-tidy/SKILL.md)

## 1. 세 가지 정리

| 정리 | 주기 | 묻는가 |
|---|---|---|
| **쓸 때마다** — 인덱스 줄을 고칠 때 덧붙이지 않고 바꿔 쓴다. 끝난 단계는 지운다 | 매번 | 묻지 않는다 |
| **매일 아침** — 인덱스 크기·긴 줄·끊긴 링크·고아 파일 점검, 긴 줄을 과제 파일로 이동 | 하루 1회(업무 보고 스킬 앞에서) | 묻지 않고 결과 한 줄 |
| **1회 압축** — 날짜 이력이 쌓인 과제 파일을 스냅샷 + 이관 문서로 가른다 | 파일당 1회 | 승인받는다 |

**Why 묻지 않나** 내부 관리를 사용자에게 물어 왕복이 생겼다(인덱스 편집 6회, 압축 명령 12회, 질문 2회). 내부 관리는 하고 결과만 한 줄 보고한다.

## 2. 손대지 않는 것(코어)

정리 대상은 **「활성 작업」·「종결」 절의 과제 상태 줄뿐**이다. 아래는 크기가 커도 줄이지·옮기지·합치지·지우지 않는다.

- 인덱스의 「작업 방식(피드백)」「사용자」「참조」「기술 지식」「보존 가드」「즉시 참조 함정」 절
- `feedback`·`user`·`reference` 유형 파일의 본문 전부
- 프로젝트 rules 파일, 규칙 문서, 스킬
- 과제 파일의 함정(⛔·★) 구절 — 옮겨 받기만 하고 지우지 않는다

한도를 못 맞추면 이 구역을 건드리지 말고 사용자에게 묻는다(어느 과제를 종결로 내릴지).

**Why** 일하는 방식이 깎이면 잘하던 일을 갑자기 못하게 된다.

## 3. 매일 아침 루틴

### 측정(명령 1회)

- 인덱스 바이트 수(상한 대비)·줄 수(200줄 대비)
- 900바이트를 넘는 줄
- 끊긴 링크(인덱스가 가리키는데 파일이 없는 것)
- 고아 파일(어디에서도 참조되지 않는 것)

### 백업(고치기 전에 반드시)

바꿀 파일(인덱스 + 옮겨 받을 과제 파일)을 **메모리 폴더 밖** 백업 폴더에 날짜별로 복사한다.

**Why 밖에** 메모리 폴더 안에 두면 같은 내용이 두 번 로드된다.

### 정리 기준(순서대로, 목표 크기까지 — 상한 밑에서 멈추지 않는다)

| # | 대상 | 처리 |
|---|---|---|
| 1 | 끊긴 링크 | 파일명이 바뀐 것이면 고치고, 파일이 없으면 링크만 걷어 낸다(줄 내용은 둔다) |
| 2 | 긴 활성 작업 줄 | 지난 경위·커밋 해시·검체·완료 단계를 과제 파일 스냅샷으로 옮기고, 인덱스에는 「지금 상태 · 다음 · ⏳대기 · 작업물」만 남긴다 |
| 3 | 과제 파일이 없는 과제의 긴 줄 | 경위가 일일노트에 있으면 지우고, 없으면 과제 파일을 만들어 옮긴다 |
| 4 | 종결 과제 | 종결 목록 파일로 옮긴다(링크 + 한 구절). 인덱스에는 그 파일 링크 한 줄만 |
| 5 | 결정이 뒤집힌 옛 문구 | 지운다 |

### 옮기는 방법

- **문장을 다시 쓰지 않는다.** 줄(구절)을 그대로 잘라 옮긴다. file:line이 든 구절은 원문 그대로.
- 옮기기 전후로 file:line 패턴 개수를 「인덱스 + 대상 파일」 합계로 대조한다. 줄면 되돌린다.
- 옮긴 구절마다 대상 파일에 원문 그대로 있는지 **문자열 일치**로 확인한다. 하나라도 없으면 백업에서 되돌린다.
- 받는 쪽에 「인덱스에서 이동(MM-DD)」 머리말을 붙이고, 인덱스 줄에는 그 파일 링크를 남긴다. 링크할 파일이 없으면 옮기지 않는다.
- 「보존 가드」 절과 「먼저 언급 금지」 표시 줄은 손대지 않는다.

**Why** 요약하며 옮기면 근거 위치와 미묘한 조건이 사라진다. 다른 방식(개수 대조 + 문자열 일치)으로 이중 확인해야 이관 중 유실을 잡는다.

### 보고

한 줄: 「메모리 정리: N → M 바이트 · 긴 줄 k개 과제 파일로 이동(원문 일치 확인) · 백업 <폴더> · 끊긴 링크 0 · 고아 1(<파일>)」

- 고아 파일은 지우지 않는다. 보고만 한다(보존 가드나 참조용일 수 있다).
- 일일노트에는 쓰지 않는다(내부 관리).

## 4. 과제 파일의 1회 압축

이미 이력이 쌓여 수백 줄이 넘은 과제 파일에 쓴다.

1. 사용자 승인을 받는다(대상 파일·방식).
2. 「함정·확정 사실·금지/주의」 불릿과 file:line이 든 줄은 **원문 그대로** 남긴다.
3. 이력은 주제 폴더의 이관 문서로 통째 옮긴다(줄 삭제·이동만).
4. 압축 전후 file:line 개수를 대조한다.
5. 최상단에 「현재 상태 스냅샷(날짜)」과 「확정 정책·결정 표」를 고정한다.
6. 옛 스냅샷 제목들은 「옛 스냅샷 잔존 함정(원문 §)」 한 절로 모은다.

실제 결과: 과제 파일 두 개가 각각 절반 이하 크기로 줄었고, 원문 줄 누락 0, file:line 줄은 전부 메모리에 남았다. 목표 크기에는 못 미쳤는데 원인은 「file:line·주의 구절 원문 유지」 규칙이었다 — 그 규칙은 지킬 가치가 있어 그대로 뒀다.

## 5. 피드백 파일의 합병

작은 피드백 파일이 수십 개로 불어나면 묶음 파일로 합친다.

| 묶음 | 들어가는 것 |
|---|---|
| 질문·결정 | 묻는 것/안 묻는 것, 발언 해석, 보류·재질문, 전언 신뢰, 과잉 철회 금지 |
| 분석·위임 | 부재로 단정 금지, 생성 주체 판정, 영향도 전수, 무거운 추론, 위임 크기 |
| 산출물·기록 | 산출물 위치·확장자, 문서 갱신 시점, 일일노트 쓰기 |
| Git·PR | 브랜치 기준, 리뷰어, PR 설명, 수정 승인, 작업 폴더 |
| 코드 스타일 | 프로젝트 코드 관례, 주석 기준, 식별자 약어 |
| 쿼리 전달 | 전체 실행형, 범위 정의, 형식, 개인정보 |
| 상황별 형식·용어 | 특정 상황에만 쓰는 형식 규칙과 용어 |

- 본문은 **원문 그대로** 절로 옮긴다(요약하지 않는다).
- 합병 뒤 옛 문장 중 뒤집힌 결정이 남아 있지 않은지 독립 검증을 한 번 돌린다. 실제로 옛 규칙 문장 일곱 곳이 남아 있었다.
- 새 피드백은 기존 묶음의 절로 추가하고 인덱스 줄은 늘리지 않는다.

실제 결과: 피드백 45개 파일이 묶음 7개로, 인덱스가 약 절반 크기·줄 수로 줄었다.

## 6. 종결 과제

- 인덱스에서 빼고 종결 목록 파일에 한 줄(링크 + 한 구절 + 「이 함정 때문에 파일을 보존한다」).
- 종결 목록 머리에 「활성 작업이 아니다 — 먼저 언급 금지, 재문의 때만 참조」를 적는다.
- 재검색 가치가 있는 상세 회고는 팀 문서나 별도 지식 저장소로 옮기고 메모리 파일은 지운다.

## 7. 크기 경고가 뜨면

도구가 인덱스 크기 경고를 띄우면 그 턴에 바로 정리한다. 다음으로 미루지 않는다.

## 8. 규칙이 늘어나는 비용을 관리한다(에이전트의 책임)

규칙·피드백 메모리·함정은 실패가 날 때마다 한 줄씩 는다. 줄이는 일은 저절로 일어나지 않는다. 그래서 **추가·통합·감량을 묶어 에이전트의 책임**으로 둔다.

| 자리 | 하는 일 |
|---|---|
| **새 규칙을 넣을 때** | 같은 묶음 안의 겹치는 줄·낡은 줄을 **먼저** 합치거나 지우고 나서 넣는다 |
| **주간 회고** | ① 4주 넘게 쓰이지 않은 규칙 ② 서로 겹치는 규칙을 **지울 후보**로 올린다 |
| **크기 상한** | 메모리 인덱스(바이트 기준 → [설계](01_design.md))와 함정 파일(줄 수 → [함정 파일 패턴](03_trap-file-pattern.md))에 상한을 둔다. 상한에 닿으면 넣기 전에 뺀다 |

**Why** 사용자의 말 — 「규칙은 잘 관리해 달라고 했었다」. 규칙이 늘어나는 비용이 아쉬운 점으로 꼽혔을 때, 그 관리는 이미 에이전트에게 맡겨진 일이었다.

2절(코어는 손대지 않는다)과의 관계 — 매일 도는 자동 정리는 여전히 코어를 건드리지 않는다. 규칙의 감량은 위 세 자리에서만 한다. 주간 회고는 후보를 올릴 뿐이고, 회고 루틴이 규칙 파일을 직접 고치지는 않는다.

아직 정하지 못한 것 — 「4주 넘게 쓰이지 않았다」의 판정법. 지난 4주의 세션 기록·정정 로그·일일노트에서 그 규칙이 적용되거나 인용된 흔적을 세는 방식으로 [회고 루틴 템플릿](../templates/routines/local-weekly-session-retro.md)에 초안을 넣었지만 한 번도 돌려 보지 않았다. 흔적이 없다는 것은 「필요 없는 규칙」의 증거가 아니다(잘 지켜져서 조용한 규칙일 수 있다). 그래서 삭제가 아니라 후보다.
