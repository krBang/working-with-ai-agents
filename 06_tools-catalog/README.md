# 도구 카탈로그

에이전트가 쓰도록 직접 만든 MCP·CLI 도구들의 **개념 문서**다. 코드는 없다. 각 문서는 「풀려던 문제 → 설계 원칙 → 사용 흐름 → 평가 → 교훈」 순서로 쓰여 있고, 특정 조직의 테이블·규칙 대신 일반 용어를 쓴다.

| 문서 | 도구 | 형태 | 한 줄 |
|---|---|---|---|
| [01](01_dev-e2e-automation.md) | 개발 환경 E2E 자동화 | MCP + 스킬 | DB 스냅샷·항상 롤백 스크립트·프로시저·API·배치·서버·TC 흐름·감사·되돌리기 |
| [02](02_repo-xref.md) | 레포 횡단 정적 참조 조회 | CLI + 스킬 | 테이블·루틴을 누가 읽고·쓰고·부르나. 위치만 주고 판단은 하지 않는다 |
| [03](03_ticket-automation.md) | 티켓 발번·조회 | MCP | 채번 대장을 플로우 호출로. 발번·수정은 매번 승인(MCP 서버 계층은 팀원과 함께) |

## 도구를 만들기로 한 기준

- 같은 왕복이 건당 서너 번씩 반복된다.
- 규칙이 문서에 있는데도 같은 사고가 난다(→ 규칙을 도구 안의 가드로).
- 응답이 커서 컨텍스트를 채우는 기성 도구를 대체할 수 있다.
- 반대로, **검색 몇 번이면 되는 일에는 만들지 않는다.** 만든 뒤에는 사용 로그로 실제 쓰이는지 본다.

## 공통 설계 원칙

| 원칙 | 내용 |
|---|---|
| **위협 모델을 먼저 적는다** | 막으려는 것은 「모델의 성실한 실수」다. 고의 우회는 못 막는다고 README에 쓴다 |
| **가드는 문서가 아니라 도구가 강제한다** | 거부 응답에 규칙 이름과 「고칠 점」을 담는다. 에이전트가 같은 요청을 재시도하지 않게 서버 안내문에 적는다 |
| **승인은 도구 이름 단위로 설계한다** | 조회(무승인)와 상태 변경(매번 승인)을 서로 다른 도구로 나눈다. 한 도구에 위험 수준이 다른 일을 섞지 않는다 |
| **감사 로그는 재생 가능하게** | 값은 가리되 구조는 남긴다. 이 로그가 회귀 테스트의 재료가 된다 |
| **개인정보는 환경에 맞게** | 개발 환경 도구는 결과를 **마스킹**한다. 가리지 못하는 형태는 한계로 명시한다 |
| **비밀은 도구도 모른다** | OS 자격 증명 저장소에 두고 사용자가 터미널에서 등록한다. 도구는 「있음/없음」만 돌려준다 |
| **설정은 코드 폴더 밖** | 개인 경로에 둔다. 코드 폴더에는 자리표시자만 든 예시 파일을 둔다. 자리표시자가 남아 있으면 접속하지 않는다 |
| **실패하면 재시도 대신 상태 확인** | 상태를 바꾸는 호출이 실패했을 때 재시도는 중복을 만든다 |
| **가드가 주 용도를 깎으면 그것이 최우선 결함** | 실사용 재생 회귀로 매 회차 확인한다 |
| **알려진 한계를 README에 적는다** | 평가 루프의 남은 지적이 낮은 심각도로 수렴하면 한계로 옮기고 멈춘다 |

## MCP로 만들까, CLI + 스킬로 만들까

| | MCP 서버 | CLI + 스킬 |
|---|---|---|
| 상시 컨텍스트 | 도구 설명이 매 세션 로드된다 | 스킬 description 한 줄만 |
| 설치 | 서버 등록·의존성·재시작 | 레포를 받으면 바로 |
| 승인 | 도구 이름 단위 권한·훅으로 정교하게 | 셸 명령 단위(패턴 매칭) |
| 사람이 직접 쓰기 | 어렵다 | 같은 CLI를 터미널에서 |
| 맞는 일 | 승인 수준이 갈리는 일, 상태를 갖는 일(잠금·감사·세션) | 읽기 전용 조회, 의존성 없는 분석 |

## 배포

- 문서 레포 하나를 **로컬 경로 플러그인 마켓**으로 쓴다. 팀원은 레포를 받고 마켓을 추가해 필요한 플러그인만 설치한다.
- 로컬 경로 마켓은 **작업 폴더의 파일을 바로 실행한다.** 그래서 그 레포는 기본 브랜치로 체크아웃해 둔다. 다른 브랜치로 바꾸면 그 브랜치의 도구가 뜬다.
- 갱신은 받아 오기 → 에이전트 도구 재시작(또는 MCP 재연결). 실행 중인 서버는 재시작해야 새 코드가 반영된다.
- 플러그인으로 바꾸면 도구 이름의 접두가 달라진다. 권한 규칙·훅 matcher를 함께 바꾸고 예전 수동 등록을 지운다.
- 개인 설정·비밀·감사 로그는 설치본 밖에 있어 갱신해도 그대로다.

## 교훈 모음

1. **효용을 막는 것은 미구현보다 제약인 경우가 많다.** 「안 되는」 이유를 제약과 미구현으로 갈라 본다.
2. **도구에 쓰는 시간이 업무를 앞지르는 순간이 온다.** 기능 동결·분할·슬림화의 기간을 따로 둔다.
3. **만든 쪽이 평가하지 않는다.** 독립 평가자 → 메인 재검증 → 수정의 회차를 돈다.
4. **실행되는 폴더를 직접 고치지 않는다.** 원본 작업 폴더에서 고치고 검토 뒤 동기화한다.
5. **두 에이전트가 같은 도구 폴더를 동시에 고치지 않는다.**
6. **떠올리지 않으면 안 쓴다.** 스킬 description·입력 훅으로 「이럴 때 이 도구」를 떠올리게 한다.
7. **같은 재제안은 문서로 막는다.** 결정의 근거 절을 README에 두고 메모리에 「재제안 금지」를 적는다.
8. **실행 경로는 추정하지 않는다.** 「서버는 캐시본을 실행한다」고 추정했는데 프로세스 명령줄을 보니 작업 폴더를 바로 실행하고 있었다. 재설치 뒤에도 옛 프로세스가 남아 새 규칙이 먹지 않았다. 반영은 서버 재연결이고, 재연결 뒤에는 실제 호출과 감사 로그로 새 동작을 확인한다.
9. **도구의 결함은 실업무 호출에서 드러난다.** 단위 테스트는 통과하고 있었는데, 실업무 유형별로 호출해 보니 결함이 하루에 여덟 건 나왔다. 업무 유형별 실측이 평가의 일부가 됐고, 결함마다 회귀 테스트를 추가했다.
