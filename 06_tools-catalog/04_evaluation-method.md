# 자작 도구 평가 방식

도구를 「다 만들었다」고 말하기 전에, 그리고 고칠 때마다 거친 평가 절차.

## 1. 기능 우선의 5점 척도

두 축을 따로 매긴다.

| 축 | 보는 것 |
|---|---|
| **기능** | 정확성(틀린 결과를 내지 않는가)·안전(막아야 할 것을 막는가)·주 용도를 실제로 해내는가 |
| **최적화** | 토큰·왕복 횟수·지연·출력 크기 |

**규칙** 기능 5점 유지가 먼저다. 최적화 5점은 기능을 깎지 않는 선에서만 추구한다. 최적화 수정 뒤에는 기능 회귀 여부를 **먼저** 확인하고 보고한다.

**Why** 사용자의 기준 — 「최적화까지 5점이면 좋지만 나는 기능 중심이다. 기능 5점을 유지하는 선에서 최적화 5점까지 가는 것은 좋다.」 그리고 가드를 강화하다 주 용도를 깎은 일이 실제로 있었다.

## 2. 독립 평가자 회차제

```
구현 ─▶ 독립 평가(만든 맥락을 모르는 에이전트) ─▶ 메인 재검증 ─▶ 수정 ─▶ 다음 회차 …
                                                                    └─▶ 정지 조건 충족 ─▶ 끝
```

| 단계 | 내용 |
|---|---|
| 평가자 | 구현 대화를 보지 않은 별도 에이전트. 코드·README·테스트만 준다. 내 결론은 주지 않는다 |
| 브리프에 넣는 것 | 평가 축과 척도, 「기능 회귀가 있으면 최적화 점수보다 먼저 보고」, 「범위 밖·의도된 제약은 감점하지 않는다(README·설계 근거를 볼 것)」, 상태를 바꾸는 호출 금지 여부 |
| 평가자의 산출 | 지적 목록(심각도·file:line·문제) + 축별 점수 + 잘된 점(유지할 것) + 「배포 전 필수 / 나중」 구분 |
| 메인 재검증 | 지적마다 코드를 읽거나 직접 실행해 ✅확인 / ⚠오탐 / 미검증을 붙인다. 오탐을 걸러 낸 뒤에만 사용자에게 전달한다 |
| 수정 | 확인된 지적만 고친다. 고친 지적은 회귀 테스트로 남긴다 |
| 회차 기록 | 회차마다 점수·남은 지적·수정 요지를 문서에 남긴다 |

실제로는 도구 하나에 아홉 회차가 돌았다.

### 정지 조건

- 기능·최적화 모두 5점, 또는
- 남은 지적이 전부 「그럴 수도 있음(PLAUSIBLE)」·심각도 낮음·자원 한도 문제로 묶이면 **멈추고 README 「알려진 한계」로 옮긴다.**

**Why** 평가 루프는 끝이 없다. 사용자의 주의 — 「여러 번 검증·작업하는데 본질을 잃으면 안 된다.」

### 평가에 쓰는 모델

- 가장 비싼 모델의 독립 평가는 사용자가 명시할 때만 한다(예상 토큰을 함께 제시).
- 먼저 메인이 정답 사례·재현율로 검증한다. 그것으로 충분하면 독립 평가를 덧붙이지 않는다.
- 다른 모델의 결과를 최상위 모델로 자동 재평가하지 않는다.

## 3. 실사용 재생 회귀

**수정 회차마다 가장 먼저 돌린다.**

| 도구 | 재생 재료 | 통과 기준 |
|---|---|---|
| E2E 도구 | 시나리오·흐름 파일의 SQL, 감사 로그의 조회 기록 | 회귀 0 |
| 참조 조회 도구 | 표본 대상의 단어 검색 대비 재현율 | 미해명 누락 0 |

**Why** 테스트는 전부 통과하는데 어제까지 되던 업무 호출이 막히는 일이 있었다. 단위 테스트는 가드가 「막아야 할 것」을 보지만, 실사용 재생은 「막으면 안 되는 것」을 본다.

감사 로그를 처음부터 재생 가능한 형태로 남겨야 한다(값은 가리되 구조는 유지).

### 안전장치는 누수 입력을 실제로 넣어 본다

구현 에이전트의 「차단됨」 보고를 그대로 믿지 않는다. 밤새 구현된 안전장치에 우회가 있었는데(여러 문장을 이어 붙이면 가드가 사라졌다) 보고는 「롤백했다」였다. 독립 리뷰가 잡았고, 수정 뒤에는 메인이 그 누수 입력을 실제 도구로 실행해 거부되는 것을 확인했다.

### 남은 마찰 — 평가 실행이 사용 로그에 섞인다

평가·수정 에이전트가 도구를 호출하면 그 기록이 「실사용 측정 로그」에 섞인다. 일주일에 예닐곱 번 손으로 걸러 냈고 근본 해결은 하지 못했다. **처음부터 평가 실행과 실사용을 구분하는 표지(환경변수·별도 로그 파일)를 도구에 넣어 두는 것이 좋다.**

## 4. 효용 평가 — 「쓸모 있는가」는 따로 본다

품질 검토와 별개로 업무 효용을 등급(하/중/상)으로 매긴다.

**「상」의 기준을 먼저 정한다**(예):

| 기준 | 내용 | 판정 방법 |
|---|---|---|
| 범위 | 업무 유형 N개 중 대부분에서 「요청 한 문장만 받고 준비 → 실행 → 판정 → 기록까지, 도구 밖으로 빠지지 않고」 끝낸다 | 유형별 1회 실제 실행 |
| 개입 | 회차당 사용자 개입 0~1회 | 실행 기록의 개입 횟수 |
| 추가 비용 | 새 케이스 추가가 설정·시나리오 파일만으로 된다(코어 수정 없이) | 새 유형 1건을 실제로 추가해 본다 |
| 확산 | 다른 사람이 15분 안에 설치하고, 남이 만든 데이터로도 실행된다 | 설치 절차 실측 또는 대리 판정 |

**표본을 센다** — 하루 치 일일노트의 「실행·실측」 줄에서 「테스트 묶음 중 도구로 끝낸 비율」을 센다. 표본이 하루·한 명이면 참고값이라고 적는다.

**막는 것을 분류한다** — 「안 되는」 유형마다 원인이 **제약**(기능은 있는데 가드가 거부)인지 **미구현**인지 가른다. 제약이 많으면 기능을 더 만들 것이 아니라 가드를 풀어야 한다.

## 5. 중간 평가 문서

도구가 여러 개가 되면 한 문서에 나란히 놓고 본다.

| 절 | 내용 |
|---|---|
| 한눈에 | 도구별 성숙도(별점)·실제 업무 효용·비용과 부담·한 줄 평가 |
| 수치 | 감사 로그 건수(일별), 사용 로그 횟수, 코드·테스트 줄 수 |
| 도구별 | 좋은 점(실제 사례) / 약한 점 / 결론(더 넣지 않는다·동결·분할·측정 유지) |
| 전체 소견 | 방향이 맞는가, 도구에 쓰는 시간이 업무를 앞지르지 않는가 |
| 다음 판정 | 도구별 판정 기준과 날짜 |

**실제 소견의 한 줄** — 「반복되는 약점은 도구보다 위임 결과의 검증이다. 부재형 결론은 코드를 열어 반증한 뒤에만 전달한다.」

## 6. 평가 루프 중의 커밋

- PR을 올린 뒤의 평가·수정 회차마다 커밋하지 않는다. 작업 트리에 모아 두었다가 루프가 끝나면 **커밋 1개**로 올린다.
- 주간 패치도 같다. 한 주 치를 한 번에.

**Why** 평가 회차마다 커밋을 올려 리뷰어 알림과 커밋 노이즈를 만들었다.

## 7. 다른 사람의 도구

팀원이 만든 도구는 이 절차로 평가하지 않는다.

- **아이디어(착안·쓰임새) 수준으로만 평가한다.** 세부 결함의 보완은 작성자의 몫이다.
- 리뷰 요청이 「승인해 달라」면 막을 만한 **보안·파괴 위험**과 「틀린 결과로 안심시키는 것」만 한두 줄로 확인한다.
- 코드와 맞고 반대 의견이 없으면 댓글 초안을 만들지 않는다. 내용 요약과 「문제 없음」 한 줄만 사용자에게 보고한다.
- 승인 여부는 사용자가 직접 판단한다.

**Why** 에이전트가 찾아낸 결함 목록을 그대로 동료에게 보내는 것은 리뷰가 아니라 부담이다.
