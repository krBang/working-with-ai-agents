# 개발 환경 E2E 자동화 도구(MCP + 스킬)

> 코드는 싣지 않는다. 풀려던 문제, 설계 원칙, 사용 흐름, 평가 경위, 교훈만 남긴다.

## 1. 풀려던 문제

- 개발 환경 테스트를 매번 셸 + DB 드라이버 + HTTP 호출로 조립했다. 토큰 발급, 한글 본문 인코딩, 띄운 서버 끄기 같은 **같은 실수가 반복**됐다.
- 테스트 케이스 실행의 가장 긴 구간(화면에서 테스트 데이터를 만드는 일)을 사람이 했다.
- 목표: **테스트 케이스만 주면** 준비 → 실행 → 판정 → 기록까지 에이전트가 끝낸다.

## 2. 지키는 것은 셋뿐

| 지키는 것 | 방법 |
|---|---|
| **개발 환경 전용 접속** | DB 호스트·API 호스트·로컬 프로필이 가리키는 DB 호스트를 검사해 운영을 차단한다. 접속 뒤 실제 호스트도 다시 확인한다 |
| **비밀값 비노출** | 세션 키·토큰은 OS 자격 증명 저장소에 두고 프로세스 메모리에서만 쓴다. 어떤 결과·로그에도 없다. 사용자가 터미널에서 등록한다 |
| **결과 값 마스킹** | 테스트 계정에도 팀원 본인의 이름·연락처가 있다. 결과와 감사 로그 양쪽에서 가린다 |

그 밖의 제약은 **효용을 위해 풀었다.** 처음에는 「내 테스트 계정의 건만」「허용 경로만」「등록된 배치만」 같은 가드가 많았는데, 평가에서 이것이 도구를 못 쓰게 하는 주원인으로 드러났다(아래 5절).

## 3. 도구군

| 묶음 | 도구 | 요지 |
|---|---|---|
| 조회 | 자유 조회 · 한 건의 상태 스냅샷 · 조건 대기 | 읽기 전용 연결. 스냅샷은 한 건에 딸린 테이블들을 섹션별로 한 번에 뜬다 — 테스트 전후 비교의 기본 단위 |
| 항상 롤백 | 다중 문장 스크립트 · 두 프로시저 결과 비교 | 한 트랜잭션으로 돌리고 **항상 ROLLBACK**. 미반영 프로시저를 임시 사본으로 만들어 시험하거나, 같은 입력 조합에서 현행과 개정본의 결과 차이를 본다 |
| 변경 | 단일 쓰기 · 등록부의 프로시저 호출 · API 호출(로컬 서버/개발 배포본) · 로컬 배치 실행 · 시나리오 실행 | 감사 로그를 남기고, 커밋된 쓰기는 되돌리기 정보를 함께 남긴다 |
| 로컬 프로세스 | 서버 기동 · 상태 · 로그 · 종료 | 종료는 이 도구가 기록한 프로세스만. 로그는 오류 줄 + 스택 앞부분만 |
| 반영 전 점검 | 프로시저 반영 점검 | 파일 ↔ 환경의 정의·시그니처·참조 객체 권한을 대조한다 |
| TC 흐름 | 흐름 목록 · 시작 · 다음 · 상태 · 리포트 | 화면이 낀 테스트 케이스를 단계로 실행한다(아래 4절) |
| 감사 | 감사 목록 · 되돌리기 | 커밋된 쓰기의 역방향 문장 실행(기본 키가 있는 테이블만) |
| 점검 | 설정 점검 | 설정·연결 상태만 돌려준다(값 없음). 설치 합격 기준이 된다 |

### 상태 변경의 공통 규칙

1. **한 번 호출로 실행한다.** `dryRun`을 주면 실행하지 않고(쓰기·프로시저는 실행 후 롤백) 미리보기와 1회용 확인값을 준다. 확인값은 요청 내용의 해시에 묶여 있어, 미리보기와 똑같은 요청에만 쓸 수 있다.
2. **대상을 거부하지 않고 표시한다.** 「내 테스트 계정의 건인가」를 결과에 표시만 한다. 남이 만든 검체·과거 건·식별 번호가 없는 API도 된다.
3. 모든 실행과 미리보기를 감사 로그에 남긴다. 조회 기록은 별도 파일에 쌓고 크기로 회전한다(상태 변경 기록은 되돌리기에 쓰이므로 회전하지 않는다).
4. **실패하면 재시도하지 말고 스냅샷으로 확인한다.**

### 마스킹의 범위와 한계

- 결과의 개인정보 열, 감사 로그 SQL의 리터럴(개인정보 컬럼에 비교하는 값, 개인정보 열 자리의 INSERT 값)을 가린다. 열 매핑을 못 하면 그 문장의 리터럴을 전부 가린다(fail-closed).
- 가리지 못하는 형태(위치 인자 호출, 리터럴이 왼쪽에 오는 비교, 동적 SQL 안의 값 등)를 README에 **한계로 명시**한다.

## 4. 화면이 낀 테스트 케이스의 흐름 실행

| 개념 | 내용 |
|---|---|
| 흐름 파일 | 테스트 케이스 묶음을 YAML로 적는다. 단계 = 화면 블록 · 조회 · 대기 · API · 배치 · 판정 |
| 화면 블록 라이브러리 | 「생성」「등록」「취소」 같은 화면 조작을 블록 파일 하나씩으로 둔다. 흐름은 이름으로 부른다 |
| 역할 분담 | **비화면 단계는 도구가 연속 실행**하고, 화면 단계만 에이전트가 브라우저 자동화로 수행한 뒤 결과(화면값)를 도구에 보고한다 |
| 화면값 대조 | 금액·건수·문구·노출 여부를 형에 맞게 정규화해 DB 값과 대조한다 |
| 실패 분류 | 여섯 범주 — 요소(화면) · 전제 조건 · 가드 · 서버 · 판정 · 환경. 서버 범주면 서버 로그의 오류를 붙인다 |
| 재개 | 실패 지점부터 다시 시작한다. 같은 시간대에 같은 건이 둘 이상이면 채택하지 않는다(중복 생성 방지) |
| 사람 개입(handoff) | 사람이 해야 하는 단계(외부 인증 창 등)는 명시적으로 넘기고 개입 횟수를 센다 |
| 전제 점검 | 테스트 수단의 잔액 같은 전제를 실행 전에 확인한다 |
| 계층 인식 실행 | 단계 종류마다 계층(화면 / 데이터 / 서버·배치)을 두고, 계층별로 테스트 케이스를 모아 실행한다. 조건에 맞는 건을 전부 집어 가는 배치는 케이스별로 돌리지 않고 **모아서 한 번** |
| 표류 점검 | 블록이 기대하는 화면 문구가 UI 레포에 아직 남아 있는지 린트한다 |
| 리포트 | PR 본문용·TC 문서용·JSON. 마스킹을 다시 적용한다 |

화면 조작 자체는 브라우저 자동화가 연결된 세션이 한다. 테스트 실행의 승인 기준은 [승인 경계 8](../01_principles/02_approval-boundary.md).

## 5. 평가 경위 — 「중」에서 「상」으로

1. **1차 독립 품질 검토** — 판정 REVISE. 치명 2건(함수 이름을 따옴표로 감싸면 거부 목록을 우회 / 속성 표기로 행 전체 출력 차단을 우회), 높음 3건(다른 표기법의 응답 키가 마스킹을 빠져나감 / 대상 가드가 한 종류의 키만 봄 / 로컬 프로필의 DB 점검이 한 종류의 접속 문자열만 해석).
2. **메인의 재검증 표** — 지적마다 코드를 읽거나 가드를 직접 실행해 ✅확인 / ⚠오탐 / 미검증을 붙였다.
3. **효용 평가 「중」** — 여덟 가지 업무 유형 중 끝까지 되는 것은 둘. 하루 표본에서 도구로 끝낸 테스트 묶음은 다섯 중 하나.
4. **상향 방안** — 세 묶음으로 나눴다.
   - A. 제약 완화(코어 로직 추가 없이 가드 분기·설정만)
   - B. 기능 추가(항상 롤백 스크립트, 결과 비교, 흐름 실행기)
   - C. 확산(설치 한 명령, 새 TC 추가를 초안 자동 생성으로)
5. **「상」의 기준**을 먼저 정했다 → [평가 방식](04_evaluation-method.md)
6. **부재 중 구현** — 사용자가 「권고안 기준으로 진행하라」고 하고 자리를 비운 밤에 단위별로 구현하고 결정 기록을 남겼다(채택한 안 · 다른 선택지 · 설계와 다르게 정한 것 · 다음 날 할 일).
7. **슬림화** — 엔진이 만 줄, 테스트가 구천 줄 가까이 불었다. 기능 추가를 동결하고 줄였다.
8. **독립 평가 아홉 차례** 끝에 기능·최적화 만점. 실사용 재생 회귀 0.

## 6. 교훈

| 교훈 | 계기 |
|---|---|
| **효용을 막는 것은 미구현보다 제약이다** | 「안 되는」 유형 여섯 중 넷은 기능이 이미 있는데 가드가 거부하고 있었다 |
| **기존 수단보다 약한 구간이 있으면 그 구간에서 안 쓰인다** | 도구가 계획 확인·DDL·다건 조회를 못 해서, 정작 어려운 테스트는 전부 도구 밖(셸)에서 했다. 「각자 하던 것은 전부 되고 더 편하게」가 완화 기준이 됐다 |
| 가드는 환경의 실제 위험에 맞춘다 | 개발 환경에는 실고객 데이터가 없고 팀원은 이미 DB·API를 직접 쓴다. 그래서 안전 가드 추가는 다루지 않기로 했고 「가드 추가 제안 금지」를 메모리에 적었다 |
| 호출 수 감소는 부수 효과다 | 주 효과는 쓸 수 있는 상황의 폭과 반복 실수 제거였다 |
| 도구가 업무를 앞지르면 멈춘다 | 감사 로그의 대부분이 도구 자체의 개발·시험 호출이었다. 「매일 쓰는 조회·점검」과 「무거운 흐름 엔진」을 나누고 기능을 동결했다 |
| 화면 자동화는 깨지기 쉽다 | 하루에 화면 문구 여섯 곳이 어긋났다. 안정된 테스트 케이스만 남기고, 고정 스크립트로 굳힐지는 안정된 뒤에 판단한다 |
| 환경은 초기화된다 | 개발 DB를 현행화하면서 검체와 반영해 둔 프로시저가 사라졌다. 반영 점검 도구가 이것을 바로 잡아냈다 |
| 진행 중 실행과 정의 변경은 충돌한다 | 블록을 고치면 진행 중이던 실행을 재개할 수 없다(해시 불일치). 고치기 전에 실행을 끝낸다 |
| 가드 강화가 주 용도를 깎으면 그것이 최우선 결함이다 | 마스킹을 강화하다 프로시저의 출력 값까지 가려 결과 비교가 안 됐다 |
| 「수단 없음」이라는 위임 결과는 반증한다 | 「그 상태로 만들 방법이 없다」는 결론이 올라왔는데 다른 API 조합으로 가능했다 |
| 자동 재적재는 편하지만 부작용이 있다 | 재적재 뒤 예외 클래스가 달라져 「거부」가 도구 오류로 올라왔다. 그리고 재적재되는 도구에는 운영 가드를 얹지 않는다 |

## 7. 팀 배포

- 문서 레포를 로컬 경로 플러그인 마켓으로 쓴다. 설치 15분 절차(패키지 → 초기화 명령 → 비밀 등록 → 플러그인 등록 → 설정 점검 → 첫 시나리오)를 README에 표로 둔다.
- 계정과 키는 **각자 본인 것**이다. 공용 계정은 두지 않는다.
- 설정 점검 도구의 출력이 「설치 완료」의 합격 기준이다.
- 팀원 실사용 참여 없이 평가해야 할 때는 팀원의 코드·PR을 근거로 대리 판정했다(그 사실을 명시).
