# 레포 횡단 정적 참조 조회 도구(CLI + 스킬)

> 코드는 싣지 않는다. 풀려던 문제, 설계 원칙, 사용 흐름, 평가 방식, 교훈만 남긴다.

## 1. 풀려던 문제

「이 테이블을 누가 읽고 쓰나」「이 루틴을 누가 부르나」에 답하려고 매번 여러 레포를 검색했다. 검색은 두 가지로 틀렸다.

- **놓친다** — ORM `save()`, 매퍼의 포함 조각, 애플리케이션의 프로시저 호출 API, 운영 브랜치에만 남은 호출부.
- **섞인다** — 주석·로그 메시지 속 이름, 다른 스키마의 같은 이름, 여러 worktree의 중복 히트.

영향도 분석의 **출발 목록**을 빠르고 빠짐없이 얻는 것이 목표다. 영향 여부의 판단은 하지 않는다.

## 2. 무엇을 보나

실행도 DB 접속도 없다. 레포 소스만 읽는다. 세 레이어를 **테이블·루틴 단위**로 본다.

| 레이어 | 뽑는 것 |
|---|---|
| 저장 프로시저(.sql) | 루틴 정의, 호출문, 식 안의 함수 호출, 테이블 쓰기(종류별)·읽기 |
| SQL 매퍼(.xml) | 문장 id별 테이블 읽기/쓰기·루틴 호출. 포함 조각을 펼쳐 **쓰는 문장 기준**으로 가른다 |
| 애플리케이션 코드 | ORM 엔티티 매핑 위치(「쓰기 가능 경로」 — 읽기 전용이라고 단정하지 않는다), 네이티브 SQL 문자열, 프로시저 호출 API |

종류: 읽기 · 쓰기(INSERT/UPDATE/DELETE/MERGE/TRUNCATE/DDL로 세분) · 호출 · 정의 · 엔티티 · 참조.
확실도: 확정 · 스키마 미한정 · 추정 · 추정(문자열 SQL) · 쓰기 가능 경로.

## 3. 설계 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| git 객체에서 읽는다 | 기준 ref(통합 브랜치)를 체크아웃 상태와 무관하게 git 객체에서 직접 읽는다 | 작업 폴더가 어느 브랜치에 있든 결과가 같고, worktree가 여러 개여도 레포당 한 벌만 센다 |
| 운영 브랜치를 함께 대조한다 | 기본 실행이 「운영 브랜치에만 있음 N건」을 덧붙인다. 합집합 한 목록이 필요하면 옵션으로 | 통합 브랜치에서 바뀐 호출부가 운영에는 살아 있다 |
| 미커밋 작업물도 볼 수 있다 | 특정 작업 폴더만 워킹트리로 즉석 스캔하는 옵션 | 작업 중인 새 테이블은 기준 ref에 없어 0건이 나온다 |
| 결과에 **소스 줄 본문을 싣지 않는다** | 위치·종류·확실도만. 내용은 파일마다 붙는 「열기」 명령으로 연다 | 헤더 주석의 연락처·설정 비밀이 대화로 나가는 것을 막고, 출력 크기를 줄인다 |
| 출력이 크면 접는다 | 히트가 많으면 파일별 요약, 더 많으면 레포별 한 줄. 좁히는 옵션을 안내한다 | 핫한 테이블은 히트가 수백 건이다 |
| 메시지 속 이름은 호출이 아니다 | 로그·예외·사용자 언어 문자열 속 이름은 행에서 빼고 꼬리에 건수만 | 오탐의 최대 원천이었다 |
| 문제를 숨기지 않는다 | 스캔하지 못한 레포, 매퍼로 인식 못 한 파일, 오래된 fetch 시각을 머리에 경고로 낸다. 자동 fetch는 하지 않는다 | 결과가 불완전할 수 있다는 사실이 결과의 일부다 |
| **0건의 고정 문구** | 0건이면 「범위 밖 목록 + 다음에 볼 곳」을 함께 낸다 | 0건은 부재의 증거가 아니다 |
| 커밋 해시 단위 캐시 | 레포@커밋 해시별 색인 캐시. ref가 안 바뀌면 다시 읽지 않는다 | 캐시가 있으면 1초 안쪽 |
| 호출 로그 | 호출마다 대상·ref·히트 수·소요를 한 줄 남긴다 | 2주 사용량으로 다음 단계를 정한다 |

## 4. 왜 MCP가 아니라 CLI + 스킬인가

「MCP로 바꾸자」는 제안이 반복해서 나왔다. README에 이 절을 두고 「다시 나오면 여기부터 본다」고 적었다.

- 설치 0 — 레포를 받으면 바로 실행된다. MCP는 서버 등록·의존성 설치·재시작이 필요하다.
- 의존성 0 — 표준 라이브러리만 쓴다.
- **상시 컨텍스트 비용이 없다** — MCP 도구 설명은 매 세션 로드되지만, 스킬은 description 한 줄만 로드되고 필요할 때 본문을 읽는다.
- 사람도 같은 CLI를 터미널에서 그대로 쓴다.
- 플러그인은 배포 수단일 뿐 구조는 그대로다.

메모리에도 「CLI + 스킬 유지 — MCP 전환 재제안 금지」를 적어 뒀다.

## 5. 스킬이 맡는 것

스킬(SKILL.md)은 CLI를 「언제 쓰고 언제 쓰지 않는지」를 에이전트에게 알려 준다.

| 상황 | 도구 |
|---|---|
| 「이 테이블을 누가 읽고 쓰나」「이 루틴의 호출부」 | **이 도구** |
| 컬럼·테이블이 실존하는가 | 스키마 조회(사용처 0건을 「없음」으로 읽지 않는다) |
| 실제 데이터 확인 · 루틴 실행 | 개발 환경 도구 |
| 애플리케이션 메서드의 호출 추적 | 언어 서버의 참조 찾기 |
| 영향 여부의 판단·설계 | 사람과 설계 검토 에이전트 — 이 결과는 입력 자료일 뿐 |
| 「되나/막히나」(조건·분기·코드값 판단) | **대상 밖.** 정의 위치까지만 얻고 본문을 읽는다 |

질문 유형별 신뢰 범위도 표로 준다 — 루틴 호출부는 전수 목록으로, 테이블 쓰기 주체는 전수 후보로(엔티티의 실제 저장 주체는 한 번 더 확인), 테이블 읽기는 전수 출발 목록으로, 조건·분기 판단에는 쓰지 않는다.

## 6. 검증 — 재현율 점검

표본 대상(참조가 많은 테이블·루틴 수십 개)마다 단어 단위 검색 결과와 이 도구의 히트를 같은 ref·같은 레포에서 대조한다. 검색만 찾은 줄마다 이유(다른 스키마, 메시지 문자열, DDL 설명문 등)를 붙이고, **이유를 못 붙인 「미해명」이 한 건이라도 있으면 실패**다.

독립 평가에서 기능·최적화 만점을 받은 뒤 플러그인으로 배포했다.

## 7. 교훈

| 교훈 | 계기 |
|---|---|
| 좋은 도구도 떠올리지 않으면 안 쓴다 | 결과는 검색보다 확실히 나았는데 측정을 시작한 첫 며칠 동안 호출이 네 번뿐이었다. 「누가 부르나·영향도」 키워드에서 이 도구를 떠올리게 하는 장치(입력 훅)를 검토했다 |
| 확장은 사용량을 보고 정한다 | 「주 N회 미만이면 다음 단계로 가지 않는다」는 기준과 판정일을 미리 정했다 |
| 「영향 있나」는 결국 열어 읽어야 한다 | 위치 목록으로는 분기를 판정할 수 없다. 도구가 답하는 질문과 답하지 않는 질문을 문서 맨 위에 적는다 |
| 반복되는 재제안은 문서로 막는다 | 같은 구조 변경 제안이 세션마다 다시 나왔다. 근거 절과 메모리의 「재제안 금지」로 막았다 |
| 질문이 다른 도구와 역할을 가른다 | 이 도구는 객체 이름에서 출발하는 고치기 전 설계·분석 단계용이다. 변경(diff)에서 출발하는 PR 직전 점검은 따로 둔다 |
