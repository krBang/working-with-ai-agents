# 티켓 발번·조회 자동화 도구(MCP)

> 코드는 싣지 않는다. 풀려던 문제, 설계 원칙, 사용 흐름, 교훈만 남긴다.
> 저작: 플로우 호출 도구(인증 캐시 포함)·운영 규칙·안내문은 직접 만들었고, MCP 서버 계층은 팀원이 붙인 것을 함께 다듬었다.

## 1. 풀려던 문제

과제 번호를 공유 스프레드시트에서 손으로 채번했다. 번호를 받아야 브랜치를 만들 수 있어서, 작업을 시작할 때마다 사람이 시트를 열어야 했다. 일일 업무 보고를 만들 때도 시트의 과제 이름·상태를 손으로 대조했다.

## 2. 구조

```
에이전트 ── MCP 도구 ──▶ 업무 자동화 플로우(HTTP 트리거) ──▶ 공유 스프레드시트
              │
              └─ 조직 계정 토큰(사용자가 터미널에서 1회 로그인, OS 보호 저장소에 캐시)
```

- 시트에 직접 쓰지 않는다. 조직의 업무 자동화 서비스에 만든 플로우를 **조직 계정 토큰으로 호출**한다(서명 주소가 박힌 웹훅이 아니다 — 주소는 비밀이 아니고 토큰이 필수다).
- 응답은 동기식이다. 발번이면 번호·시트 행·브랜치 이름을 바로 돌려준다.

| 도구 | 승인 | 하는 일 |
|---|---|---|
| 내 정보 · 담당자 설정 | 없음 | 저장된 담당자 이름 확인·설정 |
| 목록 조회 | 없음(허용 목록) | 기간·상태로 조회. 한 번에 최대 N건이라 잘리면 기간을 나눠 다시 조회한다 |
| 발번 | **매번** | 번호가 실제로 소모된다 |
| 수정 | **매번** | 상태·기한·담당·비고 |

## 3. 설계 원칙

| 원칙 | 이유 |
|---|---|
| 발번 전에 **제목·설명을 먼저 제안**하고 승인받는다 | 호출 한 번이 시트에 행 하나를 만든다. 시험 호출도 실제 번호를 소모했다 |
| 실패·지연 시 **재시도하지 않고 목록으로 확인**한다 | 응답만 늦고 발번은 됐을 수 있다. 재시도는 중복 발번이 된다 |
| 잘못 발번한 건은 행 삭제가 아니라 **상태값으로 폐기**한다 | 번호 매김이 마지막 행 기준이라, 행을 지우면 같은 번호가 다시 나온다 |
| 서버 안내문(instructions)에 사용 규칙을 적는다 | 도구를 쓰는 모든 세션이 같은 규칙을 본다 |
| 입력 형식은 훅으로 강제한다 | 「제목·설명은 각각 한 줄로 짧게」가 문구로는 안 지켜졌다. 실행 전 훅이 줄바꿈과 길이 상한을 검사해 거부한다 |
| 인증은 사람이, 도구는 캐시만 | 최초 1회 로그인은 자동화할 수 없다(조직 정책). 백그라운드 프로세스에서는 로그인 창이 뜨지 않아 기기 코드 방식을 쓴다 |
| 바꿀 값은 한 번의 호출로 묶는다 | 수정할 때마다 비고에 변경 이력이 붙어 길어졌다 |

## 4. 겪은 함정

- **한글 본문 인코딩** — 셸 인자로 한글을 보내면 로컬 코드 페이지로 깨져 요청이 거부됐다. UTF-8 파일로 만들어 파일로 보낸다.
- **브랜치 이름 대소문자** — 응답의 브랜치 이름은 소문자인데 레포 관례는 대문자였다. 안내문에 「관례대로 바꿔 안내」를 적었다.
- **서버 안내문과 사용자 기준의 충돌** — 안내문은 「PR을 만들면 완료로 바꿀지 묻는다」였는데 사용자의 기준은 「운영에 나가면 완료」였다. 사용자 기준이 우선이고, 메모리에 「안내문보다 이 규칙이 우선」을 적었다. 안내문을 고칠 수 있으면 고친다.
- **비고에 전체 주소를 넣지 않는다** — 너무 길다. 「레포 약칭 + 번호」만.
- **로그인 만료** — 만료되면 사용자가 터미널에서 다시 로그인해야 한다. 도구는 그 명령만 안내한다.

## 5. 평가

「범위가 좁고, 규칙은 가드가 강제하고, 응답이 짧아 대화 소음이 없다. 매일 쓴다. **완성형 — 더 넣지 않는다.**」

세 도구 중 가장 작고 가장 자주 쓰였다. 처음에는 스킬(CLI 호출 절차)로 만들었는데, 팀원이 MCP 서버를 붙였고 그쪽으로 일원화했다. MCP에서는 목록 조회(허용)·발번·수정(매번 승인)에 서로 다른 승인 수준을 도구 이름 단위로 걸 수 있다.

## 6. 옮겨 심을 때

- 채번 대장이 무엇이든(시트·이슈 트래커) 「조회는 무승인, 생성·수정은 매번 승인, 실패 시 재시도 대신 조회」 세 가지는 그대로 쓸 수 있다.
- 이슈 트래커에 공식 API가 있으면 플로우 계층은 필요 없다.
- 생성 도구에는 입력 형식 훅을 같이 거는 설계를 참고해 자기 환경에 만든다. → [가드 훅 설계](../05_hooks-and-scripts/README.md)
