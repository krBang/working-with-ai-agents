# 쿼리 전달 형식

사용자가 DB 클라이언트에 붙여 직접 실행할 쿼리를 건넬 때의 형식. 운영 쿼리의 안전 규칙은 [운영 조회 루프](../02_procedures/06_prod-query-loop.md)에 있고, 여기는 「어떻게 건네는가」다.

## 1. 항상 그대로 실행 가능한 전체로

**규칙** 쿼리는 복사해서 바로 실행되는 전체 형태로 준다. 「앞의 CTE까지는 동일」「마지막 SELECT만 교체」 같은 축약 전달을 하지 않는다. 같은 드라이빙 집합을 쓰는 변형이라도 `WITH`부터 끝까지 매번 다시 적는다. 문서에 넣을 때도 독자가 섹션 하나만 보고 실행할 수 있어야 한다.

**Why** 사용자는 받은 쿼리를 그대로 붙여 실행한다. 조각을 이어 붙이다 누락·오타가 생기면 결과가 틀리는데 원인을 찾기 어렵다.

## 2. 확인은 작게, 최종은 전체로

**규칙** 범위 정의 → 건수 검증 쿼리 하나 → 사용자 확인 → **확정되면 전체본**으로 다시 준다. 수정이 생기면 바뀐 조건만 먼저 주고 건수를 확인한다. 큰 쿼리 뭉치를 매번 통째로 다시 던지지도, 확정 뒤에 「이 부분만 바꿔 끼우세요」라고 조각을 주지도 않는다.

**Why** 같은 날 전체본을 세 번 연속 다시 던져 혼란을 줬고, 반대로 확정 뒤에 조각을 줬다가 「이제는 전체로 줘야지」라는 말을 들었다.

## 3. 대상 범위는 업무 조건으로

**규칙** 대상을 정할 때 파생 데이터의 존재(뒤 단계 테이블과의 조인)로 거르지 않는다. 업무 조건(완료 일자가 채워짐 + 결과 상태가 정상 등)으로 정의한다.

**Why** 건수가 예상과 달라 뒤 단계 테이블과 조인해 맞췄더니, 「그건 뒤 단계까지 만들어진 건으로 구분한 것」이었다. 건수가 맞는 것과 범위가 옳은 것은 다르다.

## 4. 화면에 전부 보여 준다

**규칙** 실행을 부탁하는 쿼리는 문서에만 넣지 않고 **대화 본문에 코드블록으로 전부** 싣는다. 여러 단계면 실행 순서대로 「1) … 2) …」 라벨 + 빈 줄 + 블록. 일부만 인라인으로 보여 주지 않는다.

**Why** 두 단계 중 하나를 문서 절 번호로만 안내했더니, 사용자는 대화에 보인 한 줄만 실행했다 — 「눈에 안 보여 주니까 안 했잖아」.

## 5. 형식

| 규칙 | 이유(Why) |
|---|---|
| 설명 문장과 코드블록 사이, 쿼리와 쿼리 사이에 **빈 줄 한두 줄** | 터미널에서 드래그 복사할 때 설명 줄이 딸려 온다 |
| 여러 문장을 한 번에 줄 때는 문장마다 `-- Q1 …` 주석 머리 + 빈 줄 구분 | 클라이언트의 「커서 위치 문장 실행」으로 하나씩 돌릴 수 있다 |
| 실행할 쿼리는 **클립보드에도** 넣는다(대화에도 본문은 그대로 보여 준다) | 복사 단계를 없앤다. 일반 텍스트는 문자 깨짐이 없다 |
| 여러 단계를 한 트랜잭션으로 묶는 보정 스크립트는 맨 앞에 트랜잭션 시작, 맨 끝에 커밋과 롤백을 **둘 다** 적고 「정상이면 / 다르면」 주석을 단다 | 「자동 커밋을 끄고 실행하세요」라는 안내는 빠뜨리기 쉽다 |
| 프로시저 호출문은 사용자의 클라이언트 관례대로(예: 출력 파라미터 생략) | 관례와 다른 형태를 줬더니 매번 고쳐야 했다 |
| 판정의 축이 되는 구분 컬럼을 결과에 반드시 넣는다 | 빠져서 사용자가 전체 조회로 바꿔야 했다 |
| 어느 환경에서 돌리는지 한 줄로 못 박는다 | 개발/운영이 섞여 헷갈렸다 |
| 기존 실측 문서가 있으면 그 형태(CTE 구성·출력 컬럼·판정 기준 위치)를 따른다 | 「원래 쓰던 방식으로」 — 형태가 바뀌면 결과를 지난번과 대조할 수 없다 |

## 6. 개인정보

| 규칙 | 이유(Why) |
|---|---|
| 검증·실측 쿼리에는 개인정보 컬럼(이름·연락처·주소·회원 식별값)을 **처음부터 넣지 않는다** | 사용자가 직접 지워야 했다. 판정에 아무 기여도 하지 않는 컬럼이었다 |
| 식별은 키로 한다 | |
| 개인정보 축이 판정 대상이면 값이 아니라 길이·NULL 여부·앞 글자 마스킹 형태로 뽑는다 | |
| 사용자가 **요청한 추출 산출물**에는 이 규칙이 적용되지 않는다 | 요청받은 산출물은 요청한 컬럼 그대로 낸다 |

## 7. 운영 데이터의 화면 대조

운영 결함의 확인은 「쿼리로 화면 로직을 재현한 결과」까지로 판정한다. 실고객 데이터를 화면에서 열어 대조하자고 제안하지 않는다. 화면 최종 확인은 개발 환경 검체로만.

## 8. 보정 쿼리의 목표 값

보정·원복 쿼리를 줄 때는 「사용자가 말한 상태 이름 ↔ 쿼리의 코드값 ↔ 코드표 조회 결과」를 나란히 적는다. 처리자 칸에 넣는 식별값은 사용자 메모리에 적힌 것을 쓴다(코드 헤더의 작성자 표기와 다를 수 있다).

**Why** 사용자가 말한 상태와 다른 코드값을 같은 세션에서 반복해 넣었다.

## 9. 정본 템플릿이 있는 요청

사용자가 정본 쿼리 템플릿을 준 종류의 요청은 값만 바꿔서 준다. 개발 환경 검증·조인 재설계·컬럼 이름 변경을 하지 않는다. 템플릿에 없는 항목만 같은 형식으로 한 블록 덧붙이고 무엇을 덧붙였는지 한 줄 알린다.
