# 대신 쓰는 글 — 메시지·메일·공유 문서·가이드

에이전트가 사용자 이름으로 나갈 글을 쓸 때의 기준.

## 1. 메신저·메일의 톤

| 규칙 | 계기 |
|---|---|
| 날씨·계절 인사 같은 상투적 인사말을 넣지 않는다 | 초안의 계절 인사를 사용자가 싫어했다 |
| 늦은 연락은 과한 사과 대신 담백하게(「이제야 연락드립니다」) | 과한 사과·과한 감사를 뺀다 |
| 흐름은 인사 → 용건 → 요청. 메신저는 맺음 인사 없이 요청 문장으로 끝낸다(메일과 다르다) | 메신저에 메일식 맺음말을 붙였다 |
| 상대가 먼저 마무리 인사를 한 대화의 답장은 인사로 받아도 된다 | 예외를 사용자가 확인해 줬다 |
| 모르는 소속·직함·이름은 지어내지 않는다 | 팀 이름을 지어내 넣었다 |

사용자마다 다르다. 처음 몇 번의 교정을 메모리에 「대신 쓰는 메시지 톤」으로 모아 둔다.

## 2. 메일 초안은 처음부터 HTML로

**규칙** 메일 초안은 텍스트 코드블록이 아니라 HTML 파일로 임시 폴더에 만들어 브라우저에 띄운다. 제목 칸 + 본문 박스(전체 선택 → 복사 → 붙여넣기) 구성, 인라인 스타일, 표는 인라인 테두리. 화면 캡처가 있으면 크기를 줄여 본문에 넣는다(파일 첨부는 번거롭다).

**Why** 텍스트 초안은 메일 클라이언트에 붙이면 표와 서식이 무너진다. 두 번 연속 같은 지적을 받았다.

- 소속 표기는 **내부용과 외부용을 구분**한다(내부 메일은 팀 이름, 외부 메일은 회사 이름).
- 외부 메일은 담백하게. 우리 쪽 내부 사정(내 쪽 결함·기존 동작 설명)은 넣지 않는다.

## 3. 팀 공유 문서

**형식** 팀의 기존 공유 문서 관례를 따른다. 사용자가 「이런 말투가 좋다」고 짚어 준 표본 하나를 정해 둔다.

- 맨 위: 한 문장 개요
- 메타 불릿: 작업 일정, 관련 과제
- **현황**: 문제 상태를 구체적인 불편 사례와 함께
- 그다음 개발 내용 / 해결 사항 / 검증 / 일정

**무엇을 담을지의 기준은 하나다 — 팀원이 이것을 읽고 무언가를 하거나 판단하는가.** 아니면 뺀다.

| 뺀다(전부 「내가 헤매다 바로잡은 흔적」이다) | 담는다 |
|---|---|
| 내 측정 오류와 그 교정 | 남이 해야 할 일 |
| 내 가설과 그 가설이 틀린 경위 | 쓰면 안 되는 것과 그 이유 |
| 개발 환경 실증 ID, 실측 수치표, 디버깅 서사 | 건드리면 깨지는 것 |
| 그 파일을 만질 사람만 알면 되는 지엽적 주의 | 미결 항목과 소유자 |
| 검증해서 「문제 없음」이 나온 건 — 아예 적지 않는다 | |
| 내 판단 과정(대안을 검토하고 접은 경위) — 결론 한 줄만 | |

**Why** 건조한 변경 목록(1차)도, 서사형 성과 문서(2차)도 반려됐다. 팀은 애초에 그 실수를 하지 않았으므로 교정 과정은 그들에게 정보가 아니다. 검증 이력과 실측 근거는 개인 분석 문서와 쿼리 문서에 남긴다.

## 4. 다른 팀에 줄 가이드·회신

**규칙** 문장마다 두 가지를 본다 — ① 요청자가 물은 것에 답하는가 ② 내가 실측·코드로 확인한 사실인가. 둘 중 하나라도 아니면 뺀다.

- 요청받은 사용법만 담는다. 내 쪽 사정이나 후속 제안을 덧붙이지 않는다.
- 내부 용어(구현 수단의 이름)는 뺀다. 상대가 알 필요 없는 구현 세부다.
- **우리 몫이 아닌 후속 조치를 약속하지 않는다.** 다른 조직이 진행하는 확인을 「요청드리겠다」고 적지 않는다. 우리 데이터로 확인되는 사실까지만 쓰고 마무리한다.

**Why** 가이드에 「이 단계를 하면 저것이 생긴다」는 인과를 덧붙였는데 사실과 달랐다(앞 단계만으로 이미 생겼다). 회신에 「필요하면 그쪽에 확인을 요청하겠다」고 썼는데 그 확인은 다른 조직이 맡는 일이었다.

## 5. PR 제목·설명

- 내 작업 내용만 담백하게. 브랜치 운영 사정(다른 작업 제외·선반영)은 넣지 않는다.
- 세 블록 — 한 줄 요약 / 세부 사항 / 관련 이슈 — 에서 끝낸다. 생성 도구 서명을 붙이지 않는다.
- 목록 앞에 빈 줄, 평평한 한 단계 목록, 한 불릿은 한 줄. 올린 뒤 렌더링을 확인한다.

## 6. 발번용 제목·설명

- 제목 = 무엇을 고치는지 일반화한 한 구절(20~30자).
- 설명 = 구체 대상 한 줄(40~80자).
- 원인·수치·파일명·진행 방식은 넣지 않는다. 대안 버전을 덧붙이지 않는다.

**Why** 문단을 써 줬더니 「대장에서는 그게 설명급이다, 간단하게」.

## 7. 메신저에 붙일 API 안내

기본 주소를 한 줄로 따로 두고, 각 API는 메서드 + 경로 + 파라미터 이름만 쓴다. 전체 주소에 쿼리 문자열을 붙이면 메신저가 자동 링크로 바꾸면서 뒤쪽이 잘려 보인다.

## 8. 공유 채널에 애매한 내용

특정 요청 건의 데이터 보정처럼 그대로 쓰기 애매한 일은 일반화한 문구 대안을 한 줄로 함께 제시한다. 개인정보·식별값은 어떤 공유 문구에도 넣지 않는다.

## 9. 용어

- 사용자가 정한 이름으로 통일한다. 새 문서·커밋·PR·주석·메시지에 모두 적용하고, 원문을 인용할 때만 옛 이름을 쓴다.
- 이미 만든 폴더명·푸시된 커밋 메시지는 그대로 둔다(경로를 바꾸지 않는다).
- 총칭과 하위 항목을 같은 층에 놓지 않는다(총칭이 한 항목의 이름처럼 쓰이면 표가 애매해진다).
- 코드 쪽의 옛 표기는 코드의 관례다. 문서로 옮길 때 현재 용어로 바꾼다.
