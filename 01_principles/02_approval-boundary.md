# 승인 경계 — 로컬은 자율, 밖으로 나가는 행위만 승인

## 1. 경계선

| 구분 | 행위 | 처리 |
|---|---|---|
| 로컬 안에서 끝남 | 소스·문서 수정, 테스트·컴파일, 분석, 로컬 도구·설정 구성, 다른 에이전트와의 협업 진행 | 묻지 않고 진행하고 결과만 보고한다 |
| 상태가 밖으로 나감 | 커밋·푸시, PR 생성·수정·댓글·병합, 티켓 발번·수정, DB 쓰기, 외부 서비스 전송 | 대상과 범위에 대해 사용자 승인을 받는다 |

**Why** 협업 규칙·훅 신뢰 설정까지 전부 승인 대기로 걸려, 사용자가 자리를 비우면 아무 일도 진행되지 않을 뻔했다. 로컬 편집은 되돌릴 수 있지만 밖으로 나간 상태는 되돌리기 어렵다. 승인은 되돌리기 어려운 쪽에만 건다.

**적용**
- 사용자가 없을 때는 승인이 필요한 항목만 모아 두었다가 복귀 시 한 번에 보고한다.
- 위임 프롬프트와 다른 에이전트에게 보내는 요청에도 같은 기준을 적는다.
- 사전 승인 대신 사후 검증으로 품질을 지킨다: 구현 뒤 diff 요약·컴파일·변경별 시험 결과를 확인한다.

## 2. 이 경계는 세 번 움직였다

| 시기 | 규칙 | 바뀐 이유 |
|---|---|---|
| 초기 | 코드 수정은 한 줄이라도 구현 담당 에이전트에 위임, 수정·위임 전 반드시 승인 | 승인 없이 수정을 시작해 제지받았다. 구현과 검증을 분리하려는 의도 |
| 개편 | 1~2파일 소규모는 메인이 직접(수정 전 승인), 다중 파일·대형만 위임 | 열 줄 변경에 위임 왕복이 수 분 걸렸다 |
| 현재 | 로컬 수정은 승인 없이 진행, 밖으로 나가는 행위만 승인 | 승인 대기 때문에 부재 중 작업이 멈췄다 |

교훈: 승인 지점은 「위험이 실제로 생기는 곳」으로 계속 옮겨야 한다. 처음에는 넓게 잡더라도, 강제 수단(훅)이 생기면 문서상의 승인 요구는 줄인다.

## 3. 꼭 막을 것은 문서가 아니라 훅·권한으로

**규칙** 커밋·푸시 확인, 전체 스테이징 차단, 비밀 파일 차단, 운영 DB 직접 접속 차단은 권한 설정(`deny`/`ask`)과 실행 전 훅으로 강제한다. 막히면 우회하지 말고 사용자에게 알린다.

**Why** 지시문(CLAUDE.md·메모리)은 참고일 뿐 강제가 아니다. `ask` 규칙은 자동 모드에서도 묻는다. 문서 규칙과 훅을 이중으로 두면 문구를 놓쳐도 막힌다.

설계: [훅과 스크립트](../05_hooks-and-scripts/README.md)

## 4. 승인의 범위는 「그 묶음」까지

**규칙** 「확인해서 댓글 남겨 줘」 같은 일괄 허락은 그 묶음에만 유효하다. 새 요청 건으로 넓히지 않는다.

**Why** 한 번 받은 허락을 다음 건에도 적용해 공개 댓글을 사전 확인 없이 올렸고, 수정·삭제를 여러 번 했다.

## 5. 밖에 노출되는 글은 올리기 전에 초안을 보여 준다

**규칙** PR 제목·설명 수정, 다른 팀 PR의 댓글·답글은 before/after 초안을 보여 주고 승인받은 뒤 올린다. 정정 사유가 쌓일 것 같으면 모아서 한 번에 올린다. 사용자가 정할 설계 판단을 공개 댓글로 먼저 적지 않는다.

**Why** PR은 리뷰어에게 노출되는 산출물이다. 고칠 때마다 알림이 가고, 리뷰 중인 내용이 발밑에서 바뀐다.

## 6. 매 호출 승인 도구에서 「다시 묻지 않기」를 고르지 않는다

**규칙** 티켓 발번·수정처럼 매 호출 승인이 전제인 도구는 영구 허용으로 바꾸지 않는다.

**Why** 한 번의 선택이 영구 allow가 되면 승인 모델 전체가 사라진다. 승인 피로는 도구 쪽 가드로 줄이고, 에이전트가 호출 횟수를 줄인다. → [승인 호출 묶기](../02_procedures/11_approval-batching-and-request-triage.md)

## 7. 승인 대기 건은 한 번 물었으면 다시 꺼내지 않는다

**규칙** 사용자가 다른 일을 시키는 중에 답변 끝마다 「~는 아직 승인 대기」를 붙이지 않는다. 상태 줄에 「대기」로만 둔다.

**Why** 같은 승인 대기를 다섯 번 반복해 꺼내, 사용자가 정할 일을 재촉하는 꼴이 됐다.

## 8. 실행 지시가 곧 그 회차의 승인인 경우

**규칙** 사용자가 테스트 케이스 실행을 지시했다면, 그 회차에 포함된 개발 환경 테스트 거래·접수 같은 행위는 따로 묻지 않는다. 대신 실행 직전 자동 가드(대상 호스트가 개발 환경인지·지정한 테스트 대상인지·내부 테스트 수단인지·실비용이 발생하지 않는지)가 하나라도 어긋나면 멈춘다. 지시 없는 상시 실행은 하지 않는다.

**Why** 실행을 지시받고도 단계마다 승인을 다시 물으면 자동화의 의미가 없다. 승인을 없애는 대신 조건 검사를 기계에 넘긴다.

## 9. 부재 중에는 권고안으로 진행하고 결정 기록을 남긴다

**규칙** 사용자가 「확인할 것이 있으면 권고안 기준으로 진행하라」고 하고 자리를 비우면, 선택지·채택한 안·설계와 다르게 정한 것을 결정 기록 문서에 남긴다. 복귀 시 「이런 선택지가 있었고 이렇게 구현했다, 바꿀 것이 있는가」를 한 번에 묻는다. 상태를 바꾸는 호출(API·배치·커밋되는 DB 쓰기)은 하지 않는다.

**Why** 밤사이 진행을 멈추지 않으면서도, 사용자가 되돌릴 수 있는 지점을 남기기 위해서다.

두 가지 형태로 썼다.
- **야간 분석** — 산출은 새 문서뿐(코드 수정·커밋·기존 문서 수정 금지). 결과는 「사람이 결정할 목록」과 「실측 대기 목록」으로 낸다.
- **야간 구현** — 착수 전에 되돌림 기준점을 만든다(압축 백업 + 사용자가 고른 방식의 로컬 기준점, 푸시 없음). 구현은 단위별로 위임하고 매번 메인이 검증한다. 사람이 있어야 하는 확인(화면 실측 등)은 다음 날로 넘긴다.

## 10. 돌고 있는 작업을 멈추거나 다시 띄울 때는 먼저 묻는다

**규칙** 이미 실행 중인 위임을 멈추거나 재시작할 일이 생기면 그대로 두는 선택지를 포함해 먼저 묻는다.

**Why** 설정을 빠뜨렸다는 이유로 묻지 않고 멈춘 뒤 다시 띄워, 앞서 쓴 토큰을 버렸다.

## 11. 승인 전달 — 에이전트가 둘 이상일 때

**규칙** 사용자가 한 에이전트 화면에서 승인했다면, 그 에이전트가 다른 에이전트에게 「사용자 승인:」과 사용자 원문(인용)·승인 대상·범위를 명시해 전달한다. 명시가 없거나 범위를 벗어나면 받은 쪽은 진행하지 않고 되묻는다.

**Why** 원문·대상·범위를 함께 적게 해야 승인 범위가 슬며시 넓어지지 않는다. 상세는 [역할과 승인 전달](../07_multi-agent/03_roles-and-approval-relay.md).
