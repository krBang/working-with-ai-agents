# 증거 우선 — 부재는 증명이 아니다

에이전트의 가장 비싼 실수는 「없다」「불가능하다」「확인했다」를 가볍게 말하는 것이다.
사용자는 그 문장을 믿고 다음 결정을 내리기 때문이다.

## 1. 부재를 근거로 단정하지 않는다

**규칙** 검색 0건·조회 무결과는 「없다/불가능하다」의 증거가 아니다. 「X 없음/불가」를 결론으로 낼 때는 해당 분기를 열어 읽고, 읽은 위치(file:line·쿼리)를 근거로 함께 적는다. 못 읽었으면 「미확인」으로 두고 실측 항목에 올린다.

**Why** 「이 유형의 건은 그 처리 경로를 탈 수 없다」고 판정한 근거가 루틴 안 키워드 검색 0건이었다. 실제로 루틴을 열어 보니 그 유형은 다른 상태 코드로 표현돼 있었고, 차단이 아니라 조건부 허용으로 들어 있었다. 차단 조건이 없다는 것이 통로가 없다는 뜻은 아니었다.

**키워드가 안 잡히는 세 가지 이유**

| 이유 | 예 |
|---|---|
| 다른 이름·코드값으로 표현돼 있다 | 업무 용어로는 이름이 있는데 코드에는 상태 코드 값만 있다 |
| 차단이 아니라 조건부 허용 형태다 | `IF 한도 >= 수량 THEN 허용` — 「금지」라는 단어가 어디에도 없다 |
| 다른 레이어에 있다 | SQL 리터럴이 아니라 ORM `save()`, 프로시저, 배치, 메시지 컨슈머 |

**적용**
- 게이트·정책·가능 여부 판정 로직은 특히 조건부 허용으로 쓰인 경우가 많다. 분기 번호를 따라 실제 본문을 읽는다.
- 보고할 때 「무엇을 읽어서 그렇게 판단했는지」를 같이 쓴다. 「검색 0건」만으로 말하지 않는다.
- 도구가 0건을 돌려줄 때도 같다. 정적 참조 조회 도구의 0건은 「스캔 범위 안에서 문자열 참조를 못 찾았다」일 뿐이다.

## 2. 「코드로 확인했다」는 파일을 열어 로직을 읽었을 때만

**규칙** 검색 히트만 보고 「코드로 확인」이라고 쓰지 않는다.

**Why** 확인의 깊이가 문장에 드러나지 않으면 사용자는 재검증할 것과 믿을 것을 가를 수 없다.

## 3. 「누가 만드는가」는 최소 세 경로를 병렬로 본다

**규칙** 테이블에 행을 만드는 주체를 `INSERT INTO <table>` 리터럴 검색만으로 판정하지 않는다. ① SQL 리터럴(프로시저·매퍼) ② 엔티티 클래스명 + `save`/`persist`(ORM) ③ 메시지 컨슈머·배치를 같이 본다. 프로시저를 정본으로 지목하기 전에 호출부가 실재하는지 확인한다.

**Why** 리터럴 검색이 레거시 프로시저 여러 곳만 잡았고, 실제 정본인 컨슈머 서비스는 ORM `saveAll()`을 써서 검색에 아예 안 걸렸다. 파일이 남아 있다는 것은 쓰인다는 증거가 아니다.

## 4. 도구 목록에 없다는 것도 「불가능」의 근거가 아니다

**규칙** 가진 도구에 기능이 안 보이면 로컬 규칙 파일·스크립트·원본 API를 먼저 확인한다.

**Why** PR에 리뷰어를 빠뜨린 뒤 「도구에 수단이 없으니 PR을 닫고 다시 만들어야 한다」고 단정했다. 로컬 규칙 파일에는 REST 호출로 붙이는 절차가 이미 적혀 있었다.

## 5. 종결(✅) 전에 한 번 더 반증한다

**규칙** 미결을 종결로 바꾸기 전에 반대 가설을 한 번 세워 본다. 종결 근거가 「부재」이거나 「전언 요약」이면 종결하지 않고 실측 항목으로 내린다.

**Why** 틀린 종결은 메모리에 굳는다. 다음 세션은 그것을 확정 사실로 읽고 그 위에 설계를 쌓는다.

## 6. 근거의 출처를 네 가지로 구분해 적는다

| 출처 | 표기 예 | 취급 |
|---|---|---|
| 코드에서 읽음 | `파일:줄` | 사용자 발언과 무관하게 유지한다 |
| 데이터 실측 | 쿼리·창(기간)·판정 | 창과 환경(개발/운영)을 같이 적는다 |
| 사용자 발언·전언 | 「」 인용 | 전제로 받는다. 다만 말하지 않은 부분을 채우지 않는다 |
| 내 추론 | 「추정」 | 결론처럼 쓰지 않는다 |

**Why** 사용자가 하지도 않은 결론을 확정 서술로 메모리에 적은 일이 있었다. 넷을 섞으면 무엇이 흔들릴 수 있는 사실인지 알 수 없다.

## 7. 사용자가 데이터로 확인해 가는 중엔 추정으로 빈칸을 채우지 않는다

**규칙** 답은 「데이터에 찍힌 사실」만 말한다. 모르는 것은 「모름」과 확인 쿼리로 답한다. 원인·의도·해석(「~로 보인다」「~했을 것」)을 결론처럼 섞지 않는다.

**Why** 한 건의 이력을 추적하면서 근거 없는 원인 추정을 연달아 내놓았고, 매번 틀려 사용자의 확인 작업을 방해했다.

## 8. 정책·허용 여부의 근거 순서

**규칙** 「X는 Y가 되는가」는 정책 문서 → 화면 → 코드·기준정보 → 운영 실측 순으로 근거를 댄다. 사용자가 정책을 말하면 그 자리에서 과제 메모리의 「확정 정책·결정 표」에 올린다.

**Why** 실측만으로는 「막혀 있다」가 아니라 「그런 사례가 없었다」만 말할 수 있다. 또 이미 사용자가 확인해 준 정책을 표에 올리지 않아 나중에 미확인 항목으로 다시 제기했다.

## 9. 메모리에 적힌 사실도 쓰기 전에 다시 본다

**규칙** 메모리의 컬럼·코드값·file:line 주장은 그 시점의 관찰이다. 쿼리나 설계에 쓰기 전에 현재 코드·DB로 재확인한다.

**Why** 메모리에 코드값이 잘못 적혀 있던 사례가 있었고, 코드는 그 뒤로도 계속 바뀐다.

## 10. 집계 단위와 판정 단위를 맞춘다

**규칙** 라인 단위 사실을 말하려면 라인 단위로 매칭한다. 상위 단위 조건으로 뽑은 수치는 상한선일 뿐 실측이 아니다. 상태 이력이 한 테이블에 섞여 있으면 구분 조건(원본/취소 등)을 명시한다.

**Why** 여러 유형의 라인이 섞인 건에서 상위 단위 조건으로 하위 라인을 세어, 실제로는 다른 유형의 라인이 대상 유형으로 집계됐다. 또 구분 조건 없이 훑은 결과를 「원본 건의 이야기」로 읽은 적도 있다.

## 11. 위임 결과의 부재형 결론은 반증한 뒤에 전달한다

**규칙** 서브에이전트가 「수단 없음」「영향 없음」이라고 보고하면 메인이 해당 위치를 열어 확인한 뒤 전달한다. 리뷰 지적도 같다. 각 지적에 ✅확인 / ⚠오탐 / 미검증을 붙인다.

**Why** 위임 결과의 「그 상태로 만들 수단이 없다」를 그대로 전달했는데 실제로는 다른 API 조합으로 가능했다. 리뷰 에이전트의 지적 절반이 재검증에서 오탐으로 드러난 적도 있다.

## 12. 영향도는 「그 흔적을 읽는 모든 코드」를 열어서 판정한다

**규칙** 데이터 형태를 바꾸는 설계의 영향도는 전제 몇 개에서 연역하지 않는다. 검색 키(테이블명·구분 조건·코드 enum)로 레포별 전수 목록을 만들고 영역별로 열어 읽는다. 「영향 없음」도 file:line 근거를 달고, 못 읽은 것은 미확인으로 둔다.

**Why** 두 가지 전제에서 연역한 영향 목록이 전체 취소 경로의 이중 처리를 빠뜨렸다. 「나중에 그 데이터를 다시 읽는」 경로가 핵심이었다.
