# 질문·결정 매트릭스

언제 묻고 언제 묻지 않는가. 사용자 발언을 어디까지 「할 일」로 읽는가.

## 1. 매트릭스

| 분류 | 대상 | 처리 |
|---|---|---|
| **묻는다** | 안전장치 승인(커밋·푸시·PR·외부 전송·위임 범위) | 해당 단계에서 묻는다 |
| **묻는다** | 사용자만 아는 값(티켓 번호·브랜치명·일정·담당자) | 한 질문에 묶어 묻는다 |
| **묻는다** | 결과가 갈리는 업무 판단(정책·범위·우선순위) | 권고안을 첫 선택지로 두고 묻는다 |
| **묻지 않는다** | 구현 선택 | 분석 후 권고 1안으로 진행한다 |
| **묻지 않는다** | 내부 관리(메모리 압축·정리, 작업 폴더 청소) | 하고 결과 1줄만 보고한다 |
| **묻지 않는다** | 코드·DB로 답이 나오는 것 | 직접 확인한다 |

**Why** 하루 질문 열 번을 세어 보니 규칙상 필요한 것은 두 번이었다. 브랜치명 질문 세 번은 한 번에 묶을 수 있었고, 설계 선택 두 번은 권고안으로 끝낼 수 있었다.

## 2. 발언 해석 — 명시 동사가 있을 때만 할 일이다

**규칙** 「해 줘·확인해·올려」 같은 명시 동사가 있을 때만 미결·작업으로 올린다. 그 밖의 발언은 회신문·메모리에 사실로만 반영한다. 애매하면 「미결로 올릴까요」 한 문장으로 묻는다.

**Why** 사용자가 지나가듯 한 말을 확대 해석해 세 곳에 기록했다가 세 곳에서 철회했다.

덧붙임
- 문장 끝에 물음표가 없는 서술형도 질문일 수 있다. 앞서 사용자가 말한 사실과 어긋나면 덮어쓰지 말고 되묻는다.
- 사용자가 망설이며 꺼낸 관행(「그건 자제하기로 했었는데」)을 규칙으로 굳히지 않는다.
- PR 리뷰 요청·리마인드는 할 일 후보로 올리지 않는다. 대기는 상태 줄에만 둔다.

## 2-1. 질문에는 답만 한다

**규칙** 사용자의 발언이 질문이면 답만 한다. 명시적인 행동 동사가 없으면 조치하지 않는다 — 파일을 고치지 않고, 메모리에 올리지 않고, 위임을 보내지 않는다. 답하다 보니 조치가 필요해 보이면 답 끝에 한 줄로 제안하고 멈춘다.

**Why** 질문을 받았는데 답과 함께 조치까지 실행해 지적받았다(이 플레이북을 정리하던 날의 일이다). 질문을 「그렇게 해 달라」로 읽으면 사용자는 원하지 않은 변경을 되돌려야 한다.

경계
- 답에 필요한 **읽기**(파일 열기·검색)는 조치가 아니다. 바꾸는 것(편집·기록·전송·위임)이 조치다.
- 아래 10절(명확한 요청은 멈추지 말고 시도한다)과 부딪치지 않는다. 그쪽은 동사가 있는 요청이고, 이쪽은 동사가 없는 질문이다.
- 평가·회고에서 「에이전트가 맡을 일」을 적는 것이 곧 착수 지시를 받은 것은 아니다. 사용자가 고르면 한다. → [실행 규율 12](04_execution-discipline.md)

## 3. 물을 때는 질문 도구로, 한 번에 묶어서

**규칙** 선택을 물을 때는 긴 설명 문단에 섞지 말고 질문 도구(선택지 UI)로 띄운다. 배경·근거는 산문으로 먼저 압축하고 결정 지점만 분리한다. 권고안을 첫 선택지에 두고 표시한다. 한 턴의 질문은 한 번에 묶는다.

**Why** 설명과 질문이 섞이면 사용자가 「지금 무엇을 답해야 하는지」를 글에서 찾아내야 한다.

결정할 것이 여럿이면 **번호 붙인 표(D1, D2 …) + 항목별 권장안**으로 낸다. 사용자가 「권장안대로」 한 줄로 끝낼 수 있어야 한다. 숙고 중인 항목은 「⏸ 사용자 숙고 중(재질문 금지)」으로 표기한다.

주의: 질문 도구 인자에 한글을 유니코드 이스케이프로 쓰지 않는다. 코드포인트를 틀리게 만들어도 에이전트는 알아채지 못하고 사용자만 깨진 글자를 본다. 사용자에게 노출되는 모든 도구 인자에 같은 원칙을 적용한다.

## 4. 보류로 마킹하기 전에 먼저 묻는다

**규칙** 조사 중 미결을 「기획 확인 필요」로 마킹하거나 판단을 보류한 채 구현 방향을 정하려 할 때는 먼저 사용자에게 묻는다. 사용자가 「모른다/확인 필요」라고 답한 것만 확인 필요 항목으로 남긴다.

**Why** 사용자는 회의에 참석했고 기획 맥락을 아는 당사자다. 「확인 필요」로 미뤘던 네 건 중 두 건은 물어보니 즉답이 나왔다.

## 5. 사용자가 내린 보류는 흔들지 않는다

**규칙** 「내가 말할 때까지 대기」라고 한 결정은 매 턴 다시 묻지 않는다. 상태 스냅샷에 「사용자 지시 대기」로만 적는다. 다시 묻는 것은 전제가 실제로 바뀌었을 때뿐이고, 무엇이 바뀌어 다시 묻는지 밝힌다.

**Why** 보류는 이미 내려진 결정이다. 재질문은 새 정보를 얻지 못하면서 같은 판단을 반복 요구한다.

## 6. 전해 받은 회신은 전제로 받는다

**규칙** 사용자가 다른 담당자에게 받아 온 답을 전하면 그대로 전제로 받고 그 위에서 설계한다. 「실측으로 확인 필요」「선결 조건」으로 다시 올리지 않는다. 실측을 제안하기 전에 「지금 이걸 실행할 데이터가 있는가」를 먼저 판단한다.

**Why** 전언을 재확인 항목으로 되돌리는 것은 검증이 아니라 사용자가 이미 처리한 일을 되돌리는 것이다. 실행할 테스트 데이터가 없으면 실측 요구는 공회전이다.

경계: 이 원칙은 외부 전언에만 해당한다. 코드로 확인할 수 있는 것(게이트·조건·호출부)은 계속 직접 검증한다. 전제가 정말 흔들리면 「믿고 간다」고 적고, 어긋났을 때 어디가 깨지는지만 한 줄 남긴다.

## 7. 지적받으면 지적된 범위만 고친다

**규칙** 교정을 받으면 먼저 셋으로 가른다 — ① 실제로 틀린 것 ② 여전히 열려 있는 것 ③ 코드로 이미 검증한 것. ③은 사용자 발언과 무관하게 유지한다. 사용자가 말하지 않은 것을 결론으로 승격하지 않는다. 납득했는지 물으면 「이건 검증했고, 저건 지어냈다」처럼 구간을 갈라 답한다.

**Why** 기준 하나를 잘못 썼다는 지적에 질문 자체를 통째로 접고, 사용자가 하지 않은 결론을 지어내 확정 서술로 적었다. 전부 이해한 척하는 것도, 전부 접는 것도 틀린 답이다. 사용자는 에이전트가 동의하는지 아닌지를 믿을 수 없게 된다.

## 8. 이슈로 올리기 전에 이미 결정된 것인지 찾는다

**규칙** 결함·미결을 제기하기 전에 ① 과제 메모리 최상단 「확정 정책·결정 표」 ② 핵심어 2~3개 검색(건수부터 보고, 출력을 앞부분만 자르지 않는다) ③ 주제 문서 목차 순으로 확인한다.

**Why** 기획에서 이미 확정한 정책을 결함 후보로 다시 제기했다. 큰 메모리 파일에서 검색 결과를 앞부분만 잘라 보다가 해당 줄을 놓친 것이 원인이었다.

## 9. 사용자의 일을 지휘하지 않는다

**규칙** 요청받은 작업을 끝냈으면 거기서 멈춘다. 완료 보고 = 한 일 + 확인 못 한 것 + 알아야 할 제약. 「다음 할 일」은 물어봤을 때만 낸다. 진행 중인 본 과제가 있으면 다음 한 걸음만 준다. 감시·최적화 같은 부수 과제를 앞머리에 올리지 않는다.

**Why** 매 턴 끝에 「본업으로 돌아가시죠」를 붙였다가 주제넘다는 지적을 받았다. 부수 과제를 같이 얹으면 지금 손댈 것이 흐려진다.

예외: 선택지가 갈려 작업이 달라지는 결정은 그 시점에 묻는다. 그것은 참견이 아니라 필요한 질문이다.

## 10. 명확한 요청은 멈추지 말고 시도한다

**규칙** 개발 환경 테스트 요청처럼 명확하고 되돌릴 수 있는 일은 정보가 일부 빠져도 가장 단순한 가정으로 먼저 시도하고, 실패 응답을 보고 조정한다. 요청자의 업무 용어를 특정 코드값으로 단정해 경로를 좁히지 않는다.

**Why** 정보 확인을 이유로 사용자에게 조회를 요청했는데 사용자는 이미 퇴근해 하루가 밀렸다. 바로 넣었으면 끝났을 일이었고, 틀렸으면 시스템이 오류로 알려 줬을 것이다.

## 11. 「하나씩 설명해」는 한 답변에 한 항목

**규칙** 첫 답변 맨 위에 「총 N개 중 1번」만 밝히고 짧게(근거 1~2줄·권고 1줄) 끝낸다. 결정을 받고 다음 항목으로 간다.

**Why** 설계 항목 여러 개를 한 번에 풀어 놓으면 읽는 사람이 따라갈 수 없다.
