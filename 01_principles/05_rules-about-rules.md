# 규칙에 대한 규칙

규칙을 어떻게 만들고, 어디에 두고, 언제 지우는가.

## 1. 강제 수준 사다리

같은 실수를 막는 수단은 강한 쪽부터 검토한다.

| 수준 | 수단 | 언제 |
|---|---|---|
| 1 | 권한 설정(`deny`/`ask`)·실행 전 훅 차단 | 어기면 되돌리기 어려운 것(커밋·푸시·비밀 파일·운영 접속) |
| 2 | 도구 안의 가드(입력 검사·접속 대상 검사·미리보기 확인) | 도구를 통해서만 일어나는 실수 |
| 3 | 스크립트·스킬의 절차 단계 | 순서·형식이 정해진 반복 작업 |
| 4 | 입력 훅이 붙이는 문맥(모드) | 특정 키워드가 나올 때만 떠올려야 하는 것 |
| 5 | 규칙 문구(CLAUDE.md·메모리) | 판단이 필요해 기계로 못 거르는 것 |

**Why** 주간 회고에서 「규칙은 있는데 안 지켜짐」으로 분류된 항목이 매주 나왔다. 문구를 한 줄 더 적어도 같은 실수가 반복됐고, 훅으로 올린 뒤에는 재발하지 않았다.

예: 「메인 워킹트리가 깨끗하면 worktree를 만들지 말고 브랜치를 전환하라」는 문구로 안 지켜져서, 훅이 `git worktree add`를 감지해 메인이 깨끗하면 확인 창을 띄우게 했다.

## 2. 규칙은 실제 실패 뒤에만 더한다

**규칙** 일어나지 않은 실수를 예방하려고 규칙을 미리 쌓지 않는다. 더할 때는 새 파일을 만들지 않고 기존 묶음 파일의 절로 넣는다. 넣기 전에 같은 묶음에서 겹치는 줄·낡은 줄을 먼저 합치거나 지운다(같은 자리의 옛 줄은 남기지 않는다).

**Why** 피드백 메모리가 수십 개로 불어나자 같은 내용이 세 군데에 다르게 적히고(기록 시점 규칙 3벌), 서로 충돌했다. 충돌하는 규칙은 둘 다 안 지켜진다.

## 3. 사례가 두 번 나오면 일반 규칙으로 승격한다

**규칙** 같은 실패 유형이 다른 모습으로 재발하면 사례별 메모를 일반 규칙으로 올린다.

**Why** 「INSERT 리터럴 검색으로 생성 주체 오판」과 「키워드 0건으로 기능 부재 오판」은 같은 뿌리(부재를 근거로 단정)였다. 사례별로만 적어 둬서 일반화가 안 됐다.

## 4. 규칙 문서는 짧게, 절차는 스킬로

**규칙** 항상 로드되는 규칙 파일은 200줄 이하로 유지한다. 줄마다 「지우면 실수하는가」를 묻는다. 순서가 있는 절차(보고 작성·검증·메모리 정리)는 스킬로 옮기고, 특정 폴더에만 해당하는 규칙은 그 폴더의 규칙 파일로 옮긴다.

**Why** 항상 로드되는 문서가 길어지면 첫 턴 컨텍스트가 커지고 중요한 줄이 묻힌다.

## 5. 서브에이전트에 닿아야 하는 것은 rules 파일로

**규칙** 위임받은 에이전트는 메인의 메모리를 보지 못한다. 반드시 지켜야 할 도메인 함정은 프로젝트 rules 파일에 두고(항상 로드), 메모리 인덱스에는 포인터 한 줄만 둔다. 그래도 필요한 것은 위임 프롬프트에 직접 적는다.

**Why** 메모리에만 있던 함정이 구현 담당 에이전트에 닿지 않아 같은 실수가 위임 결과에 다시 나왔다. → [함정 파일 패턴](../03_memory-system/03_trap-file-pattern.md)

## 6. 규칙 파일을 고친 뒤에는 세션을 다시 시작한다

**규칙** CLAUDE.md·rules 파일을 고쳤으면 세션을 재시작한다. 스킬·메모리 파일은 즉시 반영되므로 재시작이 필요 없다.

**Why** 위임 에이전트는 세션 시작 시점의 규칙으로 일한다. 고친 직후의 위임은 옛 규칙을 따른다.

## 7. 하네스의 기본 지시와 사용자 규칙이 충돌하면

**규칙** 사용자 규칙이 우선한다. 충돌 자체를 설정으로 없앤다(예: 커밋·PR 서명 문구를 끄는 설정).

**Why** 세션 시작 안내문이 「PR 설명 끝에 생성 도구 서명을 붙여라」고 지시했고, 그것을 따라 PR 여러 건에 서명을 붙였다가 전부 지웠다. 커밋 메시지만 확인하고 「서명 없음」이라 판단한 것도 문제였다 — 오염된 것은 PR 본문이었다.

## 8. 스킬은 「불리는지」를 시험하고 기록한다

**규칙** 스킬을 만들면 실제 사용자 문장으로 새 세션에서 불러 본다. 안 불리면 description을 고치고, 시험 문장·결과·조치를 스킬 파일 끝 표에 남긴다. 반드시 먼저 실행돼야 하는 스킬은 입력 훅으로 실행 지시를 붙인다.

**Why** 검증 스킬의 첫 description은 불리지 않았다. 새 세션이 메모리를 먼저 읽고 「이미 검증 끝」이라고 판단했기 때문이다. 「다른 확인보다 먼저 이 스킬을 연다」는 문구를 넣은 뒤에야 불렸다.

## 9. 규칙 개편의 효과는 측정하되 착시를 의심한다

**규칙** 개편 전후를 세션 기록으로 비교한다(사용자 메시지 100개당 질문 수·에이전트 호출 수·정정 발화 수 등). 표본이 작으면 결론을 내리지 않는다. 같은 모델·같은 진입점으로 고정한 비교와 월별 추이를 함께 본다.

**Why** 개편 2주 뒤 측정에서는 질문이 절반으로 줄어 보였다. 표본을 전체 기간으로 넓히자 질문 수는 줄지 않았고(개편 직전 몇 주가 유난히 높았던 것), 확인된 효과는 에이전트 호출 감소 하나였다. 정정 발화 감소는 개편 전부터 이어진 추세와 모델 교체에서 분리되지 않았다.

도구: `session_metrics.py`

## 10. 규칙을 줄이는 정기 감사

분기에 한 번쯤 아래를 본다.

| 유형 | 조치 |
|---|---|
| 충돌(같은 주제에 다른 지시) | 한 문장으로 통일하고 나머지를 지운다 |
| 중복(규칙 파일과 메모리에 같은 내용) | 정본 한 곳만 남기고 다른 곳은 포인터로 |
| 군집(같은 주제의 작은 파일 여러 개) | 묶음 파일 하나로 합친다(본문은 원문 그대로 절로 옮긴다) |
| 저빈도(특정 상황에만 쓰는 형식 규칙) | 「상황별 형식 규칙」 한 파일로 묶어 인덱스에서 한 줄만 차지하게 한다 |
| 뒤집힌 결정 | 옛 줄을 지운다(「(이전)」으로 남기지 않는다) |

**Why** 한 번의 감사로 피드백 파일 45개가 묶음 7개로 줄고, 인덱스 크기가 절반이 됐다.

감사만으로는 늦다. 그사이에도 규칙은 는다. 그래서 감량을 **에이전트의 상시 책임**으로 두고 세 자리에 걸었다 — 넣는 자리(합치고 지운 뒤 넣는다), 주간 회고(4주 넘게 쓰이지 않은 규칙·겹치는 규칙을 지울 후보로 올린다), 크기 상한(메모리 인덱스·함정 파일). → [메모리 정리 루틴 8](../03_memory-system/02_maintenance.md)

## 11. 일하는 방식의 코어는 자동 정리 대상에서 뺀다

**규칙** 메모리 자동 정리는 과제 상태 줄만 줄인다. 작업 방식(피드백)·사용자·참조 메모리, rules 파일, 규칙 문서, 스킬은 크기가 커도 자동으로 줄이거나 합치지 않는다.

**Why** 일하는 방식이 깎이면 잘하던 일을 갑자기 못하게 된다. → [메모리 정리 루틴](../03_memory-system/02_maintenance.md)
