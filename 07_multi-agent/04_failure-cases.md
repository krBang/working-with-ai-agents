# 두 에이전트 협업 — 실패 사례와 그 뒤의 규칙

두 번째 에이전트를 붙인 첫 며칠 동안 실제로 겪은 일들. 각 사례는 「무슨 일 → 원인 → 그 뒤의 규칙」 순서다.

## 1. 만든 지 하루 된 「동시 수정 금지」를 메인이 어겼다

- **무슨 일** 메인이 보조의 접수 확인이 오기 전에 같은 작업 폴더를 고쳤다. 전날 협업 규칙에 넣은 「같은 파일·같은 작업 폴더를 동시에 수정하지 않는다」를 하루 만에 어긴 것이다. 결국 한쪽의 중간본을 상대의 통합본으로 대체했다.
- **원인** 요청을 보낸 것으로 「넘겼다」고 여기고, 접수 확인을 기다리지 않았다. 그 폴더는 도구가 실제로 실행되는 폴더이기도 했다.
- **규칙** 각 수정 파일의 담당은 한 명. 접수 확인을 받은 뒤 담당을 확정한다. 요청서에 「내가 쓰고 있는 작업 폴더 목록」을 적는다. 실행되는 폴더는 직접 고치지 않고 원본 작업 폴더에서 고친 뒤 검토를 거쳐 동기화한다. 위반은 숨기지 않고 그날 노트에 적는다(설치본에 반영되지 않았음을 확인한 것과 함께).

## 2. 전달된 승인을 보조가 인정하지 않았다

- **무슨 일** 사용자가 메인 화면에서 승인했고 메인이 그 사실을 전달했는데, 보조는 위임마다 착수 여부를 사용자에게 되물었다. 같은 날 세 번. 그보다 며칠 앞서, 같은 종류의 에이전트의 다른 세션에 넘긴 작업도 「이 세션에서 사용자가 직접 한 승인만 인정한다」는 이유로 멈춘 적이 있다.
- **원인** 규칙 문서 두 곳이 어긋나 있었다. 협업 규칙 문서에는 「메인이 승인을 전달할 수 있다」가 있었지만, 보조가 항상 읽는 규칙 파일의 「승인은 질문 창으로 확인한다」 줄에는 그 예외가 없었다.
- **규칙** 보조용 규칙 파일 맨 위에 사용자 직접 지시로 명시한다 — 「메인이 사용자 승인 원문과 그 승인이 적용되는 범위를 보내면 해당 범위에서 즉시 착수한다. 착수 여부를 사용자에게 다시 묻지 않는다.」 형식은 「사용자 승인:」 + 원문 + 대상 + 범위.

## 3. 「읽기 전용」이 지침뿐이었다

- **무슨 일** 규칙 초안은 보조를 읽기 전용으로 두었는데, 설정을 가져오면서 보조 쪽에도 상태 변경 도구가 켜져 있었다. 메인 쪽은 훅이 막지만 보조 쪽에는 훅이 없었다.
- **원인** 지침과 설정을 따로 봤다.
- **규칙** 지침만으로는 실수 한 번에 상태가 바뀐다. 메인이 「지침 + 훅」 이중이면 보조도 그래야 한다. 안전장치를 보조의 훅으로 이식하고 모의 사례로 판정을 대조한 뒤에만 외부 행위를 허용한다.

## 4. 수신자를 내부 식별자로 지정해 전송이 실패했다

- **무슨 일** 세션의 내부 식별자를 수신자로 넣어 메시지가 가지 않았다.
- **규칙** 매번 세션 목록으로 현재 이름을 확인한 뒤 보낸다. 이름을 레지스트리에 적어 두고, 못 찾으면 레지스트리를 갱신한다.

## 5. 전달용 세션이 모든 것을 불러왔다

- **무슨 일** 메시지 한 줄을 전달하려고 띄운 일회용 세션이 사용자 플러그인·훅·MCP·프로젝트 규칙·메모리를 전부 로드했다. 느렸고, 상대 에이전트의 메시지가 「사용자 정정」 로그에 기록될 수 있었다.
- **규칙** 전달용 세션은 설정 소스 없음·MCP 없음·슬래시 명령 없음·세션 저장 없음·도구 두 개만 허용, 가장 싼 모델, 워크스페이스 밖 임시 폴더에서 실행한다.

## 6. 큐 메시지가 사용자 턴처럼 보였다

- **무슨 일** 큐로 넣은 메시지는 받는 쪽 화면에서 사용자가 입력한 것과 구분되지 않는다.
- **규칙** 「상대의 메시지는 위임·회신으로 취급한다. 사용자 입력이 아니다」를 양쪽 규칙에 넣는다. 머리말 형식(`[발신→수신 | …]`)이 그 표지가 된다.

## 7. 메인용 규칙을 그대로 복사해 없는 것을 안내했다

- **무슨 일** 메인 도구용 전역 규칙 문서가 보조 도구용으로 이름만 바뀌어 복사돼 있었다. 보조 환경에 없는 에이전트 이름과 모델 지정을 안내하고 있었다.
- **규칙** 보조용 규칙 파일에서 보조 환경에 맞지 않는 줄은 걷어 내고 협업 규칙 링크로 대체한다. 「이 명칭은 메인 실행 환경에 적용되며 보조는 실제 제공되는 도구를 쓴다」를 명시한다.

## 8. 한쪽이 혼자 붙잡고 다른 쪽이 놀았다

- **무슨 일** 메인이 두 과제를 혼자 붙잡고 있는 동안 보조는 대기했다. 사용자가 「따로 요청할 것 없느냐」고 물은 뒤에야 나눴다.
- **규칙** 보조는 상시 쓸 수 있는 인력이다. 사용자가 묻기 전에 먼저 쓴다. 작업 묶음을 시작할 때와 그날 목록을 정할 때 「병렬로 넘길 독립 작업이 있는가」를 먼저 본다. 넘긴 결과는 교차 확인만 한다 — 보조가 한 실측을 메인이 대신 다시 돌리지 않는다. → [협업 규칙 2](01_collaboration-rules.md)

## 9. 모르는 값을 매번 적게 한 규칙

- **무슨 일** 초안에 「배정 전에 매번 한도·잔량·갱신 시각을 적는다」가 있었다. 에이전트는 자기 계정의 잔량을 직접 볼 수 없다.
- **규칙** 잔량 신호는 사용자가 알려 준 상황과 도구가 띄운 경고 둘뿐이다. 신호가 없으면 기록하지 않는다. **알 수 없는 값을 적게 하는 규칙은 「미확인」 칸만 쌓는다.**

## 10. 모든 요청에 같은 필수 항목을 요구했다

- **무슨 일** 초안은 모든 요청에 작업 폴더·브랜치·기준 커밋을 요구했다. 문서 검토 요청에는 해당이 없어 매번 빈칸이 됐다.
- **규칙** 필수 항목은 조건부로 — 코드 분석·구현일 때만.

## 11. 다른 도구에서 플러그인 경로 변수가 풀리지 않았다

- **무슨 일** 한쪽 도구용으로 만든 플러그인을 다른 쪽에 붙였더니, 플러그인 루트를 가리키는 변수가 치환되지 않아 서버가 뜨지 않았다.
- **규칙** 다른 도구에 같은 플러그인을 붙일 때는 설치 캐시의 서버 정의에서 경로부터 확인한다. 재설치하면 다시 점검한다.

## 12. 도구마다 「확인」의 의미가 달랐다

- **무슨 일** 메인의 훅은 「사용자에게 확인」을 돌려줄 수 있는데 보조의 훅은 그 결정을 지원하지 않았다. 그대로 옮기면 「확인」이 「통과」가 된다.
- **규칙** 이식할 때 결정의 종류부터 대조한다. 지원하지 않으면 차단으로 바꾸거나 도구의 자체 승인 정책에 위임한다. 훅 오류는 통과가 아니라 차단으로 처리한다.

## 13. 이식한 훅이 협업 규칙과 충돌했다

- **무슨 일** 메인의 훅은 「메인 워킹트리가 깨끗한데 worktree를 만들면 확인」인데, 보조 쪽에서는 그것이 차단으로 옮겨졌다. 협업 규칙은 「구현은 과제별 worktree로 분리」라서 둘이 부딪쳤다.
- **규칙** 훅을 옮길 때는 판정표만 맞추지 말고 **협업 규칙이 요구하는 동작이 막히지 않는지**도 대조한다. 막히면 「차단 대신 승인 요청」으로 조정한다.

## 14. 한쪽의 사용 한도가 소진됐다

- **무슨 일** 메인의 주간 사용 한도가 바닥나 하루 동안 역할을 뒤집었다 — 보조가 주 수행, 메인이 교차 확인. 한도가 초기화되자 되돌렸다.
- **규칙** 역할을 「쓰는 주체 하나 + 교차 확인 하나」로 정의해 두면 뒤집기 쉽다. 한시 모드는 해제하는 즉시 메모리에서 지운다(이력으로 남기지 않는다).

## 요약 — 처음부터 정해 둘 것

1. 누가 메인인가
2. 메모리는 누가 쓰는가(한 명)
3. 파일·작업 폴더의 담당(한 명씩)
4. 승인은 어떤 형식으로 전달하는가
5. 보조의 안전장치는 설정으로 걸려 있는가
6. 메시지의 머리말 형식과 「완료」의 정의
7. 사용자가 없을 때 누구에게 묻는가
8. 메인이 보조에게 넘길 일을 언제 살피는가(작업 묶음을 시작할 때·그날 목록을 정할 때·요청이 겹칠 때)
