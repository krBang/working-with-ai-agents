# 역할 분담과 승인 전달

## 1. 역할

| 영역 | 메인 에이전트 | 보조 에이전트 |
|---|---|---|
| 사용자 창구 | 사용자의 지시·승인을 받는다 | 사용자가 직접 지시한 것 + 메인이 전달한 것 |
| 메모리 | **쓴다**(유일한 작성자) | 읽기만. 갱신은 메인에 요청 |
| 일일노트 | 섹션 끝 append | 섹션 끝 append, 줄 머리에 `[이름]` |
| 규칙 파일 | `CLAUDE.md`(메인용)의 담당 | `AGENTS.md`(보조용)의 담당. 본문은 메인용과 같게 유지하되 보조 환경에 없는 도구·에이전트 이름은 걷어 낸다 |
| 구현 | 맡은 과제의 작업 폴더에서 | 맡은 과제의 작업 폴더에서(다른 폴더) |
| 통합 | diff·컴파일·시험 결과 확인 | 결과와 근거를 비식별 형태로 전달 |
| 독립 검토 | 요청하고, 지적을 재검증한다 | 같은 질문·원문으로 독립 판단한다 |
| 긴 읽기·초안·실측 | 필요할 때 | 여유가 있으면 먼저 맡는다 |

「한쪽이 메인을 잡아 주는 것이 가장 좋다」는 것이 며칠 운영한 뒤의 사용자 결론이었다. 두 에이전트가 각자 사용자에게 묻고 각자 상태를 적으면 사용자가 조율자가 된다.

보조는 사용자가 묻기 전에 먼저 쓴다. 메인이 혼자 붙잡고 있으면 보조는 논다. → [협업 규칙 2](01_collaboration-rules.md)

한쪽의 사용 한도가 소진되면 역할을 한시로 뒤집는다(보조가 주 수행, 메인이 교차 확인). 한도가 돌아오면 되돌리고, 한시 모드는 메모리에서 지운다.

### 2026-11-27 조정 — 역할을 좁혔다가 단계적으로 넓힌다

「동등한 협업자」로 시작했지만, 하루 사이에 보조 쪽 실패가 세 가지 겹쳤다. 사용자의 말을 「사용자 확정」으로 요약해 전했는데 실제 요건과 달랐고, 요청에 없던 설계 확장을 제안했고, 다른 사람의 PR 브랜치에 푸시했다. 그래서 당분간 메인이 작업을 배정·검수하고 보조는 읽기 전용 교차 검증만 맡기로 했다.

역할은 고정이 아니다. 읽기 전용 검증 → 경계가 분명한 소규모 구현 → 단독 업무 순으로, 같은 유형의 작업에서 범위를 지키는지 보면서 다시 넓힌다.

**Why** 두 에이전트의 판단이 검수 없이 각각 사용자에게 닿으면, 사용자가 어느 쪽 말이 자기 결정인지부터 가려야 한다. 사례는 [실패 사례 15~17](04_failure-cases.md).

## 2. 승인 전달

사용자는 메인의 화면에서 승인한다. 보조가 그 승인을 인정하려면 메시지에 세 가지가 있어야 한다.

```
사용자 승인: 「<사용자의 원문 인용>」
대상: <무엇에 대한 승인인가 — 파일·명령·범위>
범위: <어디까지 — 이 과제의 이 단계까지, 로컬 미커밋까지 등>
```

| 상황 | 보조의 행동 |
|---|---|
| 세 가지가 있고 요청이 범위 안이다 | 사용자 승인으로 보고 **즉시 착수**한다. 단 전달 승인은 로컬 작업 범위에만 쓰고, 외부 행위는 반드시 그 도구의 승인 창을 거친다 |
| 명시가 없다 | 진행하지 않고 메인에 되묻는다 |
| 범위를 벗어난다 | 벗어난 부분만 멈추고 메인에 되묻는다 |
| 도구 자체의 승인 창이 뜨는 행위(티켓 발번·수정, 명령 실행 권한) | 그 승인 창을 그대로 쓴다. 전달된 승인이 도구의 승인 창을 대신하지 않는다 |

**Why** 메시지는 화면에서 사용자 입력처럼 보이기도 하고, 반대로 보조가 「이것은 사용자가 아니라 다른 에이전트의 말」이라며 전달된 승인을 인정하지 않기도 했다. 둘 다 막으려면 형식이 필요했다.

이 규칙은 보조용 규칙 파일(`AGENTS.md`) **맨 위**에 「사용자 직접 지시」로 날짜와 함께 적는다. 협업 규칙 문서에만 두었을 때는 보조가 여러 번 불인정했다.

## 3. 보조 에이전트의 안전장치 — 지침이 아니라 설정으로

**문제** 「보조는 읽기 전용」이라는 문장은 지침일 뿐이었다. 설정을 가져오면서 보조 쪽에도 상태 변경 도구(DB 쓰기·티켓 발번·PR 병합)가 켜져 있었다. 그래서 메인과 같은 가드를 보조 쪽 훅에도 이식했다.

**결정** 보조도 구현을 한다. 그러니 도구를 끄는 대신 **메인의 안전장치를 보조의 훅으로 이식**하고, 그것을 외부 행위의 선행 조건으로 삼는다.

### 이식 절차

1. 보조 도구의 훅 스키마와 **테스트 호출**로 실제 도구 이름·인자 구조·승인/거부 응답 형식을 확인한다. 같은 명령도 셸·Git CLI·MCP가 서로 다른 인자로 전달된다. 파일 복사만으로는 같은 판정을 보장할 수 없다.
2. 그 입력을 메인의 가드 규칙에 대응시킨다. 훅이 포착하지 못하는 경로는 권한 설정으로 막는다.
3. 메인의 가드 정책 코드를 재사용할 수 있으면 재사용한다(판정 로직은 한 벌).

### 통과 기준

격리된 임시 레포·가짜 자격증명·모의 요청으로 **양쪽 판정을 표로 대조**한다. 운영계에 시험 요청을 보내지 않는다.

| 모의 입력 | 기대 |
|---|---|
| 전체 스테이징, `commit -a` | 양쪽 모두 차단 |
| 파일을 명시한 add, status, diff, log | 통과 |
| 커밋·푸시 | 승인 대기(메인) / 도구의 실행 정책이 승인 요청(보조) |
| 비밀번호 파일 내용 접근 / 경로만 환경변수로 지정 | 차단 / 통과 |
| 운영 서비스·호스트 직접 접속 / 개발 읽기 전용 | 차단 / 통과 |
| 문서에 쓴 SQL의 인덱스 조건 누락 / 정상 / 경고 | 중단 / 통과 / 경고 |
| 손상된 입력, 훅 오류 | **차단**(오류 시 통과시키지 않는다) |

- 훅 오류·미승인 호출에서 **실제 쓰기가 일어나지 않는지**도 확인한다.
- 결과표를 문서로 남기고 검토자(메인)에게 보낸다. 메인이 독립적으로 같은 사례를 다시 돌린다.

### 두 도구의 차이에서 배운 것

- 한쪽 도구의 훅은 「확인(ask)」 결정을 지원하지만 다른 쪽은 지원하지 않을 수 있다. 지원하지 않는 쪽에서 「확인」을 돌려주면 호출이 그냥 계속된다. 그 경우 **차단으로 바꾸거나**, 도구의 자체 승인 정책(명령 정책·MCP 도구별 승인)에 위임하고 훅은 별도 결정을 돌려주지 않는다.
- 훅은 **사용자가 직접 검토하고 신뢰해야** 활성화된다. 에이전트가 스스로 신뢰를 설정하지 않는다. 신뢰 전까지 외부 행위는 하지 않는다.
- 모의 검사로 확인한 것은 「판정」까지다. 실제 화면에 승인 창이 뜨고 취소하면 실행되지 않는지는 사용자와 함께 한 번 확인한다.
- 설정 변경은 **백업 후 적용**한다. 사용자가 허용한 범위(자기 설정 파일·자기 규칙 파일·훅 파일)를 요청서에 인용해 둔다.

## 4. 보조용 규칙 파일(AGENTS.md)에 넣은 것

- 적용 범위 — 처음에는 「둘은 동등한 협업자, 『읽기 전용』 같은 작업 범위는 해당 요청에만 적용」이었다. 2026-11-27부터는 당분간 「메인이 배정·검수, 보조는 읽기 전용 교차 검증」(1절)을 맨 위에 둔다
- 승인 전달 규칙(위 2절)과 그 날짜
- 사용자에게 묻는 경우의 한정 — 직접 확인·결정이나 추가 승인이 필요할 때만
- 사용자 할 일 블록 형식
- 작업 전에 읽을 것 — 도메인 함정 파일
- 메모리의 위치와 「읽기만, 변경은 메인에 요청」
- 협업 규칙 문서 링크
- 나머지 본문(산출물 위치·일일노트·판단/보고·Git)은 메인용 규칙 파일과 같게

## 5. 사용자가 없을 때

- 로컬 작업은 양쪽 모두 계속한다.
- 승인이 필요한 항목은 **메인이 모아** 복귀 시 한 번에 보고한다.
- 보조가 막히면 사용자가 아니라 메인에게 묻는다.
- 부재 전에 사용자가 준 승인(「자기 설정 변경은 백업 후 적용까지 허용」 등)은 요청서 맨 위에 그대로 인용한다.
