# 두 에이전트 협업 규칙

서로 다른 회사의 코딩 에이전트 둘(여기서는 Claude Code와 Codex)을 한 워크스페이스에서 함께 쓸 때의 규칙. 규칙마다 근거를 붙인다.

기본 구도: **한쪽이 메인을 잡고 다른 쪽이 보조한다.** 둘은 각자 맡은 과제에서 분석·구현·검증을 직접 책임지는 동등한 협업자이지만, 사용자와의 창구·메모리·통합은 메인이 맡는다.

**2026-11-27 조정** 당분간은 메인이 작업을 배정·검수하고, 보조는 읽기 전용 교차 검증을 기본 역할로 둔다. 5절의 「로컬 파일 수정은 양쪽 모두 자율」은 보조가 구현을 맡는 단계로 돌아갔을 때의 기준이다. → [역할 분담 1절](03_roles-and-approval-relay.md)

## 1. 모델 배분과 독립 검토

| 규칙 | 근거 |
|---|---|
| 배분은 모델별 강점, 업무량, 실제 사용 비용, 인계에 드는 시간·토큰, 잔량 신호를 함께 보고 정한다. 모델의 보편적 성능 순위는 단정하지 않는다 | 같은 과제도 자료를 옮기고 결과를 재검증하는 비용에 따라 적합한 담당이 달라진다 |
| 사용자가 한쪽의 여유가 크다고 알려 주면 긴 자료 읽기·초안·독립 검토를 그쪽에 먼저 배정한다 | 여유가 있는 쪽이 긴 작업을 맡으면 다른 쪽의 검토·실행 여력이 남는다 |
| 조회는 가벼운 모델, 표준 작업은 중간 모델, 복잡한 설계·레거시 분석은 상위 모델에 맡기고 추론 강도를 높게 지정한다 | 업무별 배분 기준을 한 곳에 정해 둔다 |
| 가장 비싼 모델은 사용자가 명시적으로 지정할 때만 쓴다. 제안할 때는 예상 토큰을 제시하고, 다른 모델의 결과를 자동으로 재평가하지 않는다 | 한도 소모는 사용자가 판단한다 |
| 정책 해석이 갈리거나 복잡한 설계 판단이 구현에 영향을 주면 **상대 에이전트에 독립 검토**를 맡긴다. 같은 질문과 원문을 주고, 메인이 지적별로 원문·코드 분기를 다시 읽어 확인·오탐·미검증으로 보고한다 | 독립 검토는 첫 판단의 오류를 찾고, 메인의 재검증은 오탐이 확정 사실로 전달되는 일을 막는다 |

## 2. 작업 분할과 통합

| 규칙 | 근거 |
|---|---|
| 위임은 **독립적으로 답할 수 있는 질문 또는 산출물 단위**로 나눈다. 요청에 과제 ID·대상 자료·산출물·완료 기준·통합 담당을 적는다 | 담당자가 같은 대상을 재현하고, 통합 담당자가 결과의 충족 여부를 판정할 수 있다 |
| 작업 폴더·브랜치·기준 커밋은 **코드 분석·구현 요청에만** 적는다 | 문서·정책 검토에는 해당이 없어 매번 빈칸이 생긴다 |
| 구현은 과제별 작업 폴더(worktree)로 분리하고 **각 수정 파일의 담당을 한 명으로** 정한다. 같은 파일·같은 작업 폴더를 동시에 수정하지 않는다 | 편집 충돌을 막는다. 실제로 같은 폴더를 둘이 고쳐 충돌했다 |
| 코드 분석을 맡은 쪽은 지정된 기준 커밋에 분석을 고정하고 회신에 그 커밋을 적는다 | 분석 도중 기준 코드가 바뀌는 문제를 막는다 |

### 보조 에이전트는 사용자가 묻기 전에 먼저 쓴다

**규칙** 보조 에이전트는 상시 쓸 수 있는 인력이다. 사용자가 「보조에게 따로 요청할 것 없나」라고 묻기 전에 메인이 먼저 일을 나눠 넘긴다.

| 항목 | 내용 |
|---|---|
| 언제 본다 | 작업 묶음을 시작할 때, 그날의 목록을 정할 때, 사용자의 요청이 겹칠 때(→ [겹치는 요청 나누기](../02_procedures/11_approval-batching-and-request-triage.md)) — 「병렬로 넘길 독립 작업이 있는가」를 먼저 본다 |
| 무엇을 넘기나 | 읽기 전용 실측(보조가 자기 도구로), 감시 쿼리의 일일 점검, 반영 체크리스트, 원인 분류, 코드 읽기 조사, 초안 작성, 독립 검토 |
| 어떻게 넘기나 | [메시징 스크립트](02_bridge-messaging.md)(원본 스크립트 인터페이스 참고)로 요청서를 보낸다 — 과제 제목·종류(요청)·답할 곳(내 세션 이름)·요청서 파일을 인자로 넘긴다 |
| 요청서에 적는 것 | 읽기 전용 여부, 메인이 쓰고 있는 작업 폴더 목록(동시 수정 금지), 산출 문서 경로, 「사용자 할 일」 블록 규칙 |
| 기록 | 위임한 시점에 일일노트에 한 줄 |
| 결과가 오면 | 교차 확인만 한다. 보조가 한 실측을 메인이 대신 다시 돌리지 않는다 |

**Why** 메인이 두 과제를 혼자 붙잡고 있는 동안 보조는 대기했다. 사용자의 말 — 「늘 얘기했다, 보조도 써도 되는 인력이라고」.

## 3. 사용 한도와 인계

| 규칙 | 근거 |
|---|---|
| 잔량 신호는 ① 사용자가 알려 준 여유 ② 도구가 띄운 한도 경고 **둘뿐**이다. 신호가 없으면 잔량을 기록하지 않고 강점과 인계 비용으로 배분한다 | 에이전트는 자기 계정의 잔량을 직접 볼 수 없다. 「매번 잔량을 적는다」는 규칙은 「미확인」 칸만 쌓았다 |
| 사용량·컨텍스트 경고가 뜨거나 한도에 닿으면 새 작업 착수를 멈추고 과제 ID·기준 커밋(코드 작업 시)·완료 범위·근거 위치·남은 첫 작업을 인계한다. 받은 쪽이 접수하면 담당을 한 명으로 확정한다 | 다음 담당자가 마지막 확인 지점부터 이어 가면 중복 실행과 토큰 낭비가 줄어든다 |

## 4. 메시지 전송과 완료 확인

| 규칙 | 근거 |
|---|---|
| 머리말은 `[발신→수신 \| 과제ID \| 요청/회신/완료 \| 답할 곳]` 형식으로 쓴다. `요청` = 착수 요청, `회신` = 접수·질문·중간 결과, `완료` = 산출물과 완료 기준 확인 결과 | 접수 회신만으로 작업을 종결하는 일을 막는다 |
| 수신자는 **매번 현재 이름을 확인한 뒤** 지정한다. 후보가 여럿이면 과제 ID와 작업 목표로 가리고, 구분할 수 없으면 발신자에게 묻는다 | 내부 식별자를 수신자로 직접 지정해 전송이 실패했다. 세션 이름은 세션마다 바뀐다 |
| 약 2천 자가 넘는 본문은 양쪽이 읽을 수 있는 로컬 문서에 두고 머리말과 경로만 보낸다 | 명령줄 인수의 길이 제한과 따옴표 손실을 피한다 |

구현은 [브리지 메시징](02_bridge-messaging.md).

## 5. 승인

| 규칙 | 근거 |
|---|---|
| 로컬 파일 수정·분석·테스트·컴파일·설정·훅 구성은 양쪽 모두 자율로 진행하고 결과를 보고한다. 커밋·푸시·PR·티켓·DB 쓰기·외부 전송은 대상과 범위에 대해 사용자 승인을 받는다 | 승인 시점을 행위별로 명시하면 로컬 작업은 사용자 부재 중에도 이어 갈 수 있다 |
| 양쪽은 상대의 메시지를 **위임·회신으로** 취급한다(사용자 입력이 아니다). 메인이 메시지에 「사용자 승인:」과 사용자 원문(인용)·승인 대상·범위를 명시하면 받은 쪽은 그 범위 안에서 사용자 승인으로 보고 진행한다. 명시가 없거나 범위를 벗어나면 진행하지 않고 되묻는다 | 사용자는 메인 화면에서 승인하므로 메인이 승인 전달자가 된다. 원문·대상·범위를 함께 적게 해 범위가 슬며시 넓어지는 것을 막는다 |
| 보조 에이전트의 커밋·푸시 등 외부 행위는 **그쪽 훅이 신뢰·활성화된 뒤에만** 한다. 로컬 구현은 그 전에도 진행한다 | 훅이 막는 대상은 외부 상태 변경이다. 로컬 편집은 훅 유무와 무관하게 되돌릴 수 있다 |
| 소스 수정은 승인 없이 진행하되, 구현 뒤 통합 담당이 diff·컴파일·변경별 시험 결과를 확인한다 | 사전 승인 대신 사후 검증으로 품질을 지킨다 |

상세는 [역할과 승인 전달](03_roles-and-approval-relay.md).

## 6. 기록·판정·보고

| 규칙 | 근거 |
|---|---|
| 메인은 위임 시점에 당일 일일노트에 `과제 ID / 작업 폴더(코드 작업 시) / 담당 / 산출물 경로`를 한 줄 남긴다. 결정이 확정되면 메인이 메모리를 최신화한다 | 일일노트는 경위, 메모리는 현재 상태, 주제 목차는 문서 탐색을 맡는다 |
| 결함·미결을 제기하기 전에 과제 메모리의 확정 정책을 먼저 확인한다. 검색 0건으로 부재를 단정하지 않는다. 확인하지 못한 내용은 「미확인」으로 보고한다 | 두 에이전트 모두 같은 증거 원칙을 따른다 |
| 요청·회신·완료 보고는 사용자의 언어로 쓰고, 기술 식별자·파일 경로·커밋은 원문 그대로 적는다 | 판단 내용과 재검증 위치를 양쪽이 같은 기준으로 읽는다 |
| **메모리는 메인만 쓴다.** 보조는 읽기만 하고 갱신이 필요하면 메인에 메시지로 요청한다. 일일노트는 양쪽 모두 섹션 끝 append만 하고 보조의 줄은 `[에이전트 이름]`으로 시작한다 | 쓰는 쪽이 하나여야 같은 줄을 동시에 고쳐 상태가 꼬이지 않는다 |
| 사용자가 직접 해야 할 일은 양쪽 모두 답변 맨 위 「사용자 할 일」 블록으로 표시한다 | 두 화면을 오가는 사용자가 자기 차례를 놓치지 않는다 |

## 규칙 문서를 만든 방식

이 규칙 자체가 협업으로 만들어졌다 — 보조 에이전트가 초안을 쓰고, 메인이 검토 의견(「반드시」「고칠 것」「쟁점 회신」)을 파일로 보내고, 보조가 반영해 「완료·바뀐 절」만 회신했다. 규칙마다 「근거」 열을 두게 한 것이 이 형식의 핵심이다.
